title: v0.639.1
description: The increments released in Bynk v0.639.1.
---
Released on 17 November 2026 as **v0.639.1**, with the increments from v0.614.1 to v0.639.1.
See [Upgrading](/book/reference/upgrading/) for what to change when you move to it.

| Version | Highlights |
|---|---|
| **v0.639.1** | `bynk deploy` refuses to put a context that hosts agents on a different Worker script than it was last deployed to (into or out of a `[deploy.workers.<key>]` group, between groups, or after a group is renamed or re-keyed), since its agents' state would start empty; `--accept-fresh-agent <context>` starts it fresh and the old script is then reported as holding agent data (#3562, G5) |
| **v0.639.0** | `bynk dev` serves a `[deploy.workers.<key>]` group as one Worker on one port (`--context` naming a member serves the whole group), and `bynk dev inspect` lists and reads the agents of every member; `bynk.deploy.worker_groups_unsupported` is removed (#3562, G6) |
| **v0.638.1** | A `[deploy.workers.<key>]` group's calls are signed and verified under keys named for its member contexts, so a group can call across an edge and its members can call each other once deployed or run under `bynk dev` (#3562, G4-4) |
| **v0.638.0** | A call between two members of a `[deploy.workers]` group stays inside the Worker instead of crossing a Service Binding to itself; it is the same signed, contract-checked, admitted request, so values are copied, a callee's fault is the same `CalleeFaulted` and a refusal the same refusal (#3562, G3-2) |
| **v0.637.0** | `bynk revert` reverts a `[deploy.workers.<key>]` group as one Worker (`--worker KEY`), so every member goes back together; a member named with `--context` is refused, naming the Worker that holds it (#3562, G4-3) |
| **v0.636.2** | A cycle between Workers that involves a `[deploy.workers]` group is refused at check time as `bynk.deploy.worker_cycle` (renamed from `bynk.deploy.group_cycle`, never released), whichever two Workers and however the cycle is closed: a call, or a publisher's binding to its subscriber (#3562, G2b) |
| **v0.636.1** | `bynk deploy` no longer fails a first deploy when wrangler uploads the Worker and then reports `[code: 10007]` (a race in its follow-up lookup), if the account shows the upload landed as the Worker's only version; any other failure, and a Worker that already existed, stay fatal (#3562, G4-2) |
| **v0.636.0** | `bynk deploy` deploys a `[deploy.workers.<key>]` group as one Worker, in dependency order with the others, and `--worker KEY` selects a Worker by its directory; the ledger records a group Worker's contexts, and a member cannot be deployed alone (#3562, G4-1) |
| **v0.635.1** | Deploy's groundwork for a `[deploy.workers]` group (#3562, G4-0): the binding graph is keyed by Worker directory (a group's `name` override and its binding to itself no longer break the order), a group has one merged `bynk-contracts.json` and `bynk-secrets.json`, and a dependency's contract is looked up under the Worker that provides it; `bynk deploy` still refuses a group |
| **v0.635.0** | A `[deploy.workers.<key>]` group has one events fan-out for every member that publishes, so several members of a group may publish events; `bynk.deploy.multiple_publishers` is removed (#3562, G3-1) |
| **v0.634.8** | A conformance harness drives a call, a refusal, a fault and an event between contexts through every topology (separate Workers, a Worker group) and asserts the same observations in each (#3562, G3-0), and a `[deploy.workers]` group's `<member>.bynk-client.ts` is left out of the generated `tsconfig.json` as a context's `bynk-client.ts` is |
| **v0.634.7** | A `[deploy.workers]` group and another Worker (another group or a single context) whose members bind to each other in both directions are refused (`bynk.deploy.group_cycle`), even though the contexts themselves are acyclic (#3562, G2b) |
| **v0.634.6** | The design of Worker groups (`[deploy.workers]`) is recorded in an ADR, which amends ADR 0193 (D2) and ADR 0017 (#3562, G7) |
| **v0.634.5** | A Worker group's entry and members carry no `bynk dev` inspection route in a deploy build, and in a dev build a member answers only its own agents' inspect requests (#3562, G6 groundwork) |
| **v0.634.4** | The `bynk/architectureModel` request gives each handler the services and agents it `calls`, and each agent its `key` and `state` fields, for the component view |
| **v0.634.3** | A fixed asset in one member of a `[deploy.workers]` group that sits at the path of a literal HTTP route in another member is refused (`bynk.asset.shadows_route`, extended across a group's members) (#3562, G2b) |
| **v0.634.2** | Two members of one `[deploy.workers]` group that serve a fixed asset path from different files, or at paths one of which would be a folder of the other, are refused (`bynk.deploy.asset_path_conflict`); the same file reached by both members is fine (#3562, G2b) |
| **v0.634.1** | The `bynk/architectureModel` request gives each service its `protocol` and the `actors` its handlers admit |
| **v0.634.0** | A `[deploy.workers.<key>]` group now builds as one Worker: its members share one `index.ts` that tries them in manifest order, one `wrangler.toml` that merges their bindings, crons, queues and addresses, and a group has at most one member that accepts WebSockets (`bynk.deploy.multiple_websocket_members`); a `bundle` build says it ignores the groups (`bynk.deploy.workers_ignored_on_bundle`) (#3562, G2b step 2c-4b) |
| **v0.633.18** | The `bynk/sequenceModel` request walks nesting in full (with each block's `depth`), shows `?` as a `Break` block, and names each handler's `trigger`, each agent lifeline's `key` and each boundary call's `callee` (with its location) |
| **v0.633.17** | `bynk registry conformance`: `yank.yank` and `yank.unyank` wait up to 65 seconds for a cached index to show the change, instead of failing a registry whose edge cache briefly kept the old index |
| **v0.633.16** | Two contexts that consume the same queue are now refused, grouped or not (`bynk.queue.duplicate_consumer`), and `bynk.deploy.queue_consumer_conflict` is removed in its favour. A project this newly refuses built cleanly before but could never deploy, since Cloudflare allows one consumer Worker per queue (#3644) |
| **v0.633.15** | A Worker entry can be emitted as one member of a `[deploy.workers]` group, marking its router's own "not mine" answers so a group's dispatcher can try the next member (#3562, G2b step 2c-4a); no output changes until groups are switched on |
| **v0.633.14** | `bynk deploy`, `bynk revert` and `bynk dev` refuse a project with a `[deploy.workers]` group, until grouping is deployable (#3562) |
| **v0.633.13** | Two members of one `[deploy.workers]` group that declare the same HTTP route or consume the same queue are refused (`bynk.deploy.route_conflict`, `bynk.deploy.queue_consumer_conflict`); two members may still share a cron expression (#3562, G2b step 2c-3) |
| **v0.633.12** | A Worker's D1, R2, Analytics Engine and Vectorize resource names, and where its D1 migrations are staged, come from the `WorkerLayout` rather than the context name, with the identity layout unchanged (#3562, G2b step 2c-2) |
| **v0.633.11** | The handlers paths and cross-context handlers imports of a Workers build come from the `WorkerLayout` rather than being spelled in place, with the identity layout unchanged (#3562, G2b step 2c-1) |
| **v0.633.10** | A user sum variant spelled like an `HttpResult` variant (`Found`, `Gone`, ...) is its own constructor inside an `HttpResult` handler, so it no longer type-checks as the HTTP response or appears in the wire contract and OpenAPI document (#3631) |
| **v0.633.9** | `bynk/wireContract` describes every HTTP response's body (value, message, redirect, raw, stream) in a new `body` field, checked against `bynk openapi` |
| **v0.633.8** | `bynk/agentStateModel` trims trailing whitespace from an invariant's `doc` and omits it when empty, and documents its `range` as running from the keyword to the end of the predicate (#3608) |
| **v0.633.7** | The Workers emit loop in `bynk-driver` is split into a per-context function and two helpers, the shape `[deploy.workers]` groups will emit through (#3562, G2b) |
| **v0.633.6** | A `storefront` example, a typed front end over a generated `bynk client`, with a system test (#3508, BC7) |
| **v0.633.5** | `bynk/agentStateModel` lists each agent's `invariant` and `transition` declarations as an optional `invariants` array, with each one's formatted predicate text, range and documentation (#3608) |
| **v0.633.4** | `bynk/wireContract` carries an HTTP handler's success payload: a `success` ref to the `T` of `HttpResult[T]` and a `payload` per response (#3609) |
| **v0.633.3** | A Workers build places a context's staged binding files and assets directory through its `WorkerLayout` too, still the identity layout, ahead of `[deploy.workers]` groups sharing a directory (#3562, G2b) |
| **v0.633.2** | A `bynk dev` build records each agent instance's committed transitions in a bounded ring buffer, and `bynk dev inspect agent` returns them as `history` (slice 1 of the dev agent-inspection track) |
| **v0.633.1** | The `bynk dev inspect` reference, the run-locally guide and the runtime-library chapter describe agent inspection, and a workerd test shows a dev session's outcomes match a deploy build's (slice 0c of the dev agent-inspection track) |
| **v0.633.0** | `AnalyticsSql` reads Analytics Engine datasets through the account's SQL API, as one binding per Worker with positional `$1` parameters of `SqlValue`, a typed result and a `SqlRetryable | SqlRejected` error; `bynk dev` runs it on Cloudflare, with a one-time notice silenced by `[dev] analytics-sql = "allow"`; `Analytics.dataset()` names a dataset's environment-qualified table for such a query |
| **v0.632.2** | A `bynk dev --trace-events` request names the request that called it, so a client can join a call across Workers |
| **v0.632.1** | `bynk dev inspect agents` lists a running session's agent instances by key, and `bynk dev inspect agent <Class> <key>` reads one's stored state as JSON (slice 0b of the dev agent-inspection track) |
| **v0.632.0** | `bynk deploy` links each `MtlsCertificate` by name, writes the certificate's id into the Worker's configuration and records it in the ledger, failing when it is missing or ambiguous and never uploading one; `bynk dev` runs the binding on Cloudflare, with a one-time notice silenced by `[dev] mtls = "allow"`; the byte forms `receiveBytes` and `sendBytes` join `send` |

## ADR: store-unique-annotation
title: `@unique(by: k)` enforces a value on at most one entry of a store Map, at commit
summary: A storage annotation implying `@indexed`, checked against the staged postings when the state commits, refused as an InvariantViolation

**Context.** "No two customers share an email" cannot be expressed: an invariant may not scan a collection (#4034 allows only `size()`), and `@indexed(by: k)` maintains an index but enforces nothing, so every author writes a check-then-put that is right only while every writer remembers it.

**Decision.** `store customers: Map[CustomerId, Customer] @unique(by: email)` keeps a unique index on `email`. It implies `@indexed(by: email)`: the postings are the index's own, equality filters on the field route through them, and declaring both is the warning `bynk.store.unique_implies_indexed`. The check is at commit, against the staged state: `commitState` asks each `@unique` map whether any value it staged under the index is now held by more than one entry (the storage-backed handle reads that value's postings through the overlay, so a committed holder and a staged one meet; the in-memory handle checks its posting lists), and a duplicate refuses the commit as `InvariantViolation` with the declaration `unique`, named `<field>.<k>`, never carrying the value. Two puts of one value in one handler, and a put that collides with a committed entry, are refused; moving a value from one entry to another in one handler is allowed. An `Option` field is unique among its `Some` values: a `None` is not indexed. Because such a posting is keyed by the payload, an equality filter on an `Option` unique field is a scan, not a routed lookup. `by:` may be any `Key` type (#4037). Adding `@unique` to a field that already holds duplicates cannot be checked at build time; the first commit that touches a duplicated value is refused.

**Consequences.** Nothing that compiled before changes meaning (`unique` was an unknown annotation). The cost is one posting read per value a handler changes, on top of the maintenance an `@indexed` field already costs. The constraint is not recorded in the schema lock: adding or removing it never makes stored state unreadable, and the lock records shape. `bynk migrate sweep` does not yet report existing duplicates; that is a follow-up, as it needs the deployed wake path. Hover shows the annotation on the field as it shows every annotation; completion and semantic tokens are unchanged, because storage annotations have no editor support of their own today.

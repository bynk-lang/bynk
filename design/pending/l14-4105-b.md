## ADR: analytics-typed-reads
title: AnalyticsSql.select[T] writes its SELECT list from the written record
summary: How a typed Analytics read finds its columns, and where the tail adds what the compiler cannot know

**Context.** Part 2 of #4105 (part 1 is `writeValue`, whose ADR states the three-change design). A read type names its columns by hand today, in `Json.decode` over the untyped `data` text, so the order a writer chose and the names a reader uses are agreed by hand.

**Decision.** `AnalyticsSql.select[T](Instance, tail, params)` is, like D1's `select[T]`, lowered by the compiler over `query`, not a declared operation: the checker records `Callee::AnalyticsSelect`, and once the context's handlers are checked it writes the `SELECT` list from the record `Instance` is written with (every `Callee::AnalyticsWrite` of that instance in the context, found after the bodies are checked because a read may be checked before a write). A field of `T` that is a field of the written record reads its column (`blob1 AS "plan"`); a field that is not is a name the tail defines with `AS`, so the tail may start with a comma that continues the select list (`", count() AS n FROM {dataset} …"`), which is how the issue's `ByCountry { country, n }` works with a tail that otherwise starts at `FROM`. An alias the tail defines takes the place of a written column of the same name (so a field can total itself, `sum(double1) AS seats`), and aliases are found by a scan that tracks parentheses and quotes (an `AS` inside a cast or a subquery is not one). A number field reads the type its column was written with, or `Float` (anything else, such as an `Int` read of a `Float` column or a `Duration` of an `Instant`, is refused). The rows decode through the same row pass `Postgres` reads use for `int8`, so an `Int` field also reads a 64-bit integer the platform quotes as text, which cannot be confirmed against the live API here (no real Cloudflare in tests) and is tolerated either way. A field neither written nor aliased, a text field over a number column (or the reverse), a `T` that is not a record, and an instance written with two record types are compile errors (`bynk.types.sql_row_shape`, and `bynk.types.argument_mismatch` for the two-record case), so no new code is added. The result is `Result[List[T], AnalyticsReadError]`, `AnalyticsQuery(AnalyticsSqlError)` or `AnalyticsDecode(DecodeError)` (the prefix because `Sql` and `Decode` are `SqlReadError`'s). The rows are decoded with the JSON decoder over the reply's `data`; a `Bool` or enum is written as text, so it is read as a `String`.

**Consequences.** Reordering the written record changes which column a name reads, and part 3 (the lock) is what makes that an error; until then the typed read follows the record as it is now, which is already safer than counting columns by hand. A read with no `writeValue` of the instance in its context has no record to read from, and takes only aliases. Hover on a column, completion of written fields in a read type, and signature help for the type argument are not in this change.

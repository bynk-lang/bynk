## ADR: boundary-refinement-entailment
title: A context boundary admits a stronger refinement by entailment
summary: refinements_match decides entailment over the closed predicate vocabulary, boundary-only, through an engine shared with the deploy gate

**Context.** Spec §6.5 said a more restrictive sending side is admitted into a more permissive receiving one, but `refinements_match` implemented that only for an unrefined receiver and otherwise required equal canonical predicate sets. The deploy-gate classifier (`contract_compat`) already reasoned by entailment, so the compiler rejected a program the gate called compatible. The cross-context contract hash covers the callee's own contract, not the caller's argument type, so relaxing the matcher cannot cause a runtime 409.

**Decision.** (A) Go: `refinements_match` becomes entailment, with equal sets and refined-to-unrefined as degenerate cases. (B) Boundary only: inside a context named types stay nominal, because implication there is subtyping and would need a type table in `compatible`, a changed `join_ty`, variance rules per wrapper, and emitted brand casts. (C) Decidable pairs are interval containment for `Int`/`Float`/`Decimal` sign and `InRange` predicates and for the string length family; `Matches` is entailed only by an identical pattern; `Decimal` gains the missing arm, compared by value. (D) The engine moves out of `contract_compat.rs` into `entailment.rs`, called by both consumers. (E) Refined named peers are not name-gated at the boundary: they never were (the `Refined`/`Refined` arm of `structural_compare_named` has no name test, unlike `Opaque`), and name-gating would break documented §6.5 behaviour. (F) There is no anonymous refined type; an inline record-field refinement is not compared by the matcher.

**Consequences.** Programs that failed with `bynk.boundary.structural_mismatch` because the sender was strictly stronger now compile; no program that compiled stops compiling. The table is part of the documented static semantics, so a pair it admits cannot be rejected later without a 2.0 event. The engine is sound but incomplete (an `Int` is modelled as unbounded). Generic unification still demands exact agreement. Where two consumed contexts declare one type name, `projected_types` decides whether they "agree" by comparing both ways; with entailment that now means equivalent conjunctions, so `Positive` and `Positive && NonNegative` agree where they were previously ambiguous. The first declaration is projected, which is sound because the two admit the same values.

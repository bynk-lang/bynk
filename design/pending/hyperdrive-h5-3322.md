## ADR: hyperdrive-h5-mysql-instance-kind
title: Hyperdrive H5 adds a `MySql` instance kind over mysql2, with its own value and error types and a closed `@tls` set
summary: `MySql` mirrors `Postgres` (same operations, rows, transactions, deploy path) with `?` placeholders, separate `MySqlValue`/`MySqlError` types, mysql2 with `disableEval`, and `@tls` carried to deploy as the config's `sslmode`

**Context.** The Hyperdrive series (H0 to H4) gave a Bynk service a route to an existing Postgres database. H0 fixed that there are two kinds, `Postgres` and `MySql`, both with binding prefix `HYPERDRIVE_`, because the placeholder style, the value set and the error codes differ. This is the last slice, proposal #3322 (part of #3184), decisions A and B accepted as recommended. It mirrors H1 to H4 and changes only what MySQL makes different.

**Decision.**

- **The kind.** `capability Legacy = MySql` is an instance-only, experimental kind of `bynk.cloudflare`, binding as `HYPERDRIVE_LEGACY`, a `[[hyperdrive]]` entry the deploy fills in. Its operations are `Postgres`'s: `all`, `first`, `run`, `transaction`, and the compiler-lowered `select[T]` and `firstAs[T]`. The SQL is a literal; its placeholders are `?`. `MySql` and `Postgres` share the binding prefix, and `HYPERDRIVE_X` cannot name both, since an instance name is unique in a Worker.

- **A. Separate types.** `MySqlValue` and `MySqlError` are not `PgValue` and `PgError`: sharing one type would blur both. Every variant is prefixed (`MySqlNull`, `MySqlText`, …) so nothing collides with `Pg*` or `Sql*`. What MySQL makes deliberate:
  - *Unsigned integers.* An `Int` is signed, so `MySqlInteger(Int)` binds a signed value and `MySqlUnsigned(String)` binds an unsigned one as its digits; the server refuses anything else. A `BIGINT` (signed or unsigned) arrives as text, as Postgres' `int8` does, and an `Int` field reads it while it fits.
  - *`DATETIME` has no time zone.* It is not an instant, so `MySqlDateTime(String)` binds wall-clock text, and the type that binds an `Instant` is a separate one, `MySqlTimestamp(Instant)`, which writes UTC text. It is right for a `DATETIME` that holds UTC by convention and for a `TIMESTAMP` only when the session zone is UTC: MySQL converts a `TIMESTAMP` through the session zone, which Hyperdrive's pooling does not let a Worker pin. On the way back every `DATETIME`, `TIMESTAMP` and `DATE` arrives as the server's text, with no zone put on it, so an `Instant` row field is refused at compile time (`bynk.types.sql_row_shape`) rather than invented. Postgres reads a `timestamptz` as an instant because the column has a zone; MySQL's has not.
  - *`TINYINT(1)` is a flag.* `MySqlBoolean` binds `1` or `0`, and a `TINYINT(1)` column arrives as `true` or `false` (through the driver's `typeCast`, on the column's type and display width), as a Postgres `boolean` does. Any other `TINYINT` is a number.
  - `DECIMAL` and `JSON` bind as `MySqlDecimal` and `MySqlJson` text; a `DECIMAL` arrives as text and a `JSON` column nested; a `BLOB` as base64.
  - *`insertId`.* MySQL has no `RETURNING`, so `MySqlRun` carries `insertId` (the `AUTO_INCREMENT` id, `0` when none or past 2^53) beside `rowCount`.

  `MySqlError` is keyed on MySQL error numbers: `MySqlConstraint(code, message)` for 1062, 1048, 1452, 1451 and 3819 (a check); `MySqlSerialization(code, message)` for 1213 (deadlock) and 1205 (lock wait timeout), which a retry may clear; `MySqlConnection(message)` for connection codes (`ECONNREFUSED`, `PROTOCOL_CONNECTION_LOST`, …), the client library's 2002 to 2013 and the Hyperdrive proxy's code-less socket failures; and `MySqlFailed(code, message)` for everything else. The proposal wrote `MySqlFailed(message)`; it also carries the error number (`0` when the driver gave none), because that is what a handler matches on and the other three variants carry it. The error is extensible, so a `match` needs a wildcard. A message never carries the connection string, the host, the user or the password: a connection failure's message is a fixed string plus the driver's code, and every message has the password removed as a second line.

- **Driver: mysql2 3.24.6, with `disableEval: true`.** Pinned exactly through the first-party npm mechanism, with a `Reach::CapabilityInstance("MySql")`, so only a Worker with a `MySql` instance carries it. Cloudflare's mysql2 guide (read 12 November 2026) asks for mysql2 3.13.0 or later and `disableEval: true` ("required to enable mysql2 compatibility for Workers"), builds the connection from `env.<binding>.host`, `user`, `password`, `database` and `port` (not a connection string), needs `nodejs_compat` (on by default from the compatibility date the toolchain emits), and opens a connection per request, leaving the pooling to Hyperdrive. The binding does the same, falling back to the binding's `connectionString` only when the parts are absent. 3.24.6 was the newest release that was more than a month old. The runtime's `mysql.ts` owns, and tests against a fake driver, that every connection has `disableEval`, and that multiple statements are off.

  *`query`, not `execute`.* The runtime uses mysql2's `query`, which substitutes each `?` outside a string literal, a quoted name or a comment with an escaped value in the client, over `execute`, which prepares a statement on the server. Hyperdrive runs in transaction pooling mode, so a prepared statement may be sent to a connection that never prepared it; Cloudflare's guide uses only `query`; and mysql2 cannot bind `LIMIT ?, ?` through `execute`. The cost is that a value is sent as an escaped literal rather than out of band. mysql2 3.24's escaper skips single-quoted strings, backtick names and `-- ` and `/* */` comments, so the compiler's placeholder count and the driver's agree there (and the count follows the driver where it differs, below), and the SQL stays a literal, so no data is ever part of the text. `??` (mysql2's identifier placeholder) is not supported.

- **B. TLS: `@tls("…")` from a closed set, carried to deploy.** `required` (the default), `verify-ca` and `verify-identity`; anything else is `bynk.capability.invalid_option`, whose explanation now lists `@tls`. Cloudflare sets TLS on the Hyperdrive **config**, not in the Worker: the config's `sslmode` is `REQUIRED`, `VERIFY_CA` or `VERIFY_IDENTITY` for a MySQL origin (`DISABLED` and `PREFERRED` are not supported), and the verify modes need a CA certificate uploaded to the account. So the annotation has no effect in the Worker and is a deploy-time fact. `wrangler.toml`'s `[[hyperdrive]]` stanza has nowhere to carry it (or to say the config is MySQL's, which the Cloudflare API needs as the origin `scheme`), so the build writes a small `bynk-hyperdrive.json` beside it, only for a Worker with a `MySql` instance (a Postgres-only project's output is unchanged), holding binding names, a kind and a mode, never a connection string. `bynk deploy` reads it. For `required` it makes the config with scheme `mysql` and `sslmode: REQUIRED`. For a verify mode it **does not make a config**: it cannot upload a CA certificate, so it stops before the plan and names the `wrangler cert upload` and `wrangler hyperdrive create … --ca-certificate-id … --sslmode …` commands, then to adopt the config with `config_id`, which the deploy already supports and which ignores the annotation. Uploading a CA from `bynk.toml` is a later option.

- **Deploy and dev reuse H2's path.** There is no second path: the same `[deploy.hyperdrive.<Capability>]` and `[dev.hyperdrive.<Capability>]` tables, ledger rows, plan lines and secret handling. The connection string is a `mysql://` URL (port defaulting to 3306); a `postgres://` string for a `MySql` instance is refused naming the scheme it wants, without being printed. The connection string stays a secret everywhere: tests hold it out of the ledger, the generated files, the plan (both formats), `Debug` output and every message.

- **The statement check reuses H4's.** With a `schema.sql` at the root, each literal `MySql` statement is parsed with `sqlparser`'s `MySqlDialect` (`bynk.mysql.sql_invalid`, a warning, for the reason H4 gives: the parser is not MySQL's, and MariaDB has forms of its own) and its `?` placeholders are counted (`bynk.mysql.sql_param_count`, an error), outside single-quoted strings (with backslash and doubled-quote escapes), backtick names and comments (`-- ` and `/* */`). The count follows what mysql2's escaper does, not MySQL's lexer: measured against `sql-escaper` 1.5.2, it substitutes a `?` inside a double-quoted string and after `#`, so those are counted, and a string literal is written with single quotes. A fixture with `ON DUPLICATE KEY UPDATE`, backtick names, `LIMIT ?, ?` and `INSERT IGNORE` produces nothing. Each code has an explanation.

- **Tests.** Stub-only. A test never reaches a database, so every operation faults until stubbed, and `expect … called with` works at the unit tier as for any capability. A PGlite-equivalent for MySQL is out of scope.

**Consequences.** A Bynk service can reach an existing MySQL or MariaDB database by the same surface and deploy path as Postgres, at the price of a second value type. The one decision that is MySQL's to make about time (no `Instant` from a `DATETIME`) means a handler reads those columns as text. A verify-mode TLS needs the config made by hand and adopted until deploy can upload a CA. Whether the emitted driver runs under `workerd` against a real MySQL is checked by the smoke where the environment can run one, and otherwise by the runtime's fake-driver tests and the binding tests.

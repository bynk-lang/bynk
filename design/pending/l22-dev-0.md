## ADR: event-delivery-queue-per-subscriber
title: Events are delivered through one compiler-owned Cloudflare Queue, with its own dead-letter queue, per subscribing service, on every Cloudflare plan
summary: The durable event substrate: a queue and a dead-letter queue per `from Events` service, replacing the fan-out Durable Object; one mechanism on every plan, the Free plan's cap accepted

**Context.** On Workers an emission travels from the handler's `__events` buffer to one fan-out Durable Object per publishing context, which delivers one signed HTTP request per subscriber over a Service Binding ([ADR 0284](0284-events-fanout-substrate.md)). The durable event delivery track (`design/tracks/durable-event-delivery.md` §1, spine #3898) traces eight defects to that shape: a failed hand-off and a failed subscriber are both logged and dropped (P1, P2), the DO stores nothing (P3), the publisher waits for every subscriber in turn (P4), every emission of a context goes through one instance (P5), every subscriber is invoked whether its pattern matches or not (P6), a subscriber that calls its publisher closes a binding cycle that cannot deploy (P7), and delivery answers on a public route (P8). ADR 0284 rejected one queue per *event type*, because one acknowledgement per message would let one subscriber's retry redeliver to siblings that had already acknowledged.

**Decision A — the substrate.** Each subscribing service (`service … from Events(E)`) gets one compiler-owned Cloudflare Queue and one compiler-owned dead-letter queue. The publisher sends one message per emission to the queue of each subscriber whose pattern and schema range match; each subscriber's Worker consumes its own queue through the generated `queue` entry, with retries, the dead-letter queue and attempt counts. Because each message has exactly one consumer, its acknowledgement belongs to that consumer, which removes ADR 0284's objection. No author declares an event queue. This supersedes ADR 0284's substrate decision.

**Decision B — no publisher→subscriber bindings.** The publisher holds a queue producer binding per subscriber queue, and no Service Binding to any subscriber, so a subscriber that also calls its publisher deploys in dependency order. This supersedes [ADR 0475](0475-service-binding-only-when-called.md) D2 and D3 for events: event delivery no longer needs the two-phase upload, and `bynk deploy`'s event-delivery cycle refusal goes with the fan-out (the cut-over slice).

**Decision C — one mechanism on every plan (D13, maintainer ruling of 26 November 2026, option A).** Events use the queue substrate on every Cloudflare plan, with no Free-plan fallback and no per-project substrate switch. On Workers Free the Queues allowance (10,000 operations a day, 3 per delivery) caps a project at about 3,300 deliveries a day, with D1's 100,000 rows written a day behind it. That cap is accepted and documented: `bynk doctor` and the deploy plan state it for a project with subscribers, and the events guide says production event workloads need Workers Paid. Past the cap a service faults, an agent's outbox defers to 00:00 UTC, and deduplication fails closed (track D9). Until live check L11 settles how a 24-hour-retention queue treats a delayed message, the three surfaces also carry the Free-plan loss warning.

**Rejected.** Keeping the fan-out DO and making it durable (it keeps P5 and P7 and rebuilds retries, dead-lettering and concurrency that Queues provide). One queue per subscribing context (Cloudflare's consumer settings are per queue, so per-service delivery settings would be impossible, and one slow subscriber would delay its siblings). One queue per event type (ADR 0284's reason). Cloudflare K2 (in beta, Paid only, batch acknowledgement and no dead-letter queue; the leading candidate for a later replay log). A Workflow per emission (more than delivery needs, priced per instance). A Free-plan fallback to in-request delivery (a second mechanism with a weaker guarantee, the shape this track removes). A per-project substrate switch is not taken now; it stays open as an additive 1.x option.

**Consequences.** Two queues per subscribing service per environment count against the account's 10,000 queues; the deploy plan warns at 90%. Each delivery costs three queue operations and about three D1 rows written for its claim (track D9's worked example: about $2.00 a month for a million emissions to two subscribers on Workers Paid). The cut-over is breaking at runtime and source-compatible, and lands before 1.0. The slices of the track's §10 build it: reserved names (2), the subscriber's queue entry and provisioning (3), the cut-over (4), the agent outbox (5), filtering at the publisher (6), delivery settings and `bundle` (7), and the legacy route's removal (8).

## ADR: event-delivery-at-least-once-from-commit
title: An event committed by an agent, or emitted by a service handler that completes, is delivered at least once; agents release through an outbox in the commit, services send before returning or fault
summary: The delivery guarantee as the track words it, and how release at commit is kept: an outbox written in the agent's storage transaction, and send-or-fault for services

**Context.** Today delivery is at most once on Workers (track §1, P1–P3), and the docs say so (#3897). [ADR 0109](0109-handler-atomic-commit.md) D1 makes events release at commit: a fault before the commit persists nothing and releases nothing. Moving to a queue must keep that property while closing the gaps between commit and hand-off. An agent has a transactional store; a service has none (track §4, D1).

**Decision A — the guarantee.** *An emission committed by an agent handler is delivered at least once to every subscriber whose pattern and schema range match it. An emission from a service handler that completes successfully is delivered at least once in the same way, and a service handler that cannot hand its emissions off faults instead of completing.* "Delivered" means the subscriber's handler runs to completion on it once, or the event reaches that subscriber's dead-letter queue after `retries` + 1 failed attempts. Duplicates are possible on the wire and are normally absorbed by built-in deduplication (the queue-protection ADR of this slice). It is not exactly-once side effects, not ordered (the ordering ADR of this slice), not across a caller's retry of a service (which mints new `eventId`s), and not durable on `bundle`.

**Decision B — agents: an outbox in the commit.** `commitStored` writes one outbox row per emission under the reserved key prefix `o/<seq>` in the same storage transaction as the state record, and sets the Durable Object alarm about 30 seconds ahead when it writes rows and none is set. After the commit the agent replies, then flushes in the background: each row goes to every queue in the running build's routing table that is not in its `sent` list, then is deleted. At most one flush runs per instance; a row's `sent` update and delete are conditional on the row still existing, so a second flush can resend but never bring a deleted row back. A flush that empties the outbox deletes the alarm; the alarm handler runs the same flush, catches its own failure and reschedules rather than throwing (backoff from 30 seconds to 1 hour). Erasure with pending rows is two-phase: a logical erase (the reserved marker key `e`, read by `loadState` as zero state) committed with the rows and the alarm, then `deleteAll()` once the last row is sent, because `deleteAll()` cannot run in a transaction and, on the compatibility date Bynk emits, also deletes the alarm. With nothing to deliver, `self.erase()` stays a single `deleteAll()`. The reply waits only for the commit's write, never for a send.

**Decision C — services: send before returning, or fault.** `Events.emit` in a service only appends to the handler's buffer. After the body returns without a fault, the wrapper sends the buffer to every matching subscriber queue, all queues concurrently, in `sendBatch` calls within Cloudflare's limits. A failed send is retried twice (after 100 ms and 400 ms); if it still fails the handler faults with `EventSendFailed`, naming the event type and the queue. A body that faults sends nothing. So a service handler that completes has sent every emission; one that faults may have performed any of its other effects and sent any subset of its emissions, as any service handler that faults after a side effect does today. The guide points authors who need effects and events to be atomic to an agent.

**Decision D — the size budget.** A queue message is at most 128 KB. `Events.emit` measures the message it will send (the signed wrapper with a placeholder signature of the real length) and, over 127,000 bytes, faults with `EventTooLarge` before the commit, on every target, so nothing is persisted and nothing is lost. This lowers today's 1 MiB cap and is breaking; the release before the cut-over only warns (`EventNearLimit`, from 96,000 bytes), and `bynk.event.unbounded_payload` warns at compile time on an `event` whose payload is plainly unbounded (track §8.1). The trace travels in the signed envelope.

**Rejected.** A per-context outbox DO for services (the hop to it fails as a queue send can, and it brings back P5). At-most-once for services (two guarantees on one surface). An outbox flushed only by the alarm (adds the alarm's delay to every emission). Sending before commit, or at each `Events.emit` call in a service (both break release at commit). Splitting or spilling large events to R2 or KV (a second store and lifecycle for a case no user has asked for). Faulting on size at send time (for an agent that is after the commit, so the event would be lost silently).

**Consequences.** Release at commit keeps its ADR 0109 meaning on every target; on Workers, release is the outbox write for agents and the completed send for services. The publisher waits for the hand-off only, never for a subscriber. An emitting agent commit costs one more `put` per emission, a delete after the flush, and a `setAlarm` and `deleteAlarm` (track D9). The cut-over slice ships services' send-or-fault and agents' send after commit (still at most once for agents, and documented so); the outbox slice makes the guarantee hold end to end for agents, and no release documents a guarantee it does not give.

## ADR: event-ordering-best-effort
title: Event delivery order is best effort, and every event is its own queue message
summary: Withdraws both per-publisher ordering guarantees ADR 0290 measured; a subscriber that needs order carries its own sequence

**Context.** [ADR 0290](0290-events-per-publisher-fifo-scope.md) measured two partial guarantees of the fan-out DO: (a) the emissions of one handler arrive in emission order, and (b) successive, non-overlapping calls to one agent arrive in order. Both held only because one DO looped sequentially. Cloudflare Queues promises no order, not even within one `sendBatch` to one queue (track §3). Keeping (a) and (b) on queues would mean serialising delivery (consumer `concurrency: 1` plus a reorder buffer), which costs throughput and brings the bottleneck back. Withdrawing behaviour that is documented and measured went to a ruling (track D4).

**Decision (maintainer ruling of 26 November 2026, option (ii)).** Ordering is best effort. Both ADR 0290 guarantees are withdrawn. Each event is one queue message with its own acknowledgement, retry and dead-letter fate. The guide keeps its existing advice: a subscriber that needs a total order across publishes carries its own sequence number in the event payload. This amends ADR 0290; the design notes' cross-agent *per-sender FIFO* (calls, not events) is unaffected.

**Rejected.** (i) Keeping guarantee (a) by sending one handler's emissions to a subscriber as one array message. A failure of one event would retry all of them, and deduplication claims the message's id, so skipping the events that completed would need a second, per-event claim design with its own lease and settle rules; it also couples the events' fates and applies the size limit to their sum.

**Consequences.** The pages that promise the old order are amended by the slices that the track's §13 assigns: the concepts page's Workers row (the cut-over slice) and `design/bynk-design-notes.md` §7 and its open-questions summary (this slice). The ordering measurement, `bynk-tests/tests/system/events_ordering_workerd.rs`, is retired with the fan-out it measures in the cut-over slice. Room is left for opt-in ordering later (#3545 part 3): an optional `sequence` in the envelope, sourced from the agent outbox's per-instance `<seq>`, and a per-key reorder step declared on the subscription.

## ADR: event-queues-reserved-signed-deduplicated
title: Event queues have reserved names, carry #3899 signed queue messages that only the event's owner can sign, and deduplicate every `eventId` per subscriber
summary: How the compiler-owned queues are protected: the `bynk-ev-`/`bynk-dl-` reservation, the v1 signed format with the subscriber queue's name, owner-only verification with the `publisherId` and type check, and the always-on claim

**Context.** Any Worker on the account with a producer binding, a Cloudflare event subscription and the dashboard can write to a queue, and account members can read and delete its messages (track §6). Owner-only emission ([ADR 0289](0289-events-owner-only-emission-check.md)) and a proven `publisherId` ([ADR 0485](0485-per-edge-call-signature.md)) must survive the change of substrate. #3899 already shipped a signed queue message format, one verification path (`queueAdmit`) and per-consumer replay deduplication in the `Idempotency` D1 store (track D2, D11).

**Decision A — reserved names.** A subscribing service's queue is `bynk-ev-<slug>-<hash>` and its dead-letter queue `bynk-dl-<slug>-<hash>`: `<hash>` is the first 8 hex digits of SHA-256 over `<qualified context>/<service>`, and `<slug>` is that pair lower-cased with every character outside `[a-z0-9]` written `-`, truncated so the name plus `env_qualify`'s `-<environment>` fits Cloudflare's 63 characters. The names are collision-checked, not injective: the compiler refuses two subscribing services whose queue names coincide (`bynk.event.queue_name_collision`). The functions live beside `env_qualify` in `bynk-project`, so the plan and the emitted config agree by construction. User code may not name a queue that starts with `bynk-ev-` or `bynk-dl-` in a `Queue @name("…")`, a `from queue("…")` consumer or a `deadLetter: "…"` (`bynk.queue.reserved_name`, an error). Only those two prefixes are reserved, not `bynk-` as a whole.

**Decision B — the #3899 format, unchanged.** An event message is a version-1 signed queue message: `bynk.from` is the publishing context's qualified name, `bynk.id` the emission's `eventId`, `bynk.ts` the signing time at the flush, and `bynk.sig` an HMAC-SHA256 under ADR 0485's publisher→subscriber edge key over `bynk-queue-v1`, `from`, `id`, `ts`, the **subscriber queue's deployed name** and the canonical body. The body is `{ "type", "payload", "envelope" }`. Signing over the source queue's name means a message moved to another subscriber's queue does not verify, and a dead-lettered one still verifies against its source. Edge keys are per environment, so a staging message does not verify in production. A rotated key keeps verifying for the 15-day window ([ADR 1096](1096-edge-keys-rotate-through-two-slots.md), #4526), which is a prerequisite for events using edge keys on queues.

**Decision C — verification before decoding.** The subscriber's `queue` entry calls `queueAdmit` directly, with the subscribing service's qualified name as `consumer` and ports built as `admitQueueBody` builds them, and an `admitsContext` that admits exactly one context: the owner of `E`, known at compile time. Then `body.envelope.publisherId` must equal the verified `from`, and `body.type` the subscribed event. An unsigned, malformed, other-version, non-owner or badly signed message is acknowledged, reported and counted, and never handled, retried or dead-lettered. A verified message whose `publisherId` or `type` disagrees with its signer is a compiler or deploy bug: it is dead-lettered and reported, and its claim is released. So ADR 0289 and ADR 0485 hold at the subscriber by signature, not only by the compiler's check on the emitter.

**Decision D — deduplication is built in and always on (#3545 part 2).** Every Workers delivery claims `queueReplayKey("<subscriber context>.<service>", <queue>, <eventId>)` through `queueAdmit`'s existing protocol: claimed only after the signature verifies, so unsigned traffic cannot fill the store; a 15-minute lease over the handler's run; confirmed when the handler completes or the guard excludes the event; released when the handler faults or the message is dead-lettered as undecodable, so a retry or a redrive is admitted once. A redelivery that meets a running lease is retried after it, not acknowledged. Claims are kept for `QUEUE_DEDUP_WINDOW_SECONDS` (15 days: 14 of retention plus 1 of delay), and a message signed longer ago is refused as `stale`, so a lapsed claim never admits a replay. A claim that fails (including on D1's daily limit) never admits unchecked: the message is retried, and on the daily limit retried with a delay to 00:00 UTC. Every subscriber Worker gets `D1_IDEMPOTENCY`. `Idempotency.claim(env.eventId, …)` in author code stays legal and correct but is redundant for redelivery; `claim` remains the tool for business keys.

**Rejected.** A separate event-message format (two signing inputs and two verifiers for one problem). Trusting the queue boundary without a signature (anyone with account access can write to a queue). A timestamp window as the replay defence, as `/_bynk/event/` uses (messages legitimately wait for days). Opt-in deduplication, as #3545's text proposed (D2's replay defence needs the claim unconditionally). Degrading to unchecked admission when the claim store fails or is over its limit (a replay and a redelivery look identical at the entry). A user-declared `deadLetter` on an events service (it would reopen the reserved-name boundary; refused as `bynk.event.delivery_dead_letter`).

**Consequences.** No new secret kind is introduced; the claims table holds keys and expiry times, never payloads. Confidentiality and availability against account members are out of scope and stated in the guide: events must not carry secrets, and a subscriber's `concurrency` and the per-queue throughput limit bound a flood, which the refusal counts make visible. A change to the shared signing or verification is one change, reviewed once, under `/security-review` on every slice that touches it ([ADR 0076](0076-feature-track-posture.md)). Each delivery costs about 3 D1 rows written, up to 5 with the key's index.

## ADR: event-outbox-row-format-versioned
title: An agent's event outbox row carries a format version and is part of the 1.0 stored-data promise
summary: `o/<seq>` rows are `{ "v": 1, "type", "payload", "envelope", "sent" }`; a 1.x runtime flushes every earlier row version, beside ADR 0538's stored-state contract

**Context.** The agent outbox (the at-least-once ADR of this slice) writes rows into the agent's Durable Object storage, where they can outlive the build that wrote them: a crash, a failed flush, or the Queues daily cap can leave rows pending across a redeploy for hours or longer. [ADR 0538](0538-stored-state-version-marker-and-frozen-encoding.md) made the encoding of stored agent state part of the 1.0 data-compatibility promise. Outbox rows are stored data of the same kind and need the same promise, fixed before the first row is written (track §10 slice 0 (e)).

**Decision.**

1. *Place.* A row is stored under the reserved key `o/<seq>`, where `<seq>` is a per-instance sequence assigned at commit; the erasure marker is the reserved key `e`. Both are outside every prefix the runtime already uses (`m/`, `s/`, `l/`, `i/`, `x/`, `c/` and `"state"`).
2. *Shape.* A row is `{ "v": 1, "type": <event>, "payload": <encoded payload>, "envelope": <envelope>, "sent": [<queue>, …] }`: the emission as committed, plus the subscriber queues it has already reached. The targets are computed at flush time from the running build's routing table, so a row written before a redeploy goes to the subscribers the running build knows.
3. *Versioned and frozen within 1.x.* `v` is mandatory. A 1.x runtime flushes every row version any earlier 1.x runtime wrote. A change to the row's shape bumps `v` and carries the reader for each earlier version through 1.x; dropping a reader is a 2.0 event. A row whose `v` is above the running runtime's is not flushed or rewritten (a rolled-back deploy): it stays stored, is logged, and is flushed once a runtime that knows the version runs, as ADR 0538's `NewerSchema` rule refuses to decode a newer state record.
4. *Operations honour it.* `bynk migrate sweep` and agent moves (#3819) preserve or flush pending rows before they touch storage, and honour `e`.

**Rejected.** An unversioned row (the first shape change would leave pending rows unreadable after an upgrade). Draining the outbox as part of each deploy instead (a deploy cannot reach every instance, and the Free-plan cap can hold rows past any deploy).

**Consequences.** The outbox slice builds against a fixed place, shape and compatibility rule, and its runtime tests include a row written by an older runtime version. `design/bynk-1.0-definition.md`'s stored-data carve-out covers outbox rows beside agent state when that slice lands.

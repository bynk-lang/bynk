## ADR: collection-field-rename
title: A renamed Map or Set is moved key by key, in resumable batches, before anything reads it
summary: `replaces` on a `Map` or `Set` store field moves its per-entry storage keys to the new name on the first load, in bounded transactional batches, instead of reading an old key
**Context.** #4482, from #3793. `replaces` renamed a `Cell` by reading its old key. A `Map` or `Set` keeps each entry, and its metadata, under a storage key that carries the field's name (`m/<field>/<k>`, `s/…`, `c/<field>`), so a rename moves keys, and reading an old one is not enough. The refusal was `bynk.store.replaces_collection`.

**Decision.** The checker allows the clause on a `Cell`, a `Set` and a `Map` without `@indexed` or `@unique` (both keep postings under the field's name); a `Cache`, a `Log` and an indexed `Map` are still `bynk.store.replaces_collection` (the second part of #4482). The lock records the rename as for a `Cell`. The emitted `loadState` calls `__moveRenamedEntries(this, storage, stored, steps, [{ kind, from, to }, …])` before `__readStored`, one entry per renamed `Map` or `Set` the lock's reads name. The runtime moves the entries in batches of up to 128 keys (Cloudflare's limit on a batched write): list the old prefix with a limit, read which of the new keys already exist, and in one `storage.transaction` write the entries that are not already there and delete every old key. An entry already under the new name wins. So an entry is always under exactly one name, and a crash between batches leaves a state the next load simply continues from; there is no single transaction over a collection, which one could not carry. The field's metadata (`c/`, the entry count and next insertion sequence) moves after the last batch. When both names hold metadata (a rolled-back deploy wrote under the old name again), the counts are merged, and the moved entries take insertion sequences after the new field's so none collides. No "done" marker is kept: a marker would strand the entries a rolled-back deploy wrote under the old name, so the check repeats instead. It is memoised per agent instance in the isolate (a weak map keyed by the instance, not by request), so a hot object pays it once per wake, not on every call: two metadata reads and one bounded `list` per renamed field, whatever the collection's size, and the move itself only when entries are found under the old name. A record a `migrate from` step covers, and a record in the wholesale layout, is not moved before the load: the step reads the record as the stored version shaped it, under the old name, and the commit that follows writes the entries under the new name and deletes the old keys. A load runs one handler at a time (#3202) and the move uses only storage operations, so no handler sees a half-moved field. The first load after the deploy does the whole move, and its cost grows with the collection. That is stated in the guide, the spec and the agents reference.

**Consequences.** A `Map` or `Set` can be renamed with `replaces`, with no `migrate from`, on workerd with a collection larger than a batch. The runtime gains `moveRenamedEntries`. A `Cache`'s expiry keys, a `Log`'s keys and an indexed `Map`'s postings are the second part. The lock keeps its existing history for the field, so `bynk.field.replaces_needed` and `replaces_settled` apply as for a `Cell`.

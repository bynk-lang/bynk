## ADR: sequence-diagram-state-writes-are-notes
title: An agent handler's state writes are notes on the entry lifeline, not a store lifeline
summary: `:=` and mutating store ops in an agent handler render as `StateWrite` notes; the store is not an ADR 0258 boundary

**Context.** The sequence diagram (ADRs 0258–0275) classifies a handler's calls into lifelines at runtime boundaries: a consumed capability, a consumed context, an agent. In an agent's own `on call` handler that left the one thing the handler is for invisible: `walk_block` walked a `Statement::Assign`'s right-hand side and emitted nothing for the write, and a store operation (`items.put(…)`, `count.update(…)`) classified as local computation, so `Order.place()` drew an `alt Pending / Placed / Cancelled` box with no `Pending → Placed` in it (#2194, slice 0 of the agent-state-views track, #2190).

**Decision.** In an agent handler, each `:=` and each mutating store operation on one of the agent's own fields is a `MessageKind::StateWrite` with `from == to ==` the entry participant, carrying the write's span and its branch, so it sits in source order among the handler's calls. The client renders it as a `note over` the entry lifeline and links it to the write. It is **not** a lifeline: the agent's store is its own storage (the Durable Object's), not a separately addressed runtime participant, so ADR 0258's classifier is unchanged. A store operation is recognised syntactically — a bare-name receiver that is one of the agent's `store` fields, not shadowed by a parameter, `let` or match binding in scope, calling an op the store-op registry marks as mutating for that field's kind — because the checker's resolved `Callee` table is not retained for the IDE (agent-state-views §3.3). The registry (`bynk_check::store_ops`) gains a `mutates` flag per operation, now the single source for both this recogniser and `bynk_lower::body_writes_state`'s commit detection, whose private name lists it replaces. Labels show `field := <value>` and `field.op(<first arg if simple>, …)`, each value truncated to 32 characters. Service handlers emit no state writes.

**Consequences.** An agent handler's diagram shows what it writes, where, and in which branch, and a click lands on the write — whether the write is awaited (`let _ <- items.put(…)`) or is a branch's tail (`Ok(a) => items.put(a, n)`), where it is the note and not also a reply. A write inside a lambda (`orders.forEach((o) => …)`) is not shown: like every other call in an argument expression, it is outside the diagram's statement-level scope (ADR 0259). The wire gains one message kind (`"StateWrite"`); clients that switch on kinds must handle it. The client's note click-map now carries each note's own range rather than only its block. The recogniser is shared with the agent-state-views state model (slices 1 and 4), so the two views agree on what a write is.

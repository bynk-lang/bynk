## ADR: ordering-and-comparators
title: `Ordering`, a universal `compare` and `sortWith`
summary: `a.compare(b)` answers an `Ordering` on every `Ord` type, `then` and `reverse` combine them, `List.sortWith` sorts by a comparator that returns one, and `Ordering`'s variants resolve only from context

**Context.** `sortBy` orders by one key in declaration order, `Bytes.compare` returned a bare `Int`, and a multi-key or mixed-direction order had no spelling. #3955 asks for the order a type already has (its `Ord`) to be readable as a value, and for a sort that takes a comparator.

**Decision.** `Ordering` is the enum `Less | Equal | Greater`, with `derives Ord` (`Less < Equal < Greater`), `then(next)` (`next` when `Equal`, otherwise the receiver; `next` is a value, not a lambda) and `reverse()`. `a.compare(b)` is a compiler-known method on every `Ord` receiver, lowered to the type's own comparator (the one `<`, `sortBy` and a `T: Ord` witness use) read as an `Ordering`; a receiver that is not `Ord` is `bynk.types.not_orderable`, and a type that declares its own `compare` method keeps it. `Bytes.compare` is that method, so it now answers an `Ordering`. `List.sortWith(cmp)` is a stable sort by a `(T, T) -> Ordering` function.

`Ordering` is the commons `bynk.ordering`, first-party and stable. A unit that mentions `.compare`, `.sortWith` or `Ordering` has it in scope as if it had written `uses bynk.ordering`: the compiler adds that `uses` to the parsed unit, so name resolution, `uses` composition, emission and shadowing by a declaration of the unit's own behave as for a written one, and a unit that mentions none of them is unchanged. This deviates from the issue's wording (an export of the `bynk` adapter): a std type reaches a unit only through an explicit `consumes` and a commons cannot consume an adapter, so `Ordering` would not have been nameable from a commons; #4231 replaces the injection with a general prelude-type hook.

The variants resolve **from context only**. A bare `Less`/`Equal`/`Greater` is an `Ordering` when an expected type names it, when it is the other operand of `==`, `!=` or an ordering operator (#3987), or when it is matched; it never competes with a sum of the author's own that shares the name, so such a type is unaffected and a bare name with no context stays that type's variant. `Ordering.Less` always works. Mechanically, `Ordering` is dropped from a bare variant's owners when another sum in scope declares the name, and an expected type or comparison operand that names it picks it back (the path #3536 added for a sum a braced `consumes` leaves out).

**Consequences.** `Bytes.compare` loses its `Int` answer, so the one in-tree use changed; `-1`/`0`/`1` is `match`ed as `Less`/`Equal`/`Greater`. `compare` is not available to a single-file program (`bynk check page.bynk`), which has no other unit to reach. The runtime gains `__bynkOrdering` and `__bynkOrderingSign` beside the comparators. The per-type kernel method tables that drive completion and signature help are keyed by receiver type, and `compare` belongs to every `Ord` type, so it is in none of them: `compare` is no longer offered after a `Bytes` receiver's `.` and has no signature help. `sortWith` is in the `List` table, so it is offered and has signature help. Hover and semantic tokens read the checker's recorded callee and are unchanged.

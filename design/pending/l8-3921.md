## ADR: default-body-cap
title: Every body-taking HTTP route has a 1 MiB request-body cap by default
summary: A route that takes a body is capped at 1,048,576 bytes unless it or its service says otherwise, with no unlimited setting and a build hint for routes on the default

**Context.** Body limits were opt-in: a JSON or `@form` route with no `limits { }` read an arbitrarily large body into memory before it could reject it, in a Worker with 128 MB for everything. Only `@raw` and `@multipart` routes had to declare a cap. A cap the author forgets cannot be added in the handler, because the generated router reads the body before the handler exists.

**Decision.** (A) The effective cap is the route's `@limit(maxBody:)`, then the service's `limits { maxBody }`, then 1,048,576 bytes, for every HTTP route that takes a `body`. The number matches the cross-context call wire's own cap. (B) There is no "unlimited" setting. A larger cap is a number, at most 524,288,000 bytes, the request-body ceiling of the largest Cloudflare plan (Free and Pro accept 100 MB and Business 200 MB, so a value above the zone's plan limit is rejected by Cloudflare, not by Bynk); a literal above it is `bynk.http.limit_bad_max_body` or `bynk.http.limits_invalid_field`. The issue named no number, so the ceiling is recorded here. (C) A `@raw` route must still declare a cap (`bynk.http.raw_body_unbounded`), because a binary upload's size is a deliberate choice. The default now covers `@multipart` too, so `bynk.http.multipart_body_unbounded` could no longer fire and is retired. (D) The `413`'s `details` name the cap and say `@limit(maxBody: …)` raises it. One hint per service, `bynk.http.body_cap_defaulted`, lists the routes relying on the default. It is a hint, not a warning, because a warning on every service with a body-taking route would break every build that denies warnings and add one line to nearly every program; the hint shows in the editor and in the machine-readable diagnostics.

**Consequences.** A service that took bodies over 1 MiB without declaring a cap now answers `413` with instructions; the changelog and upgrading page list it as breaking. A counted read now runs on every body-taking route, which it already did on capped ones, at a cost proportional to the bytes read. Hover on a route's response list says a body-taking route answers `413` and what its cap is; the `@limit`, `@form` and `@multipart` hovers state the effective cap and where it comes from, including the default.

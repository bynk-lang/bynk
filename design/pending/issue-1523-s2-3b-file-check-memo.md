## ADR: file-check-memo
title: The language server replays an unchanged file's check instead of re-checking it

**Context.** #1523 asked whether editor latency needs an incremental scheduler (R3.15); #3243's settling review proposed a language-server-only memo table instead, accepted by the maintainer. Attribution showed the per-file check (`check_file_core`) was the largest remaining share of an edit. The memo's correctness bar is the differential oracle (`xtask/tests/analysis_oracle.rs`): a memoised round must answer exactly what a fresh `analyse_project` answers, over the examples and seeded random edit sequences on both bench shapes.

**Decision.** `bynk-lsp` keeps one `AnalysisMemo` per project and calls `analyse_project_memoised`. For each file it computes `check_pipeline::file_check_digest`; if the digest equals the one stored for that file, the stored `FileRecord` (the file's errors, reference edges, hints, locals, expression types, requirements and typed unit) is replayed into the project's sinks instead of checking the file. `bynk check`, `bynk build` and every other caller stay on `analyse_project`, which has no memo parameter; a test pins that.

*What the digest covers, and why.* It is a content hash of rendered `Debug` (spans and `FileId`s included), not a pointer: the parse cache hands out freshly built decls each round, so `Arc` identity does not survive. It is span-inclusive because a diagnostic's label can point into another file at an offset, and an upstream edit moves it. It hashes: (1) the file's identity path, absolute path, kind, synthetic flag and source text; (2) the unit name and kind; (3) the source text and path of every file of the unit (a label may point into a sibling), which also stands for the unit's own symbol table, since `phase_symbol_tables` builds it purely from those files; (4) the table's cross-unit facts (`UnitTable::cross_unit_facts`: kind, flattened capabilities, consumed type aliases, derived instances), the only parts `record_flattened_caps` and `phase_resolve_derived` fill in from other units; (5) the composed symbol space the check receives: `combined_types`, `combined_fns`, `combined_methods`, `local_names`, `local_methods_for_type`, `consumed_types`, `imported_from`; (6) what the check reads of `unit_info` beyond the own table: `flattened` and the outputs of `compose_unit_assets`, `compose_unit_embeds`, `compose_unit_consts` and `shadowed_imports`; (7) every field of `UnitCheckCtx`: the project's stability policy, `uses_commons_type_names`, `visible_broken_names`, `hidden_types`, `shadowed`, `private_imports`, `d1_sql` (a content hash of every migration file it was built from: the schemas come from files outside the `.bynk` text, and `D1Sql`'s `Debug` prints only the database names), and, for contexts and adapters, the two things `check_file_core` derives from the cross-context views, `build_cross_context_info(name, ..)` (rendered by `oracle::cross_context`, which sorts its maps of maps) and `combined_types_for(name, ..)`. Maps are hashed in key order (`flattened`, `shadowed` and the symbol maps included), because `HashMap` iteration order differs between instances and an unstable digest never hits; a test requires zero misses on a warm round over every example, and another that editing a D1 migration without touching any `.bynk` file changes the answer.

*Keeping it complete.* `file_check_digest` destructures `UnitCheckCtx` exhaustively and `UnitTable::cross_unit_facts` destructures `UnitTable` exhaustively, so a new field of either is a compile error until it is classified. `check_file_core`'s parameters are the same list as the digest function's. **A change to `check_file_core`'s inputs must update `file_check_digest`.** The oracle is the arbiter for anything the types cannot see.

*The type table.* A record holds `TyId`s, so all rounds of one memo share one append-only `Types` table. Interning deduplicates, so an unchanged project adds nothing, but an edit that mints new types leaves the old ones behind. Policy: after a round, the table's size is the baseline; once it exceeds four times the baseline (and 50,000 entries, so a small project never churns) the memo is dropped and the next round starts cold on a fresh table. That bounds the table to a constant multiple of one round's by construction; a test runs 60 random edits with the limits tightened and checks it stays bounded and that a reset changes no answer.

**Consequences.** *Latency*, `cargo xtask bench` medians of edit-to-diagnostics, same machine and session, memo off then on (signature edit; body-only edit): linked 50 contexts 43 to 39 ms (43 to 40); linked 200 contexts 198 to 164 ms (205 to 165); independent 200 contexts 95 to 84 ms (93 to 82). At linked 500 contexts the gain is 472 to 376 ms in one session and 541 to 464 ms in a noisier one. The linked shape's p95 at 200 contexts stays under the #1523 yardstick (250 ms). A body edit still re-checks every file whose digest includes the edited unit's declarations, so direct consumers of an edited context miss (narrowing that key to the unit's signature plus the body facts the check reads, the needs-context set #2719 and compared type parameters #1702, is the follow-up, together with computing a unit's shared digest inputs once per unit rather than once per file: the per-unit parts are re-rendered for each file of a multi-file unit, which the bench shapes, one file per context, do not show). *The first round* of a project is slower, by the digest and the retained copies, paid once (linked 200: about 240 to 310 ms for the cold first analysis).

*Memory, and what bounds it.* Server peak RSS (`lsp_peak_rss_mb`, memo off then on): linked 50 contexts 64 to 73 MB; 200 contexts 205 to 234 MB; 500 contexts 469 to 566 MB. That is linear in the number of files, about 0.15 to 0.19 MB per file (one file per context in the bench shapes), and a constant 4x factor on the type table. A file's record holds its errors, reference edges, hints, locals, expression types and requirements, and its typed unit (kept because `ExecPlan::extend` reads it every round); there is one record per file. Nothing outside the workspace's files is retained: after each round, records for files not seen in it (a deleted or renamed file) are dropped, a changed file's record replaces its old one rather than adding to it, and a project that is closed takes its memo with it. The one shared table that can outlive a round, the interned `Types`, is reset by the 4x policy above, which discards every record with it. So retained memory is bounded by the workspace's size times a constant, plus at most four times one round's type table.

No documented guarantee changes: `bynk check`, builds and emitted output are untouched, so this is `level: patch`.

## ADR: queue-producer-message-type
title: A producer's message type is checked against the queue's consumer when both are in the project
summary: A project phase pairs each `Queue` instance's `sendValue*` call sites with the `from queue` consumer of the same name and compares their types by the cross-context boundary comparison

**Context.** Both sides of a queue are often in one project and name the same string, yet `sendValue(x)` accepted any `Codable` `x`. A mismatch surfaced only at run time, as a message the consumer could not decode, which is dead-lettered or dropped after #3878.

**Decision.** (A) For every `sendValue`, `sendValueWith` and `sendValueBatch` on an instance naming `q`, when some context consumes `q`, the argument's type (the element type for a batch) must be admitted where the consumer's message type is expected, by ADR 0714's comparison (`contract_compat::check_call` over a one-parameter shape on each side, so a stronger refinement is admitted where a weaker one is expected). Otherwise it is `bynk.queue.message_type_mismatch`, labelled at the call and at the consumer's parameter. No new syntax: a typed instance `Queue[Order]` was rejected for now. The phase (`queue_producers`) reads the checker's own `Callee::Capability` classification of each send, the call's instantiated message type from its `CapEncoding`, so a send of a type parameter that is still abstract is skipped. (B) `send`, `sendWith` and `sendBatch` warn with `bynk.queue.untyped_send` when the project consumes the queue; they stay legal for forwarding an already-encoded body. (C) A queue no context of the project consumes has no type to compare with: nothing is reported, and the hover on the instance says so. (D) A dead-letter queue's consumer is an ordinary consumer of its own queue, so a send to it is checked the same way. #3877's own consumer-to-consumer check still compares the types as written; it is unchanged here.

**Consequences.** `Ty` to `TypeRef` (`ty_to_type_ref`) moved from `bynk-emit` to `bynk-check` so the phase can name a send's type; `bynk-emit` re-exports it. The driver's per-unit callee filter and the editor analysis keep the send operations of every capability for the phase, and the whole-program call checks now also receive the units' `uses` and the type interner. An existing project that sends untyped text to a queue it consumes gains a warning. Hover on a `Queue` instance names the consuming context and message type (or "No consumer in this project"); signature help on `sendValue*` shows the consumer's message type in place of `T`; completion and semantic tokens are unchanged (no new names or token kinds). A consumer's type changing while messages are queued is not caught.

## ADR: partial-content-and-not-modified
title: HttpResult answers a range read with PartialContent (206) and a handler-resolved conditional read with NotModified (304)
summary: The two variants, their shapes, the ContentRange record, the GET-only rule and the run-time range check

**Context.** #4389, found while shipping R2 range reads and conditional gets (#4049): `HttpResult` had no variant for `206 Partial Content` or `304 Not Modified`. `RawStreamed` always answers 200, and 304 came only from the router's own conditional handling, so a handler could not answer a range read with `Content-Range`, or a conditional get from R2 with 304. #3917 added `PreconditionFailed` and `PreconditionRequired` the same way, as two more rows of the variant table that OpenAPI, the client, the status tables and the editor all read.

**Decision.** (A) `NotModified` is a nullary variant, `304`, with no body, in the same bodyless family as `NoContent`; headers come through the existing response-header wrapper. It is for a conditional read the handler resolved itself (an object store checked `If-None-Match` against its own entity tag); the router's automatic `304` for an eligible `GET` is unchanged. (B) `PartialContent(body, contentType, range)` is `206`: a `Stream[Bytes]` body like `RawStreamed`'s, a `String` content-type, and a `range: ContentRange`. The body is a stream because the case it exists for (an object store's range read) hands the handler one, and a `Bytes` part can be wrapped with `Stream.of`. The content-type is an argument because a 206 answers one representation and must name it, as `Raw` does. (C) `ContentRange { start: Int, end: Int, total: Option[Int] = None }` is a record in the `bynk` adapter, not three loose arguments, so a handler passes the range it computed as one value, a unit test matches it, and `total: None` (an unknown size, written `*`) has a name. It renders `Content-Range: bytes start-end/total`. (D) Both are refused at compile time on a route whose method is not `GET`, with `bynk.http.status_needs_get` (explain entry, compiled bad/good pair, negative fixture): a range or a validator is how a client re-reads a representation it already knows, and `HEAD` is answered by the `GET` route as today. The check is made where the variant is typed, so a user sum variant of the same name is not mistaken for it. (E) A range that is not one (`start` below 0 or past `end`, `end` at or past a known `total`, a non-integer) is a fault at run time, not a refusal at compile time, because the values are computed: the dispatch's fault path answers `500` and logs the route, so a malformed `Content-Range` is never sent. (F) Nothing reads the request's `Range` or `If-None-Match` for the handler: the router does not parse `Range` today and the issue asks only for the answers, so the handler states what it sent. (G) The rest follows the variant table: OpenAPI lists a `PartialContent` response with a required `Content-Range` header and a binary body, the generated client reads it as a raw body, the status and problem tables list both, completion and hover take them from the table, and a `system` case reads a `206` back as `PartialContent` with its range parsed from `Content-Range` and a `304` as `NotModified`.

**Consequences.** A handler can serve R2 range reads and conditional gets with their real statuses. A user sum variant named `PartialContent` or `NotModified` is disambiguated by the existing `ambiguous_constructor` rule. `ContentRange` is a new name in `bynk`, so a project that declares its own `ContentRange` and consumes `bynk` unqualified gets the usual duplicate-name error. Not done: a `Range` request header parser and an automatic `416` for an unsatisfiable range.

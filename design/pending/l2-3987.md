## ADR: comparison-operand-picks-shared-variant
title: The other operand of a comparison picks a shared bare variant's sum
summary: `==`, `!=`, `<`, `<=`, `>` and `>=` type the non-variant side first and use its sum as the bare variant's expected type

**Context.** A bare variant two sums share resolves by its expected type (#3344), but `==` and `!=` gave it none, so `e == Failed("down")` with `e: MailError` was `bynk.resolve.ambiguous_variant`. The forms #3955 (`a.compare(b) == Less`) and #3976 rely on need it, under the context-only resolution decided for compiler-known sums.

**Decision.** In a comparison, an operand that is a bare variant name several sums declare (alone, with a payload, or inside `Some(…)`, a parenthesis or a list literal's first element) is checked after the other operand, whose type is its expected type. This extends #1659's existing rule for `None`/`Ok`/`Err`/`[]`. The ordering operators follow it too, and the payload's expected type threads through `Option` and `Result` as an annotated `let` already does. With two such operands nothing decides and `ambiguous_variant` stays; so it does when the other operand's type is not a sum that declares the name (`p == Failed("x")` with `p: Level`), which keeps the qualified forms in the message. It only resolves names that were errors before, so no existing program changes.

**Consequences.** `e == Failed("down")`, `e != RateLimited`, `o == Some(Failed("x"))` and `p > Medium` compile. Hover shows the resolved owner through the existing variant resolution; completion after `e ==` is not extended (no expected-type completion exists for any position yet).

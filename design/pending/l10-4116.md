## ADR: idempotency-key-types
title: Idempotency keys are any Key type, and capability operations may be called with leading type arguments
summary: How a non-String key is stored, how the call site encodes it, and the one language rule the signature needed

**Context.** `dedup`, `remember` and `claim` took `key: String`, so a typed id was turned into a string by hand, and two call sites could encode one record two ways (#4116).

**Decision.** The maintainer accepted the issue's decisions. A: all three operations take `K: Key` for their key. B: a `String`, a refined `String` or an opaque `String` key is stored exactly as before, so existing entries match; any other key is stored as `k:` and its canonical encoding (`__bynkKeyEncode`, the one value collections use), after the unchanged handler-scope prefix. The call site does the encoding, from the key argument's checked type, so the providers (D1, in-memory, the test double) keep receiving a string and are unchanged, and the emitted interface declares a first-party `Key`-bound parameter as `unknown` for the same reason a `Codable` argument is. C: `K` is inferred from the key argument. The signature `dedup[T: Codable, K: Key]` needed one language rule that the issue assumed: a written type-argument list may cover only the leading type parameters of a capability operation, the arguments determining the rest, so `Idempotency.dedup[Quote](id)` names `T` and infers `K`. A rest that no argument determines is `bynk.generics.uninferable_type_arg`; too many type arguments is `bynk.generics.type_arg_mismatch`. A qualified cross-context call (`bynk.Idempotency.claim(key, ttl)`), which until now took its type arguments explicitly and never inferred them, infers a left-out parameter from the argument whose parameter is exactly that parameter (`key: K`) and otherwise stays `uninferable_type_arg`, so existing qualified `claim` calls keep compiling. The rule is for capability operations only: a user-defined generic function still takes all of its type arguments or none. A call with all type arguments written, or none, behaves as before, so existing `dedup[T](Json.encode(id))` source still compiles and stores the same key.

**Consequences.** A non-text key's `k:` prefix can equal a `String` key spelled `k:…`, as the issue accepts for a stored form that leaves `String` keys untouched. No key length limit exists in the providers today for either form, so none is added here. The typed `stub Idempotency.dedup[T](…)` clauses key on the written type arguments only, so they are unaffected by `K`.

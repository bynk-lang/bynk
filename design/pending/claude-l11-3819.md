## ADR: agent-jurisdiction
title: An agent is pinned to a Cloudflare jurisdiction with an annotation, and changing it after deploy is destructive
summary: Per-agent annotation, the local-dev fallback, and the per-class jurisdiction the deploy ledger records and refuses to change unconfirmed
**Context.** #3819. A Bynk agent's per-key state could not be kept inside the EU: the generated Worker always built the Durable Object id from the unrestricted namespace, and `@jurisdiction` was accepted only on `R2`. Agent stubs are made only by generated code (`Learner(id).append(…)`), so an author has nowhere to write `namespace.jurisdiction("eu")` themselves. It is also a decision that cannot be reversed: an id minted through a restricted namespace is a *different* id from the unrestricted one for the same name, so adding or changing it after deploy orphans every existing instance's state.

**Decision.** (A) The annotation is on the agent: `@jurisdiction("eu")` or `@jurisdiction("fedramp")` immediately before `agent`, taking one string literal, at most once, beside `@busyAfter`; there is no context-wide default (it can follow additively). The value set is `R2`'s, through one shared helper (`bynk_std::is_jurisdiction`) that `R2`, `D1` and the agent all use. A misuse is `bynk.agent.bad_annotation`, whose description now covers both annotations; an `@jurisdiction` before anything but an agent is the parser's existing "expected `agent`" refusal. The generated agent factory passes the jurisdiction to `makeAgent`, and the WebSocket upgrade path resolves its namespace through the same `__agentNamespace`, so every caller of one class mints the same restricted id. The Worker's configuration is unchanged: a jurisdiction is a property of the id, not of the binding or the class. The events fan-out Durable Object is not an agent and is not pinned. (B) Local `wrangler dev` (workerd) throws `Jurisdiction restrictions are not implemented in workerd` from `namespace.jurisdiction(…)`. `agentNamespace` falls back to the unscoped namespace only when the error message names a jurisdiction as not implemented, and warns once per isolate; every other failure, and a namespace with no `jurisdiction()` at all, throws, so a deployed Worker can never silently lose the restriction. The in-process test namespace implements `jurisdiction(j)` with ids of its own, so `bynk test` runs a pinned agent. (C) The ledger records, per Worker, each hosted agent class with the jurisdiction its ids were minted under (`agent_jurisdictions` in `bynk.deploy.lock`; `none` for an unrestricted class), replaced on every push like the class tombstones. The next plan compares the source with it. A difference is a `jurisdiction_changes` entry in the plan (`durable_objects_jurisdiction_changed` in `--format json`) and a line `change jurisdiction of durable object shop.Learner (none → eu; its existing instances are orphaned, irreversibly; needs --confirm-jurisdiction shop.Learner)`, which `--dry-run` shows. The deploy refuses until the change is confirmed by name, at a prompt or with `--confirm-jurisdiction <context>.<Class>` (repeatable); `--yes` never stands in, and a flag naming a class that does not change is refused, as `--confirm-delete` is. A Worker the ledger records as deployed but that lists no class (a ledger from before this) was pushed unrestricted, so adding `@jurisdiction` to an agent already deployed asks for the confirmation, including for a class that is new in the same deploy, which is the price of not claiming to know what the account holds. A Worker never deployed has nothing to orphan. The record is of what was pushed, not a claim about the account's namespaces, which Cloudflare owns (ADR 0194 D1).

**Consequences.** `@jurisdiction("eu") agent Learner { … }` keeps every instance's state in the EU, and `bynk check` refuses an unknown value. The build's `BindingSource::Agent` carries the jurisdiction to the deploy, and `DurableObject` the same. The runtime gains `agentNamespace`, and `makeAgent` and `makeWorkersAgent` an optional jurisdiction. A change to an already-deployed agent's jurisdiction has no migration path: the author creates a new class in the jurisdiction and moves the data. A jurisdiction is invisible to a query and to `bynk test`, so what a real account does with it is for a live check, which this change does not make.

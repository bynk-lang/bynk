## ADR: field-rename
title: A field renamed with replaces keeps its data, its lock history and its callers
summary: `name: T replaces old` on a record, event or `store` field reads the old name wherever the field is stored, locked or decoded, and writes the new one; the lock records the rename per field

**Context.** #3793. An agent class could be renamed without losing its state (`agent New replaces Old`), a field could not. Renaming a `store` field, an event field or a wire field was a removal plus an addition: stored state read as the field's zero, the event lock refused it (`bynk.event.non_additive_schema_change`), and the contract diff called it breaking for every caller. The most common refactor was the most expensive change in a project.

**Decision.** (A) The class form is mirrored, not a new annotation: `field: T replaces old` after the type and any refinement and before a default, and `store field: Cell[T] @annotations replaces old` before the initialiser. `replaces` is contextual. (B) A wire field reads both names on input and writes the new one. The new key wins when both arrive, and an absent key takes the default or `None` as before. Emitting both names would double payloads and emitting the old name would never finish the rename. The contract classifier keeps the rule of the wire: a request is read by the callee, which declares the old name, so a renamed request field is compatible; a response is read by the caller, which only knows the old name, so a renamed response field is breaking. (C) The lock records `renamed_from` per field (event `FieldShape`, agent `StoreShape`), the old name then the names it was itself renamed from, and the stored shape text of a service carries `R(…)`, never the hash. A reconcile renames the recorded field first, so a rename alone is additive (the version goes up by one) and one beside another change is judged by that change. A `store` clause stays while a snapshot at or above the floor records the old name (`bynk.field.replaces_needed`) and warns when none does (`bynk.field.replaces_settled`), so the checker says when it is safe to delete; an event or wire clause has no floor, so the guide says to keep it until no payload under the old name can arrive. (D) Loading reads the old key after a `migrate` step and before the zero-merge and the rehydration gate (`__renameStoredFields`), and the first commit writes the new name alone. (E) Only a `Cell` store field takes the clause. A `Map`, `Set`, `Cache` or `Log` keeps each entry under a storage key carrying the field's name, so a rename moves keys rather than reading an old one; it is refused for every layout (`bynk.store.replaces_collection`), because which layout a record is in is not the author's to see. A rename inside a record stored in a field is not recognised by the lock and still needs a `migrate` step.

**Consequences.** New codes: `bynk.field.replaces_conflict`, `bynk.field.replaces_unknown`, `bynk.field.replaces_needed`, `bynk.field.replaces_settled` (a warning) and `bynk.store.replaces_collection`. A project with no clause is byte-identical, and the lock gains a key only where a field was renamed. An older toolchain that rewrites a lock drops `renamed_from`, as for `AgentEntry.renamed_from`. The editor shows `replaces` as a keyword, offers it after a field type, and hovers the clause. Follow-ups: moving a collection's entries (a key rewrite) and renaming a field inside a stored record.

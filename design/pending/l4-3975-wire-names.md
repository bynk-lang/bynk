## ADR: wire-names
title: A type's wire names are part of its one encoding
summary: `@name` on any record field, sum variant or payload field, and `@discriminator` on a sum, name keys and values on the wire at every boundary; the Bynk names never change

**Context.** #3975. `@name("…")` was legal only on a field of a request record (`cookies`, `query`, `headers`, `@form`/`@multipart` `body`), and such a record could not be a JSON body, a result, a store field, an event or a call argument. A sum's discriminator was always `kind`, its value always the variant's exact name. So a third party's JSON could not be decoded into a Bynk type: a key that is not an identifier (`content-type`, `@odata.etag`), a name Bynk would not choose (`amount_captured`), a discriminator such as Stripe's `"type": "charge.succeeded"` or GitHub's `"action"`, a lower-case or dotted value.

**Decision.** (A) A wire name is part of the type's one encoding, so it applies wherever the type is encoded: HTTP bodies and results, `Json`, `Yaml` and `Form`, cross-context calls, queues, events and stored state. The request-record restriction and `bynk.types.field_name_record_not_boundary` are lifted. (B) `@name` goes before a record field, a pipe-form variant (after the `|`), a tag of the `enum { }` shorthand and a variant's payload field; `@discriminator("…")` goes before a sum's `type`, after its doc and before `private`. Rejected: after the body, where `derives` goes, which would separate the discriminator from the variants' names on a long sum. (C) Names are non-empty and unique within a record, within a variant's payload and within a sum (`bynk.types.field_name_duplicate`, extended to variants); a payload field's wire name may not be its sum's discriminator, `kind` unless named (`bynk.types.discriminator_collides`); `@discriminator` is on a sum only (`bynk.types.discriminator_not_sum`) and takes one non-empty string, or a `String` constant bound to one (`bynk.types.discriminator_bad_arg`); another annotation on a type or a variant is `bynk.types.annotation_unknown`. `Option` and `Result` keep their fixed shapes. (D) A wire name is part of the stored and the contract shape. An event field is recorded in `bynk.schema.lock` under its wire name, and a field of a record stored in an agent has its path under it, so changing a name is a removal and an addition as for any other change to the key: `replaces` names the previous key, judged against the field's wire name, and a stored record needs a `migrate` step. The contract hash and the stored shape text carry the wire names and a sum's discriminator (`Key("…")`), so a different request key, discriminator, variant name or payload key is breaking. `bynk.types.wire_name_on_locked_type`, which the issue gave for the time before #3793, is not added: `replaces` has landed, and a wire-name change on an event or stored field is already refused by the lock until it is declared. (E) The Bynk names never change: access, construction, `match` and diagnostics use them. The codecs, OpenAPI, the MCP descriptions, the typed system drivers and the decode error paths (`$.amount_captured`) use the wire names. The in-memory discriminant stays `tag`.

**Consequences.** The generated codecs read and write the wire key, and each decoder keeps its locals under the Bynk name. The runtime readers of a request record now build the object the codec reads under the wire key (they built it under the Bynk name and the codec read that), the path-parameter, query, header and cookie enum leaf is the bare string a payload-less sum already read, and the enum written to a typed cookie uses the variant's wire name. A record, sum or event without a wire name emits byte-identical codecs, and has the same hash and lock. New codes: `bynk.types.annotation_unknown`, `bynk.types.discriminator_bad_arg`, `bynk.types.discriminator_collides` and `bynk.types.discriminator_not_sum`; retired: `bynk.types.field_name_not_request_record` and `bynk.types.field_name_record_not_boundary`. The editor marks the annotations as decorators, offers `@name` and `@discriminator` where they can go and hovers the wire name. The lock still judges an event field of a named record type by the type's name, so a wire name inside a nested record that an event carries is not seen by it (pre-existing for any change to a nested type).

## ADR: api-key-format-opaque-handle
title: An API key is `<prefix>_<id>_<secret><checksum>` in fixed-width base62, and its public id names a random handle, never the identity
summary: The `ApiKey` key format, and how the request path reaches an identity's key store through an opaque handle that `revokeAll` replaces

**Context.** Opaque, revocable API keys are how most developer and service-to-service APIs authenticate, and Bynk has no scheme for them: a service reads the header itself and hand-writes the key generation, hashing, comparison and revocation (the API keys track, `design/tracks/api-keys.md` §1–§2, spine #3939). The track adds `ApiKey` to the closed scheme set by widening ([ADR 0080](0080-actor-schemes-closed-nominal.md)), as compiler-generated verification, never a user `Verifier` ([ADR 0175](0175-oidc-jwks-scheme.md) A), following `SignedCookie`'s pattern ([ADR 0821](0821-signed-cookie-actor.md)). Unlike a cookie, a key's secret is not self-verifying: the service must store something per key and find it from the presented key. Two questions are settled here: what a key looks like, and how the seam reaches its record without the key revealing whose it is (track §5, §6, Q1, Q2).

**Decision A — the format.** A key is `<prefix>_<id>_<secret><checksum>`:

- **Prefix.** The actor's `prefix`, `[a-z][a-z0-9]{1,15}`, defaulting to `bk`, distinct per `ApiKey` actor in a context. It makes a leaked key recognisable and attributable, and in a sum it tells the seam which arm a key is for without a lookup.
- **Id.** 24 bytes: a 16-byte random *handle* naming the identity's key store, then an 8-byte random key number within it. The id is public: safe to log, to show in a console and to pass to `revoke`.
- **Secret.** 32 bytes from `crypto.getRandomValues`. Never stored, never logged.
- **Checksum.** The CRC32 (IEEE 802.3, the reflected polynomial `0xEDB88320` that zlib and GitHub's tokens use) of the ASCII bytes of everything before it, `<prefix>_<id>_<secret>` with both separators, appended to the secret. It is not a security control (anyone can compute it). It lets a secret scanner confirm a match offline with few false positives, and lets the seam refuse a mistyped or truncated key before any lookup.

Every field is big-endian base62 over the alphabet `0-9A-Za-z` (so digit value 0 is `0`, 10 is `A` and 61 is `z`), left-padded with `0` to a fixed width: 33 characters for the id, 43 for the secret, 6 for the checksum. The secret and checksum share a part with no separator, so the seam splits them by position. A field of the right width whose value does not fit its byte count is malformed, so each key has exactly one encoding. A key is at most 100 characters; a presented key longer than 128 characters is refused before parsing. Base62 with `_` separators keeps a key one "word" that survives a double-click, a URL and shell quoting, the choices GitHub's token format made for the same reasons. Rejected: a fixed `bk_` prefix for every service, under which every Bynk service's keys look alike and a leak cannot be attributed. Rejected: plain (unpadded) base62, under which over a third of ids alone would be shorter than their own format and fail to parse.

**Decision B — the opaque handle.** The compiler generates two agents per `ApiKey` actor:

- **`<Actor>Keys(handle)`** holds one identity's keys (key number → HMAC, pepper `kid`, label, created, expires, last used, and an empty `scopes` set so scopes are not a later migration), plus the identity itself. It is the only agent on the request path.
- **`<Actor>KeyOwner(identity)`** holds that identity's handle, minted at random the first time a key is minted for it. Only the members use it; verification never does.

Verification is one agent call, because the handle is in the key, and nothing in a key reveals whose it is. Rejected: encoding the identity in the id, which would name the customer in every log line and leak, and let anyone who knows an identity aim traffic at its agent. Rejected: an index agent per id, which costs a second sequential call on every request. Rejected: a record per key id, which loses an atomic `revokeAll`. The handle does not rule out a later owner lookup (`Keys` stores the identity) or key transfer (repoint `KeyOwner`); either can be added without a breaking change.

**Decision C — `revokeAll` replaces the handle.** It runs as a `KeyOwner` handler: it empties the current `Keys(handle)` instance in one atomic commit and marks it retired, then mints a fresh handle, which `KeyOwner` commits when its handler returns. A retired instance holds no records and refuses inserts, so a key presented against it gets the ordinary `401` after the same work. `mint` also runs through `KeyOwner`, which runs one handler at a time, so a mint cannot land on a handle being retired. The order fails safe: if the second commit fails, the keys are already gone and `KeyOwner` still names the retired handle, and any `KeyOwner` handler that finds its handle retired rotates it before doing anything else, so the identity is never left unable to get a key. A single `revoke` does not rotate the handle, because the identity's other keys still live in that instance.

**Decision D — the agents are generated Bynk source with reserved names.** Both agents are generated as Bynk source and appended to the declaring context before it is parsed, as `<Actor>Sessions` is ([ADR 0998](0998-signed-cookie-sessions.md) B), so the checker, `bynk.schema.lock`, the emitter and the deploy migration treat them like any agent, and their shape is the compiler's to evolve. They read no clock: the seam and the members pass `now`, so the context needs no `consumes Clock`. Their digest compare is `bynk.crypto`'s constant-time `Crypto.equal`, a capability method, so the generated agents consume `Crypto`; the compiler supplies that requirement with the agents it generates, so an author never declares a capability for code they did not write. Their names are reserved in the declaring context: an author's declaration that takes one is `bynk.actor.api_key_agent_name_reserved`. A context-wide cap of 100 live keys per identity bounds an agent's state.

**Consequences.** A key reveals at most that two keys share an owner, when both ids are seen, until `revokeAll`. One identity's request path is serialised through one Durable Object, a per-identity throughput ceiling inherent in one agent per identity, and the reference states it. A well-formed fabricated key passes parsing and reaches an instance, which the rate limit asked before authentication bounds (the verification-contract ADR in this increment, and [ADR 1009](1009-rate-limit-annotation-client-ip.md)). `ApiKey`, its types and the reserved names enter as experimental under `[unstable] allow`; the stored record shape is versioned with the generated agents and joins the stored-data promise only on promotion.

## ADR: api-key-peppered-storage
title: An API key is stored only as a peppered HMAC, and its secret is returned once as a third secret kind
summary: The `ApiKey` pepper and its rotation, what an agent stores, and `ApiKeyValue`, the minted key's opaque type

**Context.** A service that issues keys must keep something per key to check a presented one, and whatever it keeps is an asset: a copy of the store, a log line or a debug print must not yield a usable key (track §7, §9, §13, Q3). Bynk already has the pieces. `SignedCookie` keys are environment secrets that `bynk deploy` mints when unset, selected by a `kid` and rotated through `previous` without signing everyone out ([ADR 0821](0821-signed-cookie-actor.md)). `Secret` ([ADR 1038](1038-opaque-secret.md)) and `Authorization` ([ADR 1046](1046-authorization-from-secret.md)) are opaque `secret_kind`s that cannot be stored, cross a boundary or be interpolated.

**Decision A — only a peppered HMAC is stored.** The stored value is `HMAC-SHA-256(pepper, secret)`. The pepper is the environment variable the actor's `secret` names; `bynk deploy` mints it when unset, through the same path as a `SignedCookie` key. It is unpadded base64url of at least 32 bytes, and a missing or bad pepper faults the request, with a message that names the variable and never its value. A copy of the agents' storage alone therefore allows no offline guessing. Rejected: `bynk.crypto`'s PBKDF2, which slows the guessing of low-entropy passwords and adds nothing for a 256-bit secret. Rejected: an unkeyed SHA-256 digest, under which a storage leak needs nothing more to be checked against.

**Decision B — the pepper never enters an agent.** The seam computes the digest from the presented secret and sends the digest, so an agent holds and compares digests only. `mint` computes the digest in the service handler, where the pepper arrives, as `issue` does, so `mint` is legal only in a service handler (`bynk.actor.api_key_mint_outside_handler`). `secret` and `previous` stay strings naming environment variables, as every actor's do; they are not `Secret` values, because the generated seam reads the pepper and no Bynk code holds it.

**Decision C — each record names its pepper; rotation follows cookies.** A record stores the `kid` of the pepper it was hashed under (the first 6 bytes of SHA-256 of the pepper, as a session key's). To rotate, set a new `secret` and move the old value to `previous`. While `previous` is set, the seam computes the digest under both and sends both, and the agent compares the one its record's `kid` names. A record under `previous` that verifies is re-hashed under `secret` in the same commit. A record whose `kid` matches neither pepper is refused like any other bad key (the verification-contract ADR in this increment) and is never pruned on the refusal path, which would let anyone holding an old id cause a write; `mint` prunes such records along with expired ones. Dropping `previous` ends every key not used since the rotation began, because a stored HMAC cannot be re-keyed without the secret; the reference says so beside the rotation steps. Rejected: keeping every old pepper forever, under which rotation never retires a pepper suspected of a leak.

**Decision D — the minted key is `ApiKeyValue`, a third secret kind, returned once.** `mint` answers an `ApiKeySecret` (`{ id: ApiKeyId, key: ApiKeyValue, label, created, expires }`). `ApiKeyValue` is a third `secret_kind`, beside `Secret` and `Authorization`: no string form, not `Eq`, a `Key` or `Codable`, and `bynk.types.secret_at_boundary` as a record, event or `store` field, or a handler's parameter or result. Its one exception is that a handler may return the `ApiKeySecret` that `mint` answered, and only there does it encode on the wire as the key string, so the key is shown once. At run time it is the `BynkSecret` wrapper, which renders `<secret>` everywhere, so a fault message, a trace or a failing `expect` never shows it; the public `ApiKeyId` beside it names the key. `ApiKeyId` is public and string-constructible, so it can be a path parameter.

**Consequences.** Someone who can read the agents' storage or the logs, but not the Worker's secrets, gets nothing usable. Nothing logs a key: the seam logs at most the actor and the key id, and the runtime does not log response bodies, so the key returned by `mint` passes through the response once. The test that pins `bynk`'s opaque types moves from two to three. A handler can still write the minted key somewhere unsafe before returning it: the type rules make that hard, not impossible, and the reference says so. Whether `bynk deploy` provisions the pepper correctly on a real account is live check K1, which the maintainer runs before the slice that ships it lands.

## ADR: api-key-verification-contract
title: An API key seam refuses a malformed key before any lookup and every other bad key with one identical 401, and a store fault never admits
summary: The order of checks on an `ApiKey`-guarded route, what is refused before the store is asked, and why every other failure looks the same

**Context.** A seam that answers differently, or works differently, for an unknown key than for a wrong one tells an attacker which keys exist; one that admits on a store fault is a bypass; one that caches tells a revoked key it is still good (track §8, §13, Q4). The existing seams compare in constant time through `crypto.subtle.verify`, answer `Unauthorized` for every failure after their first check, and hide the credential they consume from the handler ([ADR 0899](0899-seam-consumed-credential-hidden-from-request-headers.md)).

**Decision A — the order of checks.** On a route an `ApiKey` actor guards, before the handler runs. The request is read and its parameters decoded first, in the order an ordinary route keeps (ADRs 1009 and 1023); only a `key: identity` rate limit splits verification ahead of the body, through ADR 1023 B's `verify` and `run` steps:

1. Read the key from the actor's `header`, or from `Authorization: Bearer` when there is none. Absent, or the header sent more than once: `401`.
2. Parse: length, prefix, the three parts, base62, checksum. Any failure is `401` **with no lookup**.
3. Compute `HMAC-SHA-256(pepper, secret)`, and under `previous` too while it is set.
4. Look up and compare in the agent: `<Actor>Keys(handle).verify(keyNo, digests)`. Then the expiry, judged in the agent against the `now` the seam passes. An expired record does the same comparison work and is refused before the agent writes anything, so no refusal re-hashes a record or records its use.
5. Mint the identity through the identity type's `of`; a violation is `401`.
6. Run the handler.

`Authorization: Bearer` is the default because it is what HTTP clients, proxies and log scrubbers already treat as a credential. Rejected: `x-api-key` as the default, which is not a standard and is not redacted by default in common logging.

**Decision B — one refusal, the same work.** Every refusal from step 2 onwards is the same `401`, with the same body and headers, whatever failed. An unknown key number is compared against a fixed dummy digest, as is a record whose `kid` matches neither pepper, so the work is the same as for a wrong secret; an unknown handle reaches an instance with no records and does the same work. The comparison is `bynk.crypto`'s constant-time equality, including the compare against the dummy. A malformed key is refused faster, which reveals only that the format is wrong, which is public. The `401` carries a `WWW-Authenticate` challenge: `Bearer realm="<context>"` for the default header, and `Bynk-ApiKey realm="<context>", header="<header>"` for a named one.

**Decision C — a store fault never admits and is never a `401`.** An unreachable agent faults the request (`500`), and `AgentBusy` answers `503` with `Retry-After: 1`, as on any HTTP route, so a client does not conclude its key is bad. In an actor sum, a store fault in an `ApiKey` arm faults the request; it never falls through to a later arm or to `Visitor`.

**Decision D — nothing is cached.** Every request asks the agent, so a revoked key is refused on the next request. The price is one agent round trip per authenticated request, and the reference states it.

**Decision E — the handler never sees the key.** The actor's header joins `consumed_credential_headers`, as ADR 0899 already anticipates for `ApiKey`, so it is removed from the handler's `RequestHeaders` view, and a typed `headers` field that reads it is `bynk.http.headers_field_consumed` ([ADR 0987](0987-refuse-consumed-header-fields.md)). In a sum, every member's header is hidden whichever arm resolves: a refused key may still be a live secret, and no handler needs it.

**Decision F — fabricated keys are bounded by a rate limit asked first, and its absence is warned.** A well-formed fabricated key is cheap to make and reaches the store, so the defence is `@rateLimit(Limiter, key: clientIp)`, asked before authentication ([ADR 1009](1009-rate-limit-annotation-client-ip.md) A). It must not be opt-in: an `ApiKey`-guarded route that applies no rate limit before authentication is the warning `bynk.actor.api_key_unlimited`, which says what an unlimited route costs. It is a warning, not an error, so a service rate-limited at the edge still compiles. `key: identity` ([ADR 1023](1023-rate-limit-identity-key.md)) does not help here, since a fabricated key never reaches that limiter. Rejected: an authenticated id (a MAC over the id), which would refuse fabricated ids without a lookup but tie every id to the pepper, so a rotation would end every key.

**Consequences.** The seam is fail-closed at the HTTP boundary, in generated code, and the handler sees only the sealed identity. Revocation is as fast as the next request, not faster: a request already past the seam completes. A never-used instance may start more slowly than a busy one, so timing can tell whether a handle has been used; handles are 128-bit random, so an attacker learns this only about a handle they already hold. An `ApiKey` actor on a WebSocket `on open` is `bynk.actor.scheme_not_admissible` until the upgrade has a liveness check, as for `sessions = true` ([ADR 1061](1061-websocket-cookie-oidc-open.md) A). Every refusal path is covered by a bypass-class test ([ADR 0087](0087-security-ci-posture.md)), and a harness test pins that the failure principals get byte-identical responses.

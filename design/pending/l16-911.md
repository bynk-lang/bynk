## ADR: message-codes-are-scoped-to-their-unit
title: A message code is scoped to the unit that declares it
summary: message(code) and render resolve only against the bundles of the unit where they are called; another unit's messages are used through a function it exports

**Context.** A message `code` was a bare dotted `String` matched by string equality
(#911, the M5 question the message-bundles track left open). Two units could declare the
same code with different templates, and nothing said which one a program meant. The
identity model the issue waited on has since shipped (`[package] name = "org/package"`,
`<alias>.<unit>`), and the maintainer ruled on 27 November 2026 that a code is scoped to
the unit that declares it, so its identity is the package, the unit and the code.

In practice the collision was already contained. A commons that declares `messages` blocks
gets its own generated `render`, which reads only that commons's bundle, and a function in
that commons that renders a code reads the commons's own bundle. The leak was that the
generated `render` was also an ordinary exported function of the commons: a unit that did
`uses shop.messages` could call it (`render(tag, m)`, `uses shop.messages { render }`, or
`Messages.render(tag, m)` through an alias) and read a bundle that was not its own.

**Decision.**

- **Resolution.** `message(code)`, and `render` over it, resolve only against the bundles
  declared in the unit where they are called. Two units, in one package or in different
  ones, can each own `"greeting"` without colliding. There is no new syntax; the
  completeness and placeholder checks stay per unit, where the bundle is declared.
- **Another unit's messages** are used by calling a function that unit exports, which
  renders them in the unit that owns the bundle, as `examples/greeter-i18n` does with
  `greet`. The generated `render` is not importable: it is left out of what a `uses`
  brings in, so an importing unit's `render` is `bynk.locale`'s. A qualified or selected
  reference to it (`Messages.render`, `uses shop.messages { render }`), or a bare `render`
  in a unit that does not `uses bynk.locale`, is `bynk.messages.cross_unit_render`, which
  names the unit and the exported-function route. A bare `render` in a unit that does
  `uses bynk.locale` resolves to `bynk.locale`'s and returns the code: that combination was
  `bynk.uses.ambiguous_name` before, so no program relies on it, and a fixture pins it. A second hop through a third unit reaches nothing
  further: `uses` is not transitive, so the third unit never sees the bundle's `render`.
- **A literal code** passed to `message(…)` in a unit that declares a bundle must be a
  code of its `@reference` block, in the unit and in its suites
  (`bynk.messages.unknown_code`, with the nearest declared code as a suggestion). Before
  this, a typo compiled and rendered the code itself at run time. A code the program
  computes (`message(code)` with `code` a parameter, as `greet` does) is not checked, and
  keeps the runtime fallback, which is how one function renders whichever code its caller
  passes.
- **A unit with no bundle** is exempt from the literal check. There is no reference bundle
  to check against, and its `render` is `bynk.locale`'s, whose documented floor returns
  the code and its parameters. The locale-negotiation fixtures use this on purpose (816 is
  a no-bundle regression test), and making it an error would force every such program to
  declare a bundle it has no use for.
- **Timing.** This is before 1.0, as ruled, and it is breaking: both changes refuse
  programs that compile today. The increment's `breaking:` line carries the migration.

**Survey.** Every program in the corpus, the examples and the site's code blocks was
scanned (5,472 units and suites; 67 declare a bundle). None renders a code declared in
another unit, so no program needs the cross-unit migration. Seven fixtures name a literal
code that is not in their own unit's bundle: five have no bundle and are exempt (804 to
807 and 816), and two (808, 810) deliberately test the runtime fallback for a code the
bundle does not declare, which now reaches `render` as a computed code.

**Consequences.**

- Collisions are structurally impossible rather than a silent string match; a code's
  identity is its package, its unit and the code, with the package and unit supplied by
  where the call is, not by the code's spelling.
- A project that wants one shared set of messages declares them in one unit and exports
  the functions that render them. That is a wrapper function per use, which is also the
  pattern the guide already taught for keeping `uses bynk.locale` out of contexts.
- The note in the guide that a context must not `uses bynk.locale` alongside a bundle, to
  avoid `bynk.uses.ambiguous_name`, no longer holds: the bundle's `render` is not
  imported, so the name is not ambiguous. A context that does both gets `bynk.locale`'s
  `render`, not the bundle's.
- Not decided here: namespacing a code with its package in the template files or in
  `render`'s output, and negotiation across several bundles in one context
  (`bynk.locale.multiple_message_bundles` is unchanged).

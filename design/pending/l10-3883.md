## ADR: email-environment-addresses
title: A named environment claims only the inbound-email addresses it is mapped
summary: Why `--env staging` omits `addresses` unless `[deploy.email]` maps it one, and how a mapped address reaches the service

**Context.** Wrangler's `addresses` is top-level only, applies to every environment of a Worker, and is ignored under `env`. Bynk writes the `from email` services' addresses there (ADR 0808 F) and runs `wrangler deploy --env <name>` against the same file, so a named environment was handed production's list. Wrangler documents that naming an address another rule holds takes that rule over: interactively it asks before applying the destructive change, and non-interactively it applies nothing and exits with an error after deploying the Worker, so every staging deploy failed with the Worker already live. It also documents that an omitted `addresses` changes no Email Routing rule, while an empty list removes every rule the Worker manages. **This is derived from Wrangler's documentation and the deploy code; it has not been observed against a live account.** The live check (deploy a `from email` project to `default`, then `--env staging`, and record what Wrangler does) is filed as #4427, and this decision does not wait for it.

**Decision.** (A) A non-default environment omits `addresses` from the configuration it hands Wrangler, unless it is mapped. Omitting is Wrangler's documented "change nothing", so production's rules are left alone. An empty list was rejected, because it would delete every rule the staging Worker manages; copying production's list is today's hazard. The deploy rewrites the top-level key in the environment's copy of the file (the generated file and `default` are untouched, byte for byte). (B) `bynk.toml` maps an address per environment, following `[deploy.vectorize]`: `[deploy.email."<address>"]` with `address = { <env> = "<address>" }`. A mapped environment writes the mapped addresses as its top-level `addresses`. `default` cannot be mapped, because its addresses are the source's. A key must be an address a `from email` service names; a mapped address passes `bynk.email.invalid_address`'s rule; and no address is claimed by two environments, or by both the source and an environment, since Email Routing keeps one rule per address. Those checks need the project's sources and the checker's address rule, so the deploy makes them, before anything is pushed. The manifest's shape is read where the rest of `[deploy]` is (`bynk-project`), and a malformed table fails `bynk check`. (C) The Worker built for the project accepts mail to a mapped address: each mapped address is a route to the same service, with the same admitted verdicts, beside the source's own, so dispatch matches whichever address arrives. No runtime code changes: the routes are data in the generated `email()` entry. (D) The plan says what each environment claims: the mapped list, or `email: none (no mapping for <env> in [deploy.email]; ...)` (and `email_unclaimed` in JSON) for a Worker whose source has addresses. An environment that claims none prunes nothing, because Wrangler changes no rule for an omitted key; but a mapped address it gave up still has a live rule pointing at the Worker, which no longer accepts it, so the plan names each as `email address <a> no longer accepted (its Email Routing rule is left in place ...)` (`email_left_in_place` in JSON) and the ledger keeps the record rather than clearing it. Dropping one of several mapped addresses is still the existing `--prune` gate.

**Consequences.** A project that shared addresses across environments loses that, which never worked: the second environment either failed or took the rules over. The changelog and the upgrading note say so, and how to map an address instead. A mapped staging address on another domain needs Email Routing enabled there. The mapping is read at build time to give the Worker its routes, so a mapped address is accepted by every build of that Worker, including the default environment's, which only ever receives mail for addresses it claims. A Worker whose address is routed to another environment's mapped address by hand is still the account's choice. Hover, completion, semantic tokens and signature help are unchanged, because there is no source surface; the manifest keys are in the published `bynk.toml` schema.

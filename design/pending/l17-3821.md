## ADR: bearer-issuer-audience
title: A Bearer actor binds its tokens to a purpose with `issuer` and `audience`, and two actors on one secret must differ
summary: `Bearer` takes `issuer`, `audience` and `trustFrom`, the seam refuses a token whose `iss` or `aud` does not match, the config keys are closed, and two Bearer actors on one secret must declare different audiences

**Context.** `verifyBearerJwtHs256` checked the HS256 signature, `exp`, `nbf` and `sub`, and nothing else, so any token signed with the actor's secret was accepted whatever it was minted for. Where one HMAC secret is shared between token types, binding a token to its purpose with `iss` and `aud` is the standard defence (RFC 8725 sections 3.8 and 3.9, cross-JWT confusion), and the seam is generated, so an author could not add the check. Worse, the checker's `Bearer` arm had no closed key set: `Bearer(secret = "S", issuer = "web", audience = "api")` compiled and `issuer` and `audience` were silently ignored, so an author who wrote the protection had none (#3821).

**Decision A — `issuer` and `audience` are checked when declared.** When `issuer` is declared the token's `iss` must be present and equal it. When `audience` is declared the token's `aud` must be present and equal it, or, if `aud` is an array of strings, contain it; any other shape of `aud` is refused. A failure is `401`, after the signature, `exp` and `sub`, so a forged token reveals nothing about them. An actor that declares neither checks neither, and a token carrying an `iss` or `aud` it does not name is accepted as before, which a runtime test pins. Refinement actors follow their base.

**Decision B — the key set is closed, and two actors on one secret must differ.** The keys are `secret`, `issuer`, `audience` and `trustFrom`; any other is `bynk.actor.bearer_unknown_key` and a non-string or empty value `bynk.actor.bearer_bad_arg` (as is a `trustFrom` that names the actor's own secret). Two `Bearer` base actors that read one secret must each declare an `audience` and the two must differ, or it is `bynk.actor.bearer_secret_shared`, reported once per pair at the actor that sorts later. The message and the migration say how to fix it: declare a distinct `audience` on each and mint each actor's tokens with it, which `bynk token <Actor>` does. Refinements are exempt, because they share their base's secret by design. A pair that also names the same `trustFrom` variable is refused under the same code, since that variable could give both the same audience at run time. A repeated config key is `bynk.actor.bearer_bad_arg`, because the one that is read would be the only one checked. Rejected: a warning, since the silent confusion is the vulnerability.

**Decision C — `iat` is not required.** `exp` is already required and `iat` adds little.

**Decision D — `trustFrom` reuses `Oidc`'s mechanism.** The JSON of the named environment variable, `{ "issuer"?, "audience"? }`, replaces the declared values at run time; unset leaves them and set but malformed refuses every token (`__bearerTrust` returns `null`, which `verifyBearerJwtHs256` treats as "trust unavailable"). Only values the actor already declares or the variable supplies are checked, so an actor with `trustFrom` and no declaration checks what the variable gives it. When neither a literal nor the variable supplies an `issuer` or `audience` (a `trustFrom` actor with no literal whose variable is unset, empty or `{}`), nothing would be checked, so the seam fails closed: every request is refused and one log line names the variable, rather than a forgotten production variable silently accepting every token. A literal on either claim keeps today's fallback.

**Consequences.** Tokens that share a secret are no longer interchangeable once each actor says what its tokens are for, and an `issuer` or `audience` written by an author is enforced instead of ignored. The emitted code is unchanged for an actor that declares none of them (the third argument is passed only when there is something to check). `bynk token <Actor>` mints with the declared `iss` and `aud` (a set `trustFrom` variable replaces them, as the seam reads it, and one the seam would refuse is an error rather than a token that always 401s), the `system` tier signs a valid principal's token with them (reading a `trustFrom` variable from the case's `env` as the seam does), and `by WrongIssuer` and `by WrongAudience` drive a lone `Bearer` route that declares the claim. A project that already wrote `issuer` or `audience` on a `Bearer` actor, or that shares a secret between two actors, must mint its tokens with the claim or the distinct audience, which the changelog and the diagnostics say.

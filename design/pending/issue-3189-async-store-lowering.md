## ADR: async-ready-store-lowering
title: Store collection calls are awaited, and store queries chain through __bynkThen
summary: Every call the emitted code makes on a store handle is awaited and every store query runs its stages through a helper that serves a value or a promise, so a storage-backed handle can replace the in-memory one without a second change to the lowering

**Context.** The in-memory handles (#3254) return their values at once; the storage-backed ones (#3295) return promises. The lowering written for the first assumed the first: a keyed op called `has`/`get`/`put` and used the results synchronously, and a store `Query[T]` was a thunk producing an array that each builder and terminal indexed directly. Decision F of #3189 needs the second, and the `Awaitable` return types of the handle interface were designed for it. Doing this as its own increment keeps the lazy wiring (part 2b) small and lets this change be checked against the whole existing suite, since it must change no behaviour.

**Decision.** (1) Every call the emitted code makes on a `store Map`, `Set`, `Cache` or `Log` handle (`get`, `put`, `remove`, `add`, `append`, `prune`, `liveSize`, and the `has` and `get` of `update` and `upsert`) is awaited inside the async function that already wraps the operation; `contains` and `size` return the handle's value, which the effect that runs them already awaits. (2) A store `Query[T]` is a thunk producing its elements **or a promise of them**; its TypeScript type is `() => readonly T[] | Promise<readonly T[]>`. Each query builder and terminal runs on its source through a runtime helper, `then(value, f)` (emitted as `__bynkThen`), which applies `f` at once to a value and after a promise settles: an in-memory source still runs synchronously, a promise-returning one runs when it arrives. Operations that read another query (`flatMap`, the joins) await it. A read-modify-write (`Map` and `Cache` `get`, `update`, `upsert`) is chained through the same helper rather than awaited step by step, so over an in-memory handle its read and write still run in one tick, as before.

**Consequences.** No agent's behaviour changes: the in-memory handles return values, so each operation runs in the order it did before; the whole existing suite passes, including the TypeScript strict verification of every emitted fixture. The emitted code changes shape for every agent with a store collection (golden churn), and a store `Query` parameter's TypeScript type gains the promise alternative. The storage-backed handles are wired in by the next increment. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

**Interleaving.** Awaiting a handle call adds await points inside a handler, so the question is whether two handlers on one instance can now interleave between a read and the write that depends on it. They cannot: a handler runs inside the per-instance queue (#3217; `serialiseAgentClass` on Workers, `serialiseBundleAgent` in the bundle), which starts the next handler only when the previous one has committed, and on Workers the Durable Object output gate holds a handler's writes back until they are durable. The awaits this change adds are inside one handler, so they change when its own steps run, never which handler runs between them. `agent_serialise.test.ts` pins this for a Map: two concurrent read-modify-write handlers on one key lose an update on the raw class and both count through the queue.

**Cost.** In-memory handles return values, so each step still completes in the same turn; the only addition is one `then` call and an async wrapper per operation. Measured on the in-memory path before and after (Node, p50 over 3000 runs, `add`/`lookup`/`bump` on a Map of 100 entries): the two builds agree within noise (745 against 760 µs for `add`, 555 against 565 for `lookup`, 752 against 769 for `bump`; the same at 1000 entries). Per-operation cost at this stage is dominated by the whole-record load and commit, which part 2b replaces. List queries and list-backed stores are unchanged.

**Scope.** Only emitted code for agents with a `store` collection changes (`__bynkThen` is imported only there); a Cell-only agent's output is byte-identical, and every changed golden fixture contains a store handle.

**Concurrent operations on one key.** Within one handler, branches of `par`/`parTraverse` that update the same key are atomic over the in-memory handles, exactly as before. Over a storage-backed handle (part 2b) each storage read yields, so two such branches on one key can interleave between the read and the write; the per-instance queue protects handlers from each other, not branches inside one handler. Part 2b records this in its ADR.

## ADR: per-file-consumes
title: `consumes` is per file: a file's imports are what its own `consumes` clauses bring in
summary: Declarations are shared across a unit's files, imports are not; suites follow the same rule; amends the braces-only scope

**Context.** [ADR 0845](0845-braced-consumes-lists-what-is-in-scope.md) made the braces of `consumes bynk { … }` mean what they say, for the first-party units only, and for the unit as a whole: a `consumes` in any file of a split context counted for every file. Stage 1 left two gaps, found when the next stage was explored on github-hooks, shop, showcase and the guides (#3536). The fix attached to `bynk.consumes.type_not_selected` was a silent no-op in a sibling fragment, because the clause is in another file. And a suite had no `consumes` of its own, so its names came from its target's braces. The maintainer's decision on the issue is that Bynk has one rule for every `consumes`.

**Decision.**

1. *Declarations are shared, imports are per file.* A unit's own declarations are in scope in all its files, as before. A name from another unit, whether a standard-library unit, a context of the project or an adapter, is in scope in a file only if that file itself has a `consumes` bringing it in: a bare `consumes U` brings in all of `U`'s names, a braced list only the names it lists (an alias, `T as V`, is per file too). Two files may consume the same thing. A unit's dependencies (wiring, deploy order, the `consumes` graph and its cycle check, which services a bundle composes) are the **union** of its files' `consumes`, so repeating a clause in several files costs nothing.
2. *Three kinds of name, three warning codes.* This increment is the warning stage: each still resolves, unit-wide as before, and each warning carries a machine-applicable fix. A type, or a bare variant of a sum, is `bynk.consumes.type_not_selected` (the code stage 1 introduced, widened from "first-party units, whole unit" to "any consumed unit, this file"). A flattened capability named in a `given` clause, a call `Cap.op(…)`, `provides`, a derived capability's base or a suite's `stub` is `bynk.consumes.capability_not_selected`. A call to another unit's service (`pay.charge(…)`) is `bynk.consumes.unit_not_consumed`. The capability and call codes are siblings rather than reuses: their message says what kind of name it is, and a call needs only a clause for the unit in any form, since no braced list names a service, so the fix adds `consumes U` rather than a name. A later minor release makes all three errors, and makes the unit-wide resolution (which decides name clashes and bare-variant candidates) per file as well.
3. *The fix always edits the reported file.* It extends that file's braced clause for the owner, or inserts a `consumes` line after the file's last `uses` or `consumes` clause (or after the header), listing every name the file needs from that owner so the file's warnings share one edit. A headerless fragment, a braced `context … { }` and a suite (with or without `as <tier>`) are all supported. `bynk check --fix=bynk.consumes.type_not_selected,bynk.consumes.capability_not_selected,bynk.consumes.unit_not_consumed` migrates every fragment and suite of a project, repeating until nothing remains.
4. *Suites follow the same rule, purely per file.* A suite file may have `consumes` clauses (after `uses`, before `stub`, `env`, `fixture`, `type`, `const`, `fn`, `case` and `property`; in the grammar `consumes_decl` was already a suite member). A suite sees all the target's **own** declarations, and its own `type` still wins over an unlisted standard-library name, but the names it takes from other units come from **its own** `consumes` only, not from the target's clauses. A suite may list capabilities as well as types, since it names them in `stub` and `given`. Types reached through a capability's signature (`Response` through a `Fetch` stub) must be listed in the suite too. Options considered, from the stage 2 exploration: (a) a suite-local `consumes` (chosen: the same-file fix, no cross-file edits, and the rule stays "a file's names come from its own clauses"); (b) an error at the target's braces with a cross-file fix (rejected: needs a fix machinery that does not exist, and puts test-only names in production clauses); (c) exempt suites (rejected: a permanent hole where people copy code from); (d) suites follow the target's *unselected* set (rejected as the rule, since it keeps two meanings of "reached"). Inheriting the target's clauses on top of (a) was rejected by the maintainer.
5. *Types reached through a listed capability keep their names.* Stage 1's refinement stands, and is unit-wide on purpose: a type that a listed capability's signatures reach is in the unit's table whichever file lists the capability, and the unit's declarations share one namespace, so a local type of the same name still conflicts (`bynk.consumes.name_conflict`) rather than silently replacing it. It does not make the name writable elsewhere: writing it still needs the file's own `consumes` to list it, as for any other type. When the error stage makes resolution per file, the clash check stays unit-wide for the same reason.

**Open.** Not decided here, and not touched by the warning stage: re-exports and `exports capability`; a qualified `given B.Cap`, which names its unit but whose file need not yet consume it; agents and adapters spread across files; aliases in suites (an alias is a name of the target's table, so naming one in a suite is not warned); a local variable named like a consumed unit (`let pay = …; pay.charge(…)`) reads as the unit; and a bare `consumes U` flattens no capabilities, so it does not bring `given Cap` in, as today.

**Consequences.** Where a file names something it does not itself consume, `bynk check` warns, and the one-line migration is `bynk check --fix=bynk.consumes.type_not_selected,bynk.consumes.capability_not_selected,bynk.consumes.unit_not_consumed`. Measured on throwaway clones with that command: github-hooks 1,331 warnings in 60 files fixed by 140 edits, with `bynk check` clean and 505 tests passing afterwards; shop 17 in 5 files; showcase 65 in 11 files of one project (of 35); bynk-guide 107 in 29 files of 16 projects (of 45); architecture-that-compiles none. This repository's fixtures, examples and Book pages are migrated. The error stage carries the `breaking:` line and the Upgrading entry, with that command as its one-line fix.

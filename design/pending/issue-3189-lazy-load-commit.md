## ADR: lazy-load-and-commit
title: loadState attaches storage-backed collection handles to a current per-entry record, and commitState flushes what they staged
summary: A current-version per-entry agent record is read lazily (its Cells at once, each collection entry, posting, key range or page when a handler asks), a handler's writes stage in one overlay that commits with the record in one transaction, and a wholesale record, a record a migration step covers, and a held map keep the whole-record read

**Context.** The writer (#3263) already stores each entry and posting under its own key and commits only what changed, but `loadState` listed and joined every key into a wholesale-shaped record, so a handler's read cost, and its commit's CPU, grew with the size of every collection. The in-memory handles (#3254), the awaited lowering (#3296) and the storage-backed handles (#3295) made the swap possible without another lowering change. This is the swap (Decision F of #3189).

**Decision.**
1. *When it applies.* `loadState` reads lazily when the stored record carries `__layout: 2`, no migration step covers its stored `__v`, and the agent has a `Map`, `Set`, `Cache` or `Log` and no held `Map` (a held map keeps live connection ids inline in the record). Anything else reads whole, exactly as before: a wholesale (layout 1) record is read eagerly and split by its first commit, a record a migration step covers is joined, migrated and decoded as it always was, and a held map keeps its record. The agent's history driver (the `History[...]` property runner) also reads whole.
2. *Load.* A lazy `readStored` returns the Cell fields only (no listing). `__attachLazy` replaces the merged state's zero in-memory collection fields with `LazyStoreMap`/`Set`/`Cache`/`Log` handles over one `EntryOverlay`; an `@indexed` map keeps the indexers its zero handle was built with. The emitted per-agent spec `__lazyFieldsOf<Agent>` carries each field's decode (the boundary deserialiser, the same one the whole-record gate ran) and encode.
3. *Commit.* `commitStored` finds the handler's lazy context, reaps expired `Cache` entries (at most 64 per commit, the noted clock, oldest expiry first; `LazyStoreCache.reap` reads them from the `x/` range), stages each handle's `c/<field>` metadata by delta, and flushes the overlay together with the `"state"` record in one transaction. A handler that faults never reaches the commit, so nothing it staged is written. The wire encoders (`__wireMap`, `__wireSet`, `__wireLog`, `__wirePostings`) answer an empty placeholder for a storage-backed handle and the lazy commit drops those slots from the record.
4. *Per-key read-modify-write.* The handles gain `modify(key, f)`, which reads the entry, applies `f` to it (and to whether it was present) and writes the result as one step per key; a storage-backed handle runs the steps of one key one after another (a per-key promise chain), so `Map.update`/`upsert` and `Cache.update`/`upsert` cannot lose an update to a concurrent branch on the same key, and `put`, `remove`, `Set.add` and `remove` cannot double-count a key. Steps on different keys do not wait for each other, and a `Log` serialises `append` and `prune`. The in-memory handle's `modify` is one synchronous step. The lowering calls `modify` for those four ops (so on an in-memory handle each is atomic exactly as before).
5. *Decoding moves to the entry.* The rehydration gate decoded every collection value at load; a lazy read decodes an entry when it is first read, so a stored value that no longer decodes faults with `RehydrationViolation` when a handler first touches it, not on every call. A handler that never touches a corrupt entry no longer faults. A refined textual `Map` key or `Set` element is checked on every path that produces it from storage (a `Map` scan, `keys`, `entries`, `values`, an `@indexed` lookup's primary keys, a `Set` scan), through the same boundary deserialiser, and a failure raises the same `RehydrationViolation`; a key the program supplies is typed and is not checked. This keeps the type guarantee the whole-record gate gave (a value typed as a refined key has passed its refinement) and the principle that an entry is decoded and checked when it is touched. A test pins the eager and the lazy path faulting alike on a stored key that fails `NonEmpty`. A `Cache` key is not checked on either path: the whole-record gate only ever decoded a cache's values, so the lazy path keeps that (and the language has no scan over a cache's keys).
6. *Counts.* A keyed read of a 1000-entry `Map` reads the entry and the record (no listing); a keyed update reads a few keys; an `@indexed` lookup reads its posting prefix and the matched entries, in insertion order. The behavioural fixture asserts this at N=1000 on the emitted agent.

**Consequences.** Observable changes: (a) the corrupt-entry fault is per touched entry, not per call (accepted on #3195); (b) a refined textual key is checked when a scan produces it, not at load; (c) a store `Query` over a collection still materialises it (paged), so scans, joins and group-bys stay O(N), as before, but are read in pages instead of one listing. Two branches of one `par`/`parTraverse` that read and write the same key in separate statements (`get` then `put`) still lose an update, over in-memory handles as on main, and now also over storage-backed ones (tracked in #3297); single-call operations are atomic per key. Hover, completion, semantic tokens and signature help are unchanged: no syntax, name or signature changes. A rolled-back build reads the same stored bytes (`__layout: 2`, `m/ s/ l/ i/ x/ c/`), so no layout version changes.

**Writes and concurrency (#3298).** A store write is not a bare in-memory stage over a storage-backed handle: `update`/`upsert`/`put` first read the entry's old value (to keep its insertion sequence, unindex its old posting and keep the count), one awaited storage read per entry, and then stage the write in the overlay, which is flushed once, in one transaction, at commit. A `forEach` of N `update`s therefore does N sequential reads where a concurrent form would issue them together, and writes no more than the commit does either way (101 reads and one 100-key transaction for N=100, measured on the in-memory storage; the read is made once per entry). So moving a write from a `parTraverse` closure to `forEach` loses concurrency of those reads, not of the writes.

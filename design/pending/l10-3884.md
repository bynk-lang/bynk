## ADR: email-subaddress-dispatch
title: A plus-addressed recipient is dispatched exact, then base address, then catch-all, and the tag is readable
summary: How `user+tag@domain` finds its service, what `InboundEmail.subaddress` holds, and why a tagged claim stays legal

**Context.** Email Routing supports subaddressing (RFC 5233): once it is enabled for a domain, mail to `user+detail@example.com` is matched by the rule for `user@example.com`, and the `+detail` part stays in `message.to`. Bynk's dispatch compared the whole recipient exactly, so `support+1234@shop.example`, which Cloudflare had already routed to the `support@` Worker, matched no service and was rejected `recipient not accepted`, unless a catch-all happened to take it. Dispatch is generated runtime code that an author cannot change, so this was a bug whenever subaddressing was on (#3884).

**Decision.** (A) The order is an exact claim on the recipient, then a claim on its base address, then the domain's catch-all, which matches Cloudflare's own precedence. The base address is the local part up to the first `+`, as RFC 5233 and Cloudflare define it; a local part that starts with `+` has no base. Case is ignored, as before. (B) `InboundEmail` gains `subaddress: Option[String] = None`: the text after the first `+` of the envelope recipient's local part, with the sender's case, and `None` without one. `to` keeps the full recipient. A case sets it directly or leaves it to default, so existing tests compile; at the `system` tier the case posts `to` through the Worker's entry, which reads the tag from it. (C) Claiming a tagged address stays legal: `from email("support+vip@shop.example")` is an exact claim and wins over `support@`, and the duplicate-address rule compares full addresses, as today, so the checker is unchanged. (D) Dispatch does not depend on whether subaddressing is enabled: if it is off, Cloudflare never routes a tagged recipient to the Worker, so the extra step never runs.

**Consequences.** A project that relied on a catch-all to receive tagged mail now has it taken by the base address's service, as Cloudflare's own rule order does; the changelog says so. A `+` a sender uses as an ordinary character in a local part is indistinguishable from a tag by definition, which is RFC 5233's convention and how Cloudflare applies it. The change is in the runtime's `pickRoute` and `parseInbound` and the std type, so the grammar, the checker and the emitter are unchanged apart from the regenerated runtime bundle and the std snapshots.

## ADR: hyperdrive-h2-deploy-and-dev
title: Hyperdrive H2 provisions a Postgres instance's config from an environment variable, and wires `bynk dev`
summary: Where the connection string comes from, how a deploy makes, syncs, adopts and prunes the config, and what keeps the string out of every file and message

**Context.** After H1 a `Postgres` instance bound `HYPERDRIVE_<NAME>` with a placeholder `id` and no way to make the Hyperdrive config except by hand (`wrangler hyperdrive create`, then pasting the id). ADR 0799 H settled that the connection string comes from an environment variable `bynk.toml` names and is never written to disk. Proposal #3319 (part of #3184), decisions A to C, accepted as recommended.

**Decision.**

- **`bynk.toml` names a variable, never a string.** `[deploy.hyperdrive.<Capability>] connection_env = "MAIN_DATABASE_URL"` and `[dev.hyperdrive.<Capability>] connection_env = "MAIN_LOCAL_DATABASE_URL"`. The key is the capability's name; the binding is derived from it as the instance's is (`Main` is `HYPERDRIVE_MAIN`). A value that is not an environment variable's name (a connection string pasted in) is refused with a message that does not repeat it. `[deploy]` was a planned table (#551) and is now this slice of it; `[dev]` is new.
- **Deploy makes the config through the account's `hyperdrive/configs` API**, which takes the origin as parts (`scheme`, `host`, `port`, `database`, `user`, `password`), not as a string, so deploy reads `postgres://user:password@host:port/database` into them (percent-decoded; the port defaults to 5432; a query string is ignored, since Hyperdrive makes its own TLS choices). It posts on create and puts on a change, then records the id in the ledger keyed by (environment, Worker, capability) and writes it into the `[[hyperdrive]]` stanza, which a named environment's block copies. The config is named `<worker>-<capability>`, environment-qualified as every other derived name is. It needs `CLOUDFLARE_API_TOKEN` with `Hyperdrive: Edit` and `CLOUDFLARE_ACCOUNT_ID`, as the Secrets Store link does; a project without `Postgres` needs neither.
- **A) A per-environment `config_id` adopts an existing config.** `config_id = { production = "…" }` in the same entry; that environment needs no connection string. An adopted config is looked up (a missing one fails the deploy), recorded as adopted, and never updated or deleted. CI cannot make a config (its id would be lost if the ledger is not committed), so CI refuses a create and names `config_id` as the way out, as it does for a KV namespace.
- **B) A missing variable fails the deploy**, `--dry-run` included, before the plan, naming the variable and the capability. Every problem of a run is reported, not the first. An unreadable string names the variable and the part that is wrong, never the value.
- **C) A deploy syncs the config from the variable every time, and the string is never printed.** The ledger records only the config's id and name, and nothing derived from the string: the ledger is committed, so even a truncated, salted digest of a weak password would leak it to offline guessing. Since a change cannot be detected without one, `connection_env` configs are updated (a `PUT`, idempotent, keeping the id) on every deploy, and the plan shows the config as synced from the variable, naming the variable and never the value. With `config_id` nothing is synced.
- **A renamed capability plans a create and an orphan** (standard-library D3): the new binding makes a new config and the old is reported, and `--prune` deletes it, since a Hyperdrive config holds no data. An adopted config is only ever reported. A binding that changes from made to adopted orphans the config it made.
- **`bynk dev` reads `[dev.hyperdrive.<Capability>] connection_env`** and sets `CLOUDFLARE_HYPERDRIVE_LOCAL_CONNECTION_STRING_<BINDING>` on that Worker's `wrangler dev` and nothing else. A configured variable that is not set stops `bynk dev` naming both; a binding with no entry is left to the variable already in the environment, with a warning when neither is there; `--remote` uses the account's config and sets nothing.
- **R-16: the string reaches nothing else.** It is read from the environment, parsed, and sent to Cloudflare over TLS. The ledger holds an id and a name. The plan, its JSON, `wrangler.toml`, every file under the build directory, every error and the output of every test are checked for it. Its carriers (`Secret`, `Origin`, the local string) print as `<redacted>` under `Debug`, every message is built from names, and what Cloudflare answers is scrubbed of the string and its password before it is shown.
- **A workerd smoke over a real Postgres** (`binding_workerd.rs`, gated on a server being installed, `BYNK_REQUIRE_POSTGRES` to require one) runs `all`, `first` and `run` through `wrangler dev` with the local string in the environment, on the emitted compatibility date, and so confirms postgres.js's `node:*` imports resolve under it. It takes ports the operating system says are free, since every band below 65 536 is taken.

**Consequences.** A `Postgres` instance deploys and runs locally with no manual step. Two things the smoke showed, left to H3 as the owner of the `Postgres` surface: a connection failure under local Hyperdrive (an unreachable port, an unresolvable host) arrives with no driver `code`, so it is `PgFailed` with an empty SQLSTATE and the fixed message `connection attempt failed`, not `PgConnection`, and carries no host, user or password, so `redactSecret` needs no host stripping for those two; and a `PgJson` parameter cast `$n::jsonb` is stored as a JSON string, not parsed, because postgres.js serialises a `jsonb` parameter itself and the runtime passes it already-encoded text.

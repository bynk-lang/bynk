## ADR: websocket-address-at-system
title: A `system` case drives a WebSocket service through a real upgrade
summary: `open`, `message` and `close` run at `system` as a real upgrade, client frames and close against the participant's Worker and Durable Object, with the principal's credential offered as a browser offers it, a refusal read with `tc.refusedWith()` (refused below `system`), and the in-process-only rule retired

**Context.** #3051 let a case drive a `from websocket` service by address against a recording `TestConnection`, at `unit` and `integration`, and refused it at `system` (`bynk.test.ws_needs_in_process`): a deployed WebSocket is a real upgrade through the Worker and a Durable Object, which the `system` driver did not drive. So the handshake, the Worker-side authentication, the routing to the object, the socket's attachment and the frame decoding on the platform's path were never tested end to end, and the broken Bearer handshake of #3900 was exactly the kind of fault that let through. Promoting a case to `system` should keep its meaning (ADR 0522's principle for cron and queue); only the test driver can open a socket to the Worker it stood up (#3901).

**Decision A — `open` performs a real upgrade.** In a `system` suite the driver sends what a browser would to the participant Worker's own `fetch`: the route values in the upgrade URL's query string, `Upgrade: websocket`, and the actor's credential as `Sec-WebSocket-Protocol: bynk.bearer, <token>`, where `by A(…)` mints the token as the HTTP `system` driver does (signed with the actor's secret, carrying its declared `iss` and `aud`). The Worker's seam, the object's routing and the socket's attachment are the real ones. The Worker's `101` carries the client end of an in-process pair; the platform pieces Node lacks (the `WebSocketPair` global, a `101` `Response`, a Durable Object that accepts sockets for hibernation and delivers their frames and closes to `webSocketMessage` and `webSocketClose`) are test doubles in the test runtime, installed only by a test build and held out of every deployed Worker by a guard. A `Bearer` actor and a public service are driven; an actor the driver cannot yet present (`Oidc`, `SignedCookie`, an actor sum) fails the case at `open` with a message saying so, never an upgrade the Worker would refuse for the wrong reason. No real socket is opened, so no port is needed and a case runs in the same process as the others.

**Decision B — `tc.sent()` is the frames the server wrote, decoded as `out`.** The client end reads each server frame through the `out` type's codec (a `Bytes` service reads binary messages) and records it on the case's `TestConnection`, so a frame the server's own type would refuse fails the case. The server's frames arrive asynchronously, so each address waits until the exchange has gone quiet before it returns (every delivery and the work a handler awaited is handled and nothing new has started for a whole turn of the event loop), bounded, and reaching the bound is an error naming the cause, never a quiet return. A case asserts on whole frame lists, not timing. An error a handler throws is kept and fails the case with its message. The wait is on the event loop, not on the harness's virtual time, which these addresses do not use.

**Decision C — `svc.close(tc)` sends a client close frame, and the case awaits `on close`.** The close reaches the object's `webSocketClose` with `CloseInfo { code: 1000, reason: "", clean: true }` (or the `info` the case names, a code a page's own `close` could not send included, as a browser closing its page does), and the case does not continue until `on close` has finished, so a following address sees its effects. The client going away does not set `closed()`, as at `unit`.

**Decision D — failure principals apply, and a refusal is read with `tc.refusedWith()`.** `by Nobody` offers no credential, `by Forged` signs with the wrong key, `by Expired` presents an expired token, and `by WrongIssuer` and `by WrongAudience` present a token for another party, as for an HTTP route; the Worker answers each at the upgrade and no connection exists. The issue asked that a case assert these on the address's outcome, but an upgrade's outcome is the handler's `Effect[()]`, and typing it differently at one tier would change what the same source means at another, so the status is read from the connection instead: `tc.refusedWith()` is an `Option[Int]`, the status the Worker answered with, `None` when the upgrade was accepted. Below `system` there is no upgrade to refuse, so the read would be `None` whatever the case did, and `expect tc.refusedWith() == Some(401)` would fail misleadingly and `== None` would pass vacuously; it is refused there at check time (`bynk.test.ws_refusal_needs_system`) rather than answered. A `message` or `close` on a refused connection fails the case, naming the status. Each failure principal is answered `401`. The old single-element form's `400` and a malformed token are not principals a case can act as, so they stay pinned by the handshake's own tests (#3900) and a browser case; the `403` of a refinement actor whose claim a token lacks needs the claims a case presents, which this driver does not carry yet, and is the follow-up with the other actors.

**Decision E — `bynk.test.ws_needs_in_process` is retired.** The address works at every tier, and the code, which is now never raised, is a tombstone. A target whose only service is `from websocket` now has a serialisation edge, so `suite … as system` for it no longer needs another service (`bynk.tier.system_needs_wire`).

**Consequences.** A `system` case exercises the whole upgrade path of a WebSocket service, and the chat-room scenario of the reference runs unchanged at `unit`, `integration` and `system`. The Bearer refusals are pinned by cases and by a mutation test that turns each check of the emitted verifier off and expects exactly the case that relies on it to fail, so `refusedWith() == Some(401)` is read from the Worker's seam and not assumed. A real Chromium against the deployed Worker on workerd, extending the #3906 harness, connects a `Bearer` service with `["bynk.bearer", token]` and shows the `101` selects `bynk.bearer` and nothing else (the token is never echoed in a response header), and that the old `[token]` form, a forged token and no credential never open in a browser; this is the #3900 proof the in-process driver cannot give, since a browser's rules are not Node's. Driving `Oidc`, `SignedCookie` and sum actors at `system` is the follow-up; each is a credential to present, not a change of mechanism.

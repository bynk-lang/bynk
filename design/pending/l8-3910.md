## ADR: typed-path-parameters
title: Path parameters take the typed-query scalar set, decoded after matching
summary: A path parameter is a String, Int, Bool, Decimal, enum, or a refinement or opaque type over one; matching stays structural and decoding follows

**Context.** A path parameter had to be a `String` or a refined or opaque type over `String`, while a typed `query` field, a `cookies` field and a `@form` field also take `Int`, `Bool`, `Decimal` and enums. So `GET /orders/:id` with `id: OrderNo` (`type OrderNo = Int where Positive`) could not be written: the handler took a `String` and parsed it by hand, outside the boundary's validation.

**Decision.** (A) A path parameter accepts the typed `query` field set minus `Option` and `List`, since a segment is always present and single-valued; anything else stays `bynk.http.path_param_not_stringy`, reworded to list what is accepted. (B) Matching stays structural: a route matches on segment count and literals alone, then each parameter is decoded. `/orders/abc` against `id: OrderNo` is a `400 StructuralMismatch`, not a fall-through to another route and not a `404`, and a refinement failure (`/orders/0`) is a `400 RefinementViolation`. Type-directed routing (`/orders/:id` with `Int` beside `/orders/:slug` with `String`) was rejected: it would make the matcher depend on parsing and collide with the route-order rule. A typed parameter is therefore still a `:param` segment for #3909's ordering and for `bynk.http.unreachable_route`; in that example the one spelt later is unreachable. (C) Decoding follows `query`: the same `Int` and `Decimal` grammar, enums by case-sensitive variant name, `Bool` as `true`/`false` only. The router reads the segment with the runtime's `pathLeaf` (the typed-`query` leaf rules) and the type's own codec checks it. (D) `bynk client` takes the typed value and writes it as the segment (`String(n)`, the variant name); `bynk openapi` gives the parameter its type, `format` and bounds, and an enum a string enumeration of its names; the system-tier driver writes an enum parameter as its variant's name; hover on a path parameter's declaration names how it is decoded and the `400`s it can answer.

**Consequences.** The `400`s name `path.<name>`, the path HTTP routes already used for a refinement failure (the issue wrote `param.<name>`, the WebSocket upgrade's spelling), so no existing client of that body changes. A `String`-based parameter is decoded as before and its emitted entry is unchanged. A program that took a `String` and parsed it by hand keeps working. The `on open` parameters of a WebSocket service keep the `String`-constructible rule, since an upgrade carries them in a query string with no segment to match.

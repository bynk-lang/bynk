## ADR: lazy-storage-handles
title: Storage-backed collection handles read per entry and stage their writes
summary: LazyStoreMap, LazyStoreCache, LazyStoreSet and LazyStoreLog implement the in-memory handle interfaces over the layout-2 keys, with insertion-order, indexed and key-range reads, and a Log skew field so windows stay correct

**Context.** The per-entry layout (ADR 0785) already writes only the entries a handler changes, but `loadState` still lists every key and the handles are in-memory (#3254), so a handler's reads and its commit work still grow with the size of the state. Decision F of #3189 says a keyed read fetches one entry, an indexed read fetches the matched postings and entries, and a `Log` window is a key range. The in-memory handles' methods return `Awaitable` precisely so a storage-backed handle can replace them.

**Decision.** `bynk-emit/runtime/src/lazy.ts` adds `LazyStoreMap`, `LazyStoreCache`, `LazyStoreSet` and `LazyStoreLog`, each implementing the corresponding handle interface from `store.ts` over an `EntryOverlay`, so a handler reads its own writes and nothing reaches storage until one transaction. A keyed `get`/`has`/`put`/`remove` reads one key; `size()` reads the collection's `c/<field>` record; an `@indexed` lookup lists the posting prefix and reads the matched entries in batches, sorted by insertion sequence; a scan lists the collection in pages; `Cache.liveSize` and reaping read only the `x/` expiry range; a `Log` window lists a key range, `recent(n)` a reversed list with a limit. Entries are decoded when they are read, so a stored value that fails to decode faults when a handler first reads it. Each handler stages its collection's metadata with `finish()`.
No stored byte format changes: the keys and value shapes are those of ADR 0785. One field is added to `c/<field>`: `skew`, the most a `Log` key's time is above its entry's `t` (the key time never goes backwards, so an entry appended with an earlier `t` is keyed later than its time). A window read widens its key range by it. Absent means 0, so a record written before this field existed reads as no skew, and the eager commit now writes it too. The insertion sequence a key is given may differ between the eager commit and a handle (an entry added and removed in one handler consumes a sequence in the handle and not in the commit); only the order is frozen, and each writer keeps the collection's next-sequence counter above every sequence it holds.

**Consequences.** Nothing calls these handles yet, so no behaviour changes in this increment. They are tested against the in-memory handles: random handlers through both produce the same reads and the same stored state (up to the numbering above), and a one-entry put, a keyed get and an indexed read touch a bounded number of keys at 10 and 1 000 entries. A later increment makes `loadState` build them for current-version records and the lowering await them. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

## ADR: container-instance-key
title: A Container instance can type its names with @instances(by: K)
summary: Why the key is an option of the instance that re-types the operations, and what makes a type a valid key

**Context.** `Container.send(instance: String, req)` starts one container per distinct name. The warning for a name taken from request input (`bynk.container.unbounded_instances`) says what is wrong but leaves an author with only an authenticated actor, a constant or a closed set to satisfy it. A type that bounds the names is the most direct way to say which names exist.

**Decision.** (A) `@instances(by: K)` is an option of a `Container` instance, written with the label `by:` and the name of a type: `capability Renderer = Container @build("…") @port(8080) @instances(by: TenantId)`. (B) `K` is a type declared in the context: a refined type with a refinement, or an opaque type, over `String`. A plain alias of `String` adds no check, so it is refused, as is any other type or a name that is not declared (`bynk.capability.invalid_option`), and the option written without `by:`. (C) With it, `send`, `receiveBytes` and `sendBytes` take a `K` in place of the `String` first parameter, in the instance's own operation signatures, so a bare `String` is an ordinary type error at the call and `send`'s signature help and hover show `K`. Without it the operations take a `String`, as before. (D) The key's string form is the instance's name, so the limits on a name still apply to it (1 to 256 bytes, no control character). (E) A keyed instance is not warned about, as the accepted proposal (#4112, decision A) specifies: the key's construction (`.of`, an opaque constructor) is where the author bounds the names. This is weaker than the warning on a `String` name, and the weakness is stated rather than hidden: a refined type limits a name's shape and not how many there are, so a keyed instance on a route anyone can call, with a path parameter decoded straight into the key, is not warned about although it is as unbounded in count as the `String` case. The check does not verify the claim that the key bounds the names. The docs and the guide therefore pair a key with an authenticated actor, a `RateLimit` or a closed set (a `match` over an enum that builds the key), and the fixtures serve keyed routes `by` an authenticated actor. A stricter rule (keep following a key-typed handler input into the name on an open route, and skip only a name built by a function) is a possible follow-up, at the cost of warning on every typed path parameter.

**Consequences.** Additive: an instance without the option is unchanged. The option is a type name in an annotation, a new kind of option value beside literals; a constant of that name is not resolved. Hover and completion read the option from the capability option table, so `@instances` is offered on a `Container`, and the instance's operations carry `K` where they carried `String`.

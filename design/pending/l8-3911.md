## ADR: typed-headers-record
title: A typed headers record, decoded and validated at the boundary
summary: headers: T takes the query and cookies field rules, with case-insensitive names and comma-list splitting, through one reusable decoder

**Context.** `query` and `cookies` each have a typed record form, decoded and validated with a `400` before the handler runs, beside a raw view. `headers` had only the raw `RequestHeaders`, so every handler that reads `Idempotency-Key`, `If-Match`, `X-Request-Id` or `Content-Length` called `get` and parsed by hand, outside the boundary's validation.

**Decision.** (A) `headers: T`, where `T` is a record, follows the typed `query` and `cookies` field rules (`bynk.http.headers_field_not_stringy` for a field that cannot be read from one value); a field's name, or its `@name`, is the header name, compared without case, and `@name` must be an RFC 9110 token. A failure is a `400` naming `headers.<field>`. (B) A `List` field splits the combined value at commas outside quoted strings (RFC 9110 §5.6.1), where repeated header lines are already one combined value as HTTP specifies. A non-`List` field reads the combined value whole, trimmed, and is not refused when it has several values: the platform's `Headers` joins repeated lines with `, `, so a repeated line cannot be told from a comma inside one value, and refusing commas would refuse `Date` and `User-Agent`. A field that must be a single value uses a refinement. This departs from the issue's wording, which would have refused a non-`List` field whose header arrives as several values. (C) Values are trimmed and not otherwise decoded: no percent-decoding, as for cookies. (D) `RequestHeaders` stays as the raw view; a handler has one `headers` parameter, of either type, so a handler that must enumerate or forward every header keeps using it. (E) The "header text to typed value" step is defined once, in the runtime's `headersObject` (with `splitHeaderList`) and the checker's field rules, so a later reader of request facts on an actor (#918's envelope) or of typed headers elsewhere reuses it rather than adding a second decoder. (F) Typed headers are decoded after the actor's check, like other inputs, and are not part of authentication: the reference says so and points to actors. A credential header the route's seam consumed reads as absent here, as in `RequestHeaders`.

**Consequences.** `bynk client` sends the fields as request headers (a value with a control character is refused before sending); `bynk openapi` describes them as `in: header` parameters; a test passes a `T` value, which a `system` case sends as headers under each field's `@name`, and a `Wire` argument carries header text to probe the decoding. A record that is a `headers` parameter may carry `@name` fields (`bynk.types.field_name_record_not_boundary` allows it as for `cookies`), and a record with a `@name` field of two names that differ only in case is refused. A route with a typed `headers` takes no trailing `RequestHeaders` test argument, since the record is the case's headers. Hover on the parameter lists the headers it reads, and completion offers common header names inside `@name("…")` on a `headers` record. No existing program changes behaviour: `headers: RequestHeaders` is untouched.

## ADR: cors-origins-in-serialised-form
title: A `cors` origin is refused unless it is in the serialised form a browser sends
summary: `bynk.http.cors_invalid_origins` also checks each literal `origins` entry against `scheme://host[:port]` (lower case, no path, query, fragment or trailing slash, no default port) and suggests the corrected form; `"null"` beside `credentials: true` is refused as the wildcard is; an `env(…)` constant is checked as the value of the environment being built

**Context.** The router compares a request's `Origin` with each `origins` entry exactly, and a `SignedCookie` WebSocket upgrade does the same (#4501). A browser sends an origin only as `scheme://host[:port]`, the scheme and host in lower case, no path, query, fragment or trailing slash, and no port that is the scheme's default. An entry in another shape matches nothing, and nothing said so: every cross-origin request from that site was refused, and every cookie WebSocket upgrade got a `403`. The check only required a non-empty list of string literals or constants (#4504).

**Decision.** `bynk.http.cors_invalid_origins` is extended rather than given a new code: its rule already is "`origins` holds exact origins", and the shape of an entry is the same rule one level down, so its explanation stays one coherent statement. Each literal entry other than `"*"` and `"null"` is read by `bynk-check/src/cors_origin.rs`; one that is not an origin a browser sends is refused at the entry with the first fault in reading order (no scheme, upper-case scheme or host, trailing slash, path, query, fragment, user information, a wildcard or non-ASCII host, a default port written out, an empty or malformed entry) and, where the repair needs no guess, the form to write (`write "https://app.example.com"`). An entry with no repair that is honest (a wildcard subdomain, which `*` cannot mean because the comparison is exact, a non-ASCII host, whose punycode form is not computed here) gets the rule only. A missing scheme is repaired as `https` and the note says the scheme is the one the site is served on. `"*"` is unchanged. A non-default port is part of the origin (`http://localhost:8787` builds), and schemes a browser sends for a shell around a page (`capacitor://localhost`) build.

`"null"` is the `Origin` a browser sends from a sandboxed frame or a `data:` page, which any other site can create. It is an origin a browser sends, so the shape check accepts it, and without credentials it is compared like any other entry. Beside `credentials: true` it would let any page act with the visitor's cookies, so it is refused with `bynk.http.cors_wildcard_credentials`, extended with its own message, as the wildcard is. The WebSocket cookie upgrade already refuses `null` (#4501), so the two rules agree.

An `env(…)` constant needs no mechanism of its own. `env_consts::resolve` rewrites each such constant to the literal `bynk.toml` gives it for the environment being built, right after parsing, in the build, the deploy and the editor alike, and the `cors` pass substitutes constants into `origins` before the policy is validated. So the shape check reads the value the environment being built would deploy: a bad value for `staging` is refused when `staging` is built (`bynk build --env staging`, `bynk deploy --env staging`), not before, and the default environment with a good value still builds. The error lands on the constant's use in the `cors` block and shows the value; it cannot name the constant, since the rewrite keeps the span, not the name.

**Rejected.** A new code, `bynk.http.cors_origin_shape`: a second code for what a reader sees as one rule, and one more entry for every surface that lists codes, for nothing the extended explanation does not say. Normalising an origin instead of refusing it (lower-casing, trimming a trailing slash): the compiler would then accept a policy that does not say what it means, and the author would keep writing entries the WebSocket and `Origin` comparison cannot match. A quick-fix code action: left out of this change; the corrected form is in the note. Refusing `"null"` outright: it is an origin a browser does send, and an author who wants a sandboxed page to read a public, uncredentialed resource has no other way to say so.

**Consequences.** A source that listed an entry in a bad shape stops compiling, and the error says what to write; see `breaking`. A policy that built and matched nothing is now an error at the entry. The `cors` explanation and the HTTP reference say origins are compared exactly, in serialised form, with the refused shapes in a table; the WebSocket cookie documentation says the same once #4501 lands.

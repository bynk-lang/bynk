## ADR: edge-keys-rotate-through-two-slots
title: A rotation puts the new edge key in a second slot and retires the old one by an instant the runtime checks
summary: Two slots, a retirement marker, the consumer written before the producer, expiry enforced at admit time, a revoke flag

**Context.** #4526 (found settling #3898): a `Producer` refinement admits Bynk contexts by their edge key, and `queueForeignKeys` returned only the current one. `bynk deploy` mints a fresh edge key on `--force`, or when a Worker is redeployed after it was deleted, and kept nothing, so a message signed under the old key and still in the queue was refused as `bad_signature` and acknowledged away: silent loss. #3899 Decision H promised the previous key for the retention window, and held only for `Foreign` actors. The issue's text says the deploy records the previous *value*, but Cloudflare never returns a secret's value, so a re-mint cannot copy the old key anywhere, and the committed ledger cannot hold it (ADR 0195 D1).

**Decision.** (A) The consumer holds an edge's key in one of two slots, `BYNK_CALL_FROM_<S>` and `BYNK_CALL_FROM2_<S>`. A rotation puts the new key in the slot the live one is not in and leaves the old one untouched, so no value is ever read back. (B) The old slot is marked retiring by a secret, `BYNK_CALL_UNTIL_<S>` or `BYNK_CALL_UNTIL2_<S>`, holding the instant (whole seconds since the epoch) after which it is refused. It is a secret so it survives later deploys, which rewrite plain variables from the generated config; it is not sensitive. (C) The runtime (`edgeVerifyKeysOf`) reads that instant when it verifies, for calls (`verifyCall`) and queue messages alike, so a retired key stops working on time even if no deploy ever runs: the deploy's cleanup, which deletes the old slot and its marker once the ledger says the instant has passed, is tidiness, not security. A marker that is not a plain whole number refuses its slot (fail closed). The old key is marked retiring before the new key is put, so a failure between the two leaves one retiring key and no live one, which the next plain deploy finds (`needs_repair`) and finishes by putting the new key in the free slot, never two live keys no one could tell apart. (D) Order: the consumer is uploaded before its producer, so its new slot is put before the producer's `BYNK_CALL_TO_<T>` takes the new key, and no message is ever signed under a key the consumer cannot verify. A rotation needs both Workers in the run (as `--force` already did), so two deploys with the producer first cannot occur. (E) The window is 15 days (`EDGE_KEY_GRACE_SECONDS`): a queued message waits at most 14 days of retention and is verified when it is delivered, not when it was signed, so the old key must outlive that by the retry margin; it matches the `Foreign` behaviour. (F) `--revoke-previous-edge-key <context>` (repeatable; chosen over `--rotate-edge-key <context> --no-grace` because it names what it does, and it cannot be given without an edge to revoke) re-keys every edge on that context with no grace: the new key goes in the live slot and the other slot and every marker are deleted, and a failed delete stops the deploy. A revoke that would not apply (a `--context` run without both ends) is refused, not ignored, since a quiet no-op would leave a leaked key working. The plan output names the mode: each rotation prints the window and the date, or says the key was revoked, and the guide says to revoke after a suspected leak. (G) The ledger records, per callee Worker and edge, the slot retiring and its instant (`retiring_edge_keys`, on the environment, not on the Worker's record, which every push rebuilds): a slot number and a time, never a key. (H) A rotation is planned only from a state it can reason about; otherwise the edge is left as it is and a warning says why (`SlotRefusal`): the callee's listing could not be read (which slot is live is not known, so nothing is written blind), the previous rotation is still inside its window (both slots hold a key, one retiring: replacing either could overwrite the key a producer signs with), or the slots are in a state no rotation leaves. A revoke in any of these is an error, not a no-op. (I) The callee counts as holding an edge's key when either slot does, per name, so a cleanup that deleted the first slot does not read as an absent key (which would re-key the edge, and refuse a `--context` run, every other cycle). (J) The ledger forgets a retiring slot only once its deletes succeeded; one whose delete failed stays, and the next deploy tries it again. A rotation's own deletes (a stray marker, a revoke's old key) stop the deploy when one fails, and the message names the rerun.

**Consequences.** A `--force` rotation or a Worker redeployed after deletion no longer loses queued `Producer` messages signed before it, and no longer refuses a call signed under the old key during a rolling deploy. The old key is accepted for 15 days, which is the cost; a leaked key is dropped with `--revoke-previous-edge-key`. `breaking`: none: a project deployed before this has one live key in the first slot and no marker, which is the steady state. New secrets are managed by `deploy` (`is_edge_key` names them, so a user cannot supply them). Not changed: `Foreign` senders' `<SECRET>_PREVIOUS`, which the operator sets; the derived-epoch scheme (one root per edge plus an epoch counter), which would change the key scheme of every deployed edge.

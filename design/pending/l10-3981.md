## ADR: expect-is-bindings
title: A statement-form expect keeps the names its `is` binds
summary: Scope, emission and exclusions of `expect v is P(x)` bindings after the statement

**Context.** A failed `expect` ends the case, so after `expect r is Ok(n)` the case knows `r` is `Ok`, but `n` was unbound (`bynk.resolve.unknown_name`). Tests fell back to a `match … _ => expect false` staircase (#3981).

**Decision.** (A) The names a statement-form `expect … is P(x)` binds stay bound to the end of the enclosing block, with the type they have in an `if` body (the same shared rule, `narrowing::matched_is_tests`, so `&&` and parenthesised predicates bind and `||` and `!` do not). An `expect` used as an expression binds nothing beyond itself. (B) A `property` body binds nothing across claims: the checker's `CapabilityCtx::expect_is_bindings` is set for case and suite-helper bodies only. (C) A name that shadows an existing one gets the emitter's existing shadow rename, as a re-`let` does. (D) An or-pattern binds what every alternative binds. The emitter declares the bindings right after the failure guard, as an `if` declares them at the top of its then-branch.

**Consequences.** No grammar change. Hover and go-to-definition see the bound names as locals scoped from the statement to the end of the block; hover does not note that a name comes from an `expect`. No code action was added for rewriting a two-arm `match`.

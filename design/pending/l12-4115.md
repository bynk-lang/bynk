## ADR: fetch-set-cookies
title: A Fetch response carries every set-cookie value separately, because a joined header loses cookies
summary: Why set-cookie gets its own field on the response types, raw and ordered, with headers unchanged

**Context.** `Response.headers` joins a repeated header into one value with `", "`. `set-cookie` is the one header HTTP lets repeat with commas inside its values (RFC 6265 §3; RFC 9110 §5.3): a cookie's `Expires` attribute holds a comma, so a joined value cannot be split back into its cookies. A service that consumes or proxies a login flow could not read the cookies an upstream set, and the reference said so. The bindings see the values separately (`Headers.getSetCookie()` on Workers and Node) and dropped the distinction.

**Decision.** (A) `Response`, `BytesResponse` and `StreamResponse` each gain `setCookies: List[String]`: every `set-cookie` header value as received, in the order received, `[]` when there is none. `headers.get("set-cookie")` keeps today's joined value, for compatibility. (B) A value is the header text: this increment interprets nothing, and a `Cookie.parseSetCookie` may follow. (C) `setCookies` defaults to `[]`, so a Bynk `Response { … }` literal, and every `stub Fetch.send(_) returns Ok(Response { … })` in an existing test, still compiles. (D) Every binding that produces these types fills it: the Node and Workers `Fetch` bindings, which `Service`, `MtlsCertificate` and `Container` share; the browser binding withholds `Fetch`. A runtime without `getSetCookie()` yields the values as the Fetch standard does, one by one; one that already joined them leaves a single joined element, which the docs say.

**Consequences.** The addition is additive for Bynk programs; it changes what `Json.encode` writes for a response and what a hand-written TypeScript binding must return, so it is stated as `breaking`. It removes the "lossy" caveat from the reference.

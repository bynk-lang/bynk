## ADR: typed-capability-reads
title: A first-party capability operation may return its Codable parameter, decoded at the call site
summary: Lifts ADR 0696 decision 5 for the standard library's own operations, with the failure policy declared on each operation

**Context.** ADR 0696 decision 5 made a `Codable` type parameter in a capability operation's return type an error (`bynk.generics.codable_op_return`), because decoding a provider's reply raises what a failed decode of stored data means, which that slice did not answer. Writes worked (`Queue.sendValue[T: Codable]`); reads did not. The durable `Idempotency.dedup`/`remember` (#2840) needs one. The maintainer accepted #3458: the rule is general, the first-party providers are the only ones that may use it, and the failure policy is declared on each operation rather than inferred from its return shape.

**Decision.**
1. **The rule.** The `Effect[P]` payload `P` of a capability operation may mention one of the operation's `Codable` type parameters. The provider returns the boundary encoding of `P` as plain JSON, never a witness (the emit ABI of ADR 0310 does not grow, and no `__codec_` name appears in a capability interface). The call site decodes the reply whole, with the codec of the instantiated `P` (`__deserialise_P`, or a combinator over witnesses where `P` has a type variable), mirroring how arguments are encoded (ADR 0696 decision 4). The emitted interface returns `Promise<unknown>` for such an operation, and a type parameter that now occurs in no kept position is dropped from it. The instantiated `P` must be `Codable` (`bynk.types.not_codable`). A return-only parameter cannot be inferred from arguments, so the caller writes `Store.read[Receipt](key)`.
2. **First-party only.** "First-party" is the declaring unit: one under the reserved `bynk` root (`firstparty::is_first_party_unit`), which a user unit cannot be (`bynk.namespace.reserved`). A user-declared operation keeps an error with the new `bynk.generics.codable_op_return_not_first_party`, so decision 5 narrows rather than disappears. `bynk.generics.codable_op_return` is retired and removed from the registry and `bynk explain`. Opening it to user providers later only relaxes the rule, and wants a conformance story (a provider test kit) first.
3. **The failure policy is declared per operation.** A reply that does not decode is, by default, a **fault**: the effect rejects with `Cap.op returned a value that does not decode as P: at <path>: expected …`, naming the capability, operation, instantiated type and the `BoundaryError` path, never the value (it can be personal data). An operation may instead declare a **miss** with the internal annotation `@onUndecodable(miss)` after its return type: the call returns `None`, and a warning of the same text, prefixed `warning:`, goes to the runtime console channel (`console.warn`, not the user's `Logger`, since a handler need not hold one). `@onUndecodable(fault)` spells the default. A miss needs an `Effect[Option[..]]` return. Nothing is derived from the return shape: a future `Kv.get[T]` declares its own policy when built, and does not become a miss by being an `Option`.
4. **The annotation is internal.** It reuses the `@name(args)` annotation shape after a capability operation's return type (grammar, formatter and tree-sitter take one slot there), but it is not user-visible surface: the checker refuses any operation annotation outside a first-party unit, and a malformed one inside it, with `bynk.generics.internal_op_annotation`.
5. **`None`'s JSON encoding.** `Json.encode(None)` writes `{"kind":"None"}`, and the `Option` decoder accepts `null`, a missing value, `{"kind":"None"}`, `{"kind":"Some","value":…}` and a bare value. So a provider reports absence with `null` (or `{"kind":"None"}`), and a stored value that is not a `T` fails to decode as `Option[T]` rather than reading as `Some`.
6. **Test doubles keep the encoded form.** A double for a typed-read capability stores what the call site's encode gave it and returns it before the call-site decode, so a case runs the round trip production does: a value written as one type and read as another does not decode. `bynk.testing`, a new experimental first-party adapter (`[unstable] allow = ["bynk.testing"]`) with an in-memory `TypedReads` capability, is the proof: `read[T]` declares nothing (a fault), `readOpt[T]` declares a miss, and its binding is its own test double. It is the toolchain's test support, not language surface.

**Consequences.** The call-site rule, the runtime helper (`__bynkCapabilityReply`, in `codec.ts`), the interface change and the first-party refusal are in. Nothing in the standard library but `bynk.testing` uses typed reads yet. `Idempotency.dedup[T: Codable]` and `remember[T: Codable]`, with `dedup` declaring a miss and the durable D1 store, are #2840's work and land on this; its in-memory bindings and test double will store JSON in the same change. ADR 0696's decision 5 and its consequence "typed reads are follow-ups" are amended by this record, and standard-library D4's read-side condition (a second consumer) is met by #2840's `dedup`. ADR 0281's reaffirmation (a generic operation needs an external provider) stands. A miss metric is a follow-on.

## ADR: rate-limit-annotation-client-ip
title: A route's rate limit is asked before its body is read
summary: `@rateLimit(Limiter, key: clientIp)`, a `429` and `RateLimited`; `key: identity` waits for authentication ahead of the body read

**Context.** `RateLimit` is a capability a handler calls (`allow(key)`), so it runs after the body has been read, decoded and validated: an unauthenticated flood of large bodies costs the full read and parse before anything says no, and a limit keyed on the client's address is written by hand in every handler. Only the router acts before the body is read, as it does for the `413` and `415`.

**Decision.** [DECISION A] `@rateLimit(Limiter, key: clientIp)` names a `RateLimit` instance the route's context declares and counts by the request's `CF-Connecting-IP`. The router asks the limiter before every other step: ahead of the media-type check, the declared-length `413` and authentication, so a body over its cap still gets `429` while the limit is spent. `identity` (the verified caller) is part of the annotation's design and is refused with `bynk.http.rate_limit_key_unavailable` until the router authenticates before it reads the body (see the correction below); other keys are `bynk.http.rate_limit_bad_args`. [DECISION B] The answer is a router response: `429` with `Retry-After` set to the limiter's period in seconds and a `{ "kind": "RateLimited", "details": … }` body (problem details under `errors { format: problem }`), the new rejection `BoundaryRejection.RateLimited(detail)`, so `on rejected` renders it and a `system` test asserts `Rejected(RateLimited(_))`. It is told from a handler's `TooManyRequests` (whose body is `{ error }`) by its `kind`, as the `413` is. The addition to a closed sum is breaking, as ADR 0586's was. [DECISION C] The limiter is a named instance the route's context declares, with no `given` on the handler; at most one `@rateLimit` per route; a shared limiter counts across every route that names it, by key. [DECISION D] Experimental as `RateLimit` is: the capability's own `[unstable] allow` and platform checks apply. [DECISION E] Under `bynk dev` and in tests `clientIp` comes from the request; a request without the header counts as the one client `unknown`, so it is limited rather than uncounted. Tests drive the limiter on the harness clock.

Correction to the issue's premise: the issue and the request-lifecycle page described the router order as "… → actor → body read → 400 → handler". The emitter reads and decodes a non-sum route's body in the entry and only then calls the handler's surface wrapper, which runs the actor's verification seam. Authentication happens after the body is read (a multi-actor and a `Signature` route's wrapper reads the body itself). So `identity` "after the actor, before the body" needs verification moved ahead of the body read; that is a separate increment (it must verify exactly once and order the `429` against `401`/`403`), and this one ships `clientIp`, which has no such dependency.

**Consequences.** A flood from one address costs a counter and a `429`, not a full read, and the same limiter can still be called in a handler with `allow(key)` for a key only the handler knows. A `match` over `BoundaryRejection` without a wildcard needs an arm for `RateLimited(_)`. Per-region counting is as approximate as `RateLimit`'s, and users behind one address share a count.

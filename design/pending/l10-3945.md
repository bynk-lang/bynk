## ADR: stub-generic-capability-operations
title: A stub names the type argument of a generic capability operation
summary: The type argument is part of a stub's and an observation's target, typed by substitution, and matched at run time by a key the test build passes with the call

**Context.** A generic capability operation (`fn dedup[T](key: String) -> Effect[Option[T]]`) could not be stubbed, because a clause's value cannot be built for an unconstrained `T`. A stub that names the type has a concrete `T`, so that reason does not apply (#3945).

**Decision.** The maintainer accepted the issue's decisions. A: `stub Cap.op[T](…)` carries the type arguments in its target, the clause's arguments and value are checked against the operation with the type arguments substituted for its type parameters, and the clause answers only the calls made at those type arguments. B: a `stub` of a generic operation without type arguments stays `bynk.stub.generic_op`, with a note that gives the typed form; a wrong number of type arguments, or any on an operation that takes none, is `bynk.generics.type_arg_mismatch`; an unknown type is `bynk.resolve.unknown_type`. C: `expect Cap.op[T] called …` counts the calls made at those type arguments, and an observation without them counts every call. D: a stub gives all the type arguments, in order, as the call site does. A service stub takes none.

The call site and the clause meet at a key. Option (1) was chosen, on three conditions: production output is byte-identical, the test-build argument is trailing and the real binding ignores it, and the choice is recorded here. In a test build only, a call to a generic operation passes a trailing `{ __bynkTypeKey: "[Outcome]" }` after its own arguments, cast so the operation's declared type is unchanged. The stub class method for a generic operation reads that argument and a clause matches when its printed type arguments equal the key; the recording proxy takes the marker off the arguments, so `trace(…)` and `with` predicates still see only the operation's own, and keeps it as the call's `typeKey` for the observation filter. No production fixture's expected output changed.

Option (2) was rejected: it keyed the stub on the erased TypeScript type, which cannot tell `dedup[Int]` from `dedup[Float]`, and would have made a stub answer the wrong call.

**Consequences.** The key is the type arguments as written, so two spellings of one type (a qualified and an unqualified name, or an alias) are two keys, and a stub must be written as the call site writes it; a stub that matches nothing faults with `no stub clause matched`. The tree-sitter grammar accepts the type arguments on both forms. Hover, completion and signature help have no surface for a stub or observation target today, so they are unchanged.

## ADR: single-file-programs-reach-prelude-units
title: A single-file program merges in the first-party units behind the prelude types it names
summary: One mechanism, driven by the prelude table, in the single-file loader

**Context.** #4475, from #3976: a prelude type (`Ordering`, `ValidationRule`, `Bound`, `DecodeErrorKind`) is declared in a first-party commons and reached with no `uses` in a project, by `add_implicit_uses`, which adds the `uses` line to a parsed unit that names the type or writes a spelling that yields one. A single-file program has no other unit to `uses`, so it could not reach any of them: `e.rule` and `compare` were refused there with a note that said to move to a project, and since #3976 a single-file program could no longer read `e.kind`, which was a `String` before.

**Decision.** (A) The single-file loader merges the unit instead: `inline_prelude_units`, beside `add_implicit_uses`, reads the same table (`bynk_std::PRELUDE_TYPES`) and decides on the same words (`mentions_word`), so a new prelude type is still one row and its unit and the two paths cannot disagree. For each unit a program needs, its items are appended to the program's own, before the checks run. (B) They are parsed with the unit's reserved file id and expression-id block, as the project injection parses them, so the checker's test for the prelude type (`is_prelude_type`: a declaration whose span carries that file id) holds, and no expression id collides with the program's. (C) The alternative of building a one-unit project around the file would reach the same units through the project pipeline, but it would change what a single-file compile returns (module layout, emitted files) for every program, not only the ones that need a prelude unit; merging items changes only the programs that name one. (D) A type of the program's own with the name keeps its declaration and the unit's of that name is left out, as in a project (the user's declaration shadows the prelude's). The note of the three errors that remain (a user type of that name hides the prelude type) says so and no longer says a single file cannot reach the unit. (E) As in a project, the words are read from the source text, so a program that writes `.kind` on a record of its own also gets `DecodeErrorKind` declared in its output; it is unused and harmless, and the same over-approximation a project already has.

**Consequences.** Single-file programs read `e.kind` (matched and interpolated), `e.rule` and `Ordering`; three single-file fixtures pin the emitted output. A program that names none is byte-identical. The "needs a project" notes in the checker's errors and in `reference/types.md` are removed. Not changed: the `bynk` adapter's transparent types (`add_implicit_consumes`), which a single-file program still cannot reach.

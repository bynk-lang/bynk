## ADR: agent-state-view
title: The agent state view is an agent-scoped live panel with a diagram and an exact table, mapped back to source without Mermaid `click`
summary: `bynk/agentStateModel`; a `Show State` lens per agent; follow per agent, highlight per handler; states by DOM id, transitions by edge number

**Context.** Slice 2 of the agent-state-views track (#2190, proposal #2196) renders slice 1's agent state model. The track settled (§3.2, §3.4) that the view is agent-scoped, in its own live panel (ADR 0504), with a diagram and a handler × state table, and that click-to-code cannot use Mermaid's `click`: in `stateDiagram-v2` it takes a URL only, on states only, and opens it in a new tab.

**Decision.** The server answers `bynk/agentStateModel` (advertised under `experimental`) for the agent enclosing the cursor, anywhere in its declaration, with the model plus each handler's name and range, and puts a `Show State` lens on every agent's name — always on, beside the per-handler `Show Sequence` lens, since it is the view's only entry point from source. The extension's panel is a `LivePanel` with a new `followScope: "owner"`: cursor-follow retargets when the enclosing service or agent changes, and inside one it only reports the handler under the cursor as the view state's `focus`, which the page highlights without a re-request. The page shows one state field at a time (a selector when there are several; the choice is kept across live updates, not across a reload): a `stateDiagram-v2` with `[*] → initial`, one transition per (from, to) labelled with its handlers, computed writes to a dashed `?` state, unreachable states dimmed, truncated handlers as a note, and unchanged outcomes as self-loops only behind a toggle; and the table, total over handler × state, with every path's target, outcome and guards. Click-to-code maps the rendered SVG back to the model: a state by its DOM id (`state-<id>-<n>`, matched exactly so `s1` never matches `s10` or a note), a transition by its label's `data-id="edge<n>"`, sorted by `n` — Mermaid numbers transitions in statement order, so the sort recovers the generator's order whatever the layout's DOM order. Both shapes were checked against a real Mermaid 12.2 render.

**Consequences.** One more custom request, lens and view; the shared `LivePanel` gains an owner scope and a `focus` field in its view state that the existing handler-scoped views never set. The DOM-id and edge-number mapping is pinned by unit tests on those shapes, so a Mermaid upgrade that renames them fails tests rather than silently breaking clicks. A state links to its field's declaration, since a state has no single source location of its own. The selected field and toggle are page memory, not persisted state, which keeps `setState` the target alone (what restore reads).

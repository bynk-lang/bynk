## ADR: refined-explorer-evaluation
title: The refined-type explorer evaluates the emitter's predicate lowering in the extension host
summary: Candidates are checked client-side over the emitter's own predicate conditions, never by running project code

**Context.** The refined-type explorer (#2470) checks a typed candidate against a refined type's predicate and lists example values. Two places could evaluate: a `bynk eval` driver command that compiles and runs the project, or evaluating in the extension host over a predicate entry point the emitter already lowers. A refined type's predicate is pure, drawn from a closed set of eight forms (`NonNegative`, `Positive`, `InRange`, `NonEmpty`, `MinLength`, `MaxLength`, `Length`, `Matches`), but a driver would still build and execute the project's emitted output on a hover click.

**Decision.** The server ships each clause's condition, taken from `bynk_emit::emitter::pred_condition_and_message` (the one mapping `.of`, the boundary codec and `is` share) and printed as a JavaScript expression over `value`. The extension host evaluates it in a fresh `node:vm` context with string `eval` disabled, the candidate bound as `value` (never spliced into source), and a 250 ms limit per clause. No project code is ever evaluated: the only source is compiler-generated from the closed predicate set, and the one user-written part, a `Matches` pattern, sits inside a string literal. The checker already rejects patterns that backtrack catastrophically. Every failing clause is reported, in the runtime's check order. Examples are drawn in the server, deterministically, from the domain the test runtime's `for all` generator uses (`__bynkRng`) under a fixed seed, so the list is identical on every open; a `Matches` type has no generator (`bynk.val.needs_pin`), so only drawn strings that match are kept. The hover's "Try values…" link is a client command, offered only to a client that advertises `experimental.refinedTypeExplorerCommand`.

**Consequences.** Nothing new is compiled or run to answer a hover, and the verdict is what the compiled `.of` would decide, since both read the same lowering. `pred_condition_and_message` becomes public in `bynk-emit` and `bynk-lsp` depends on `bynk-emit`, `bynk-ts` and `regress`. `node:vm` is not a security mechanism (Node's own documentation says so) and this is not a sandbox. What bounds the risk is what reaches it: conditions the compiler generated from the user's own workspace, plus a candidate that arrives only as the context value `value`, parsed strictly (`Int`, `Float`) or taken as an opaque string and never concatenated into code. The run sets a `timeout`, and the context has no `require` or `process`. Tests pin that a hostile candidate (`1); process.exit(`) is just a failing value and that a hostile pattern stays inside its literal. An `Int` candidate is a `bigint`, as the emitted code holds one. A client other than VS Code can serve the same request but needs its own panel and evaluator. The explorer is VS Code on the desktop only; the web extension has no `node:vm`.

## ADR: cache-reaping-at-commit
title: Expired Cache entries are deleted at commit, by the clock the program read
summary: A commit deletes up to 64 expired entries of an agent's Cache fields, judged by the injected Clock the handler's Cache operations read, so reaping cannot be seen by a program and never runs on the runtime's own clock

**Context.** `@ttl` on a `Cache` hides an expired entry on read (ADR 0113) but never deleted it, so a `Cache` keyed by many distinct keys grew until the agent ran out of room, whatever the entries' lifetimes. With each entry under a key of its own (per-entry storage, #3189) deleting one is a single write, and each entry's expiry is also a key (`x/<field>/<exp>/<key>`). Where and by which clock to delete had to be chosen. The runtime's own clock is wrong: a `Cache` operation reads the injected `Clock` capability, which `bynk test` replaces with a fake, and real time is later than every `exp` a fake clock stamped, so a reaper on the runtime's clock would delete entries the program still reads as live.

**Decision.** Every `Cache` operation already reads `Clock.now()`; it now also notes that value against the handler's state object (`__noteClock`, one call at the read). When the handler commits, the commit passes that state object to the runtime, which treats every entry whose `exp` is not after the noted clock as expired (the same test `get`, `contains` and `size` use), leaves it out of the entries it writes, and so deletes its key and its expiry entry in the same transaction as the rest of the commit. At most 64 entries are deleted per commit, across all of the agent's `Cache` fields, oldest expiry first; the rest go on later commits. A handler that never ran a `Cache` operation noted no clock, and its commit deletes nothing. The latest clock a handler read is the one used. No stored byte changes: the layout already holds each entry's `exp` and its expiry key.

**Consequences.** A program cannot observe reaping, assuming its clock does not go backwards across handlers: a read, `contains` and `size` already treat an expired entry as absent, and an entry is deleted only once the program's own clock has said it is expired, so under a fake clock a live entry is never deleted. (A fake clock that is advanced past an entry's expiry, used by a handler that writes the `Cache`, and then wound back would show that entry as absent where it would have read as live again.) The 64-entry budget is shared by an agent's `Cache` fields and taken in declaration order, so a large backlog in an earlier field delays reaping in later ones until it drains. A `Cache` that is never written again keeps its expired entries until some handler that uses it commits, and a commit deletes at most 64, so a large backlog drains over several commits; an alarm sweep (still deferred by ADRs 0113 and 0121) would not depend on a handler running and is left for later. Reading still loads every entry (eager reads), so reaping bounds what is stored, not what is loaded, until the lazy-read slice. The `Cache` operation prefix in the lowering gained the one call; hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

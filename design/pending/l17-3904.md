## ADR: websocket-cookie-oidc-open
title: A WebSocket upgrade may authenticate a session cookie behind an exact Origin check, or an OIDC token in the `bynk.oidc` subprotocol pair
summary: `on open` admits a lone `SignedCookie` or `Oidc` actor; a cookie upgrade is `403` unless `Origin` is exactly a `cors` origin, a missing `Origin` included, and an `Oidc` token rides `["bynk.oidc", token]`

**Context.** A `from websocket` `on open` admitted `None` and `Bearer` actors only (#3900), so a browser app signed in with a `SignedCookie` session, or holding an identity provider's token, could not open a socket without minting a second credential. A cookie is sent by the browser on an upgrade from any site, and a WebSocket is not covered by CORS or the same-origin policy, so authenticating by cookie alone is cross-site WebSocket hijacking: a page on another site opens the socket as the signed-in user (#3904).

**Decision A — a lone `SignedCookie` or `Oidc` actor is admissible on `on open`.** `Bearer`, `Oidc` and `SignedCookie` are `websocket` protocols. They are not admissible as members of an actor sum there (`bynk.actor.scheme_not_admissible`): a sum resolves its members first-wins from one token source, and a cookie needs the `Origin` check before it is read. A `SignedCookie` actor with `sessions = true` is refused for the same code, because the upgrade does not check the session is still live and a revoked session could open a socket. Rejected: admitting it with no live check, which would quietly give a revoked session a socket.

**Decision B — a cookie upgrade checks `Origin` first, exactly.** The `Origin` header must equal one of the service's `cors` `origins`, scheme, host and port as written, or the upgrade is `403` before the cookie is read, so a refusal does not reveal whether a session exists. A missing `Origin`, `null` and `*` never match, there are no wildcards, and `Sec-Fetch-Site` is not consulted (HTTP's cross-site check accepts `same-origin` alone; an upgrade opens a long-lived bidirectional channel and is held to the stricter rule). The comparison is `webSocketOriginAllowed` in the runtime, tested against near misses (another scheme, port, case, a trailing slash, a longer host).

**Decision C — the service must list its origins.** A `from websocket` service may declare `cors`, and one whose `on open` authenticates a `SignedCookie` must declare `cors { origins: [...], credentials: true }` with no wildcard, or it is `bynk.ws.cookie_needs_origins`. `cors_not_http` now reads "`from http` or `from websocket`". Of the policy's fields only `origins` and `credentials` apply to a WebSocket. Rejected: defaulting to the request's own origin, which is the check an attacker's page cannot satisfy but also the one a separately hosted front end must always fail.

**Decision D — an `Oidc` token is the pair `["bynk.oidc", token]`.** It is the Bearer pair with its own marker (`OIDC_SUBPROTOCOL`), read by the same offer helpers, so the old single-element form is `400` naming `["bynk.oidc", <token>]`, the `101` selects `bynk.oidc` and never the token, and the token is verified against the provider's JWKS as HTTP does, with `trustFrom` honoured. Rejected: reusing `bynk.bearer` for both, which would make the marker ambiguous when an actor sum has an `Oidc` member later.

**Decision E — the credential's expiry is forwarded and re-checked.** The upgrade forwards the verified credential's `exp` (a session cookie's, or an `Oidc` token's) in the trusted header, and the Durable Object re-checks it at every frame exactly as a Bearer token's (#3903), closing with `1008`. `verifySignedCookie` returns the `exp` it checked. The Durable Object reads no trust root: it receives the binder and identity type, carried in the same seam record whatever the scheme.

**Consequences.** A browser app can open a socket with the session it already has, safely, and a client holding an identity provider's token can open one without a second credential. A cookie service lists the pages that may open it, and an existing `from websocket` service is unchanged: `cors` was an error on it, and no other behaviour moves. A `SignedCookie` actor with `sessions = true` and an actor sum with a cookie or `Oidc` member are refused until their checks (a live-session check on the upgrade, and a sum that orders the `Origin` check) are designed.

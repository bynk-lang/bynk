## ADR: container-runtime-and-config
title: A container's class is built by a runtime function and its image from a Dockerfile path
summary: Decisions B, D, F and J of #3477 for slice C1: the `[[containers]]` stanza, the class generated from literals, the readiness wait, and where build paths point

**Context.** Under the `durable_object` scheduling policy the application entry takes only `class_name`, `scheduling_policy` and an `images` map; Wrangler rejects `image`, `max_instances` and `instance_type` on it. `start()` requires an `image` (a value of `ctx.container.images`) and `enableInternet`, returns before the container is ready, and a Durable Object that restarts begins without an inactivity timeout. The output directory is `[build] out` or any `--out`, so the path from a Worker's output directory to the project is not fixed by the layout.

**Decision.** B: `[[containers]]` holds `class_name`, `scheduling_policy = "durable_object"` and `[containers.images.<Capability>]` with `dockerfile` (the file) and `build_context` (its directory), each written as the path from `<out>/workers/<worker>` back to the project (`../../../<build>` for the default `out`). This clarifies Decision B, which assumed a fixed layout: the path is computed from the directory the build is actually written to (`bynk build --out`, else `[build] out`), so any directory inside the project works, and a build whose output directory is outside the project is refused with `bynk.container.output_outside_project`, naming each container and both paths. Copying the build directory into the output was rejected: it would take `node_modules`, secrets and large files with it, and go stale. F: the class is `export const __Container_<Name> = __containerClass({ image, port, sleepAfterSeconds?, instanceType?, forward })` in `containers.ts`, so the generated file is data and the lifecycle lives in the runtime module `container.ts`, which starts with `image: ctx.container.images[<key>]` and `enableInternet: false`, applies `setInactivityTimeout` after every start and again when the class is constructed over a running container, and retries a port that is not yet listening for a bounded time (30 seconds) only after a start in the same call, with the body buffered. It is a legacy-style class, as agent and fan-out classes are; Wrangler 4.136.0 accepts it. D/J: the class reports its own failures as a 502 carrying `bynk-container-error` (`start-failed`, `unavailable`, `timeout`), which the provider reads and the class strips from the container's own responses, so a container cannot forge one; a forwarded secret the Worker lacks is a failed start that names the secret, never a value.

**Consequences.** Experimental. `bynk deploy` and the Docker preflight and the 4.136.0 refusal are C2; `bynk dev` is C3. Checked with `wrangler deploy --dry-run` at 4.136.0 for the same configuration with a digest-pinned `image` in place of `dockerfile` (a Dockerfile entry makes the dry run build, which needs Docker); not verified against a real deploy: a legacy-style class under `ctx.container`, the readiness wait, inactivity, rollback and local dev.

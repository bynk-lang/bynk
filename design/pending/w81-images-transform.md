## ADR: images-capability
title: Cloudflare Images is a one-per-Worker `Images` capability: a flat typed `transform` over `Bytes`
summary: A `Singleton` `Images` over the `[images]` binding, typed options, errors by code, stub-only in tests

**Context.** Cloudflare's Images binding resizes, converts and draws on images in the Worker from the bytes it holds, with no URL and no zone. ADR 0798 anticipated it beside Version and Workers AI, and ADR 0833 added the second `Singleton`. The proposal (#3515) was written when Cloudflare's documentation was unreachable, so its first slice checked every platform fact against [Images binding](https://developers.cloudflare.com/images/optimization/binding/), [limits and formats](https://developers.cloudflare.com/images/get-started/limits/), [draw overlays](https://developers.cloudflare.com/images/optimization/draw-overlays/), [features](https://developers.cloudflare.com/images/optimization/features/), [troubleshooting](https://developers.cloudflare.com/images/reference/troubleshooting/), Wrangler's configuration page and `@cloudflare/workers-types`.

**Decision.** `bynk.cloudflare` gains `Images`, a `Singleton` (`[images] binding = "IMAGES"`), used bare (`given Images`); `capability R = Images` is `bynk.capability.base_not_instantiable`, and the stanza is emitted only for a Worker whose closure reaches `Images`. It is experimental. The surface is flat and typed, not a pipeline builder: `transform(image: Bytes, options: TransformOptions, output: OutputOptions) -> Effect[Result[ImageResult, ImagesError]]`, where `TransformOptions` is one transform step (`width`, `height`, `fit`, `rotate`, `blur`) plus `overlays: List[Overlay]`, `OutputOptions` is a required `format` and an optional `quality`, and `ImageResult` is `{ body: Bytes, contentType: String }`. A pipeline value would hold a stream-backed, non-data handle. Further options (`gravity`, `brightness`, `composite`, text overlays, `anim`) are added later as defaulted fields. `ImageFormat`, `ImageFit` and `ImagesError` are extensible. `info(image: Bytes) -> Effect[Result[ImageInfo, ImagesError]]` is the second operation (the stream is a later slice). The platform's `info()` answers `{ format: "image/svg+xml" }` alone for an SVG, and otherwise a MIME string with `fileSize`, `width` and `height` (workers-types `ImageInfoResponse`), so the maintainer decided `ImageInfo` is a sum type: `Raster(format: ImageFormat, width: Int, height: Int, size: Int)` or `Svg`. `ImageFormat` gains `Heic`, accepted as input only; `Heic` as an output is refused before the call as `InvalidImage` (`Svg` is an `ImageInfo` case, not an `ImageFormat`, so it cannot be asked for). A MIME type `ImageFormat` does not name maps to `ImagesFailed`, never a guess.

The checks against Cloudflare's documentation amended the proposal: the binding takes output formats as MIME types (`"image/webp"`), which the binding maps from `ImageFormat`; `ImageFit` gains `Squeeze`; `.input()` accepts at most 20 MB. Errors are mapped by what the binding throws, an `ImagesError` with a numeric `code` (workers-types), also read from a message that opens with the code: 9412, 9401 and 9432 are `InvalidImage`; 9413, and 9402 when its message says the image is too large, are `ImageTooLarge` (9402 is also "the connection was interrupted", which is `ImagesFailed`); 9520 is `UnsupportedImage`; every other code, including the usage limit 9422 and timeouts, is `ImagesFailed` with the platform's message, so a code Cloudflare adds never becomes a fault. Image bytes and option values are usually data, so they are values, not faults. The binding itself refuses, without calling the platform, an empty image, a `width` or `height` below 1, a `rotate` outside 90, 180 and 270, an `opacity` outside 0 to 1, a `quality` outside 1 to 100 and an overlay positioned from both opposite edges; it does not encode the platform's own limits, which it enforces and reports. The thrown shape is the documented one; it has not been observed on a live account, because the platform's preview sessions are not reachable from the build environment.

The integration double's "not stubbed" fault is marked and rethrown by the binding, so a handler's `Err(_)` fallback cannot swallow it. In a test every `Images` operation faults until `stub Images.transform(_, _, _) returns …` replaces it, in both the unit and the integration tier: a transform cannot be faked honestly, and an image handed back unchanged would pass for the wrong reason. Under `bynk dev` Wrangler runs a low-fidelity local Images (only `width`, `height`, `rotate` and the format are supported; `--remote` gives the full version), so nothing is remote and no `[dev]` acknowledgement is added; the Book says that other options are not reproduced locally. `bynk deploy` repeats the `[images]` table in each `[env.*]` block, because bindings are not inherited. No prices, allowances or billing rules appear anywhere: the tooling links to Cloudflare's pages.

**Consequences.** New names in `bynk.cloudflare`; a program that does not consume `Images` emits its own modules byte-identically (the standard-library modules it always emits grow), and no `[images]` stanza appears for a Worker that does not reach it. No grammar or checker change.

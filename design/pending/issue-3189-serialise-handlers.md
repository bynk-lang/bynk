## ADR: serialise-agent-handlers
title: An agent instance runs one handler at a time
summary: Every handler that reaches an instance, read-only ones included, runs through a per-instance queue; a re-entrant call faults ReentrantAgentCall and a long wait faults AgentBusy

**Context.** A handler loads its agent's state, runs, and commits the whole record (ADR 0109, ADR 0110 D3). The Durable Object runtime closes its input gate only while a storage operation is in flight, so a handler that awaits anything else, such as a call to another agent or a capability, lets a second request run against the same instance. Both handlers then load the same starting record and the second commit overwrites the first. A local workerd run (#3202) lost four of six expected increments across a timer await and one of six across a `fetch`. The design notes (§12) and the Book already say the handler is the atomic unit and name the Durable Object gates as the source of that guarantee; the gates alone do not deliver it once a handler awaits. The maintainer decided the instance serialises its handlers (actor semantics).

**Decision.**

1. **One handler at a time, per instance.** Every entry point that reaches an agent instance (an agent call, a WebSocket event, an alarm, the migrate wake) runs through one first-in, first-out queue held by the instance. Instances with different keys do not wait for each other. A handler that calls a sibling handler on `this` is one handler, not a second call. This includes read-only handlers: serialising everything is the rule that can be stated in one sentence, and a read-only handler holding the queue costs only the time it runs.
2. **Where it lives.** In the runtime, not in the emitted agent class. On the Workers target the Worker entry exports each agent class wrapped by `serialiseAgentClass`; the in-memory Durable Object namespace used by `bynk test` wraps the same way; the bundle target wraps the agent value in a proxy keyed by the instance's state. Cloudflare's `blockConcurrencyWhile` is documented for construction and is not used.
3. **Re-entrancy faults, it does not hang.** A handler that reaches its own instance again, directly or through other agents, would wait on itself. Each agent-to-agent call carries the ids of the instances whose handlers are running along the way, in an internal request header added only by the stubs an instance's own `env` hands out, and an instance that finds its own id in the chain faults `ReentrantAgentCall` at once, without running the handler. The header is read only on the internal `/_bynk/agent/` route, never on a forwarded client request, and a chain longer than 16 is refused. The checker has no cross-agent call graph, so this is a runtime rule, not a static one.
4. **Waiting is bounded, and is a different fault.** A call waits at most 30 seconds (`AGENT_QUEUE_WAIT_MS`, one named constant) for the handlers ahead of it, then faults `AgentBusy` ("agent X busy: waited 30 s behind N queued calls"). The timer measures queue wait only, never a handler's own run time, and a call that gives up passes its place on. It is a separate fault because a hot instance can reach it with no cycle. It is also the backstop for a cycle the chain cannot see: a call that leaves the Worker through a Service Binding and comes back, or the bundle target, which has no call chain. The limit is not configurable in this increment; a per-agent or per-project setting is a possible later addition.

5. **Events fan-out gives the place up.** An agent handler that emits events commits first and then awaits the fan-out, which calls subscribers; a subscriber may call the publishing instance back. The stub the instance's own `env` hands out for the fan-out route therefore gives the handler's place up before the fan-out request goes out, so the subscriber's call is served instead of queuing behind the handler that is waiting for it. Every emitted handler has the same shape: events are buffered while the body runs, the state is committed, the buffered events are handed to the fan-out, and only `return __result` is left. So the place is given up when nothing is left to run or commit for that handler; a handler that faults emits nothing.
6. **The bundle target has no chain.** Catching a cycle exactly in-process needs async context (`AsyncLocalStorage`), which the in-browser build does not have, and a plain "running now" set would mistake a legitimate concurrent external call for re-entrancy. A cycle there is caught by the queue-wait limit, as `AgentBusy`; the same program therefore reports `ReentrantAgentCall` on Workers and `AgentBusy` in the bundle target. The bundle wrapper takes the wait limit as a parameter so tests can use a short one.

**Consequences.** A handler's load, body and commit are no longer interleaved with another handler's on the same instance, which makes "persisted atomically when the handler returns" true when a handler awaits. Throughput on one instance is one handler at a time, as for any actor; a handler that awaits a slow call holds its instance for that time. **Behaviour change:** a cycle through other agents (`X` calls `Y`, which calls `X`) previously ran, silently losing updates; it now faults `ReentrantAgentCall`. Every handler on an instance is serialised, including read-only ones. The per-entry storage track (#3195) keeps this model: with per-entry keys, disjoint writes would no longer overwrite each other, but `Cell` writes and writes to one entry still would, so the queue is still what makes handlers atomic. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

## ADR: sql-column-types
title: The SQL capabilities share one set of column types
summary: `D1`, `Postgres` and `MySql` read the same row field types and bind `Decimal` and `Instant` as typed parameters, each with one storage convention

**Context.** #4046. The three capabilities disagreed on what a column can be. A `D1` row was `Int`, `Float`, `String`, `Bool`, `Bytes` or `Decimal`; `Postgres` added `Instant`; `MySql` read `Decimal` but not `Instant`; `Duration` and an enum were a row type nowhere. So a `D1` table could not hold a timestamp read as an `Instant`, and money went in as `Text(d.toString())` and came back as a `Decimal`. `PgNumeric` and `MySqlDecimal` took a `String`.

**Decision.** (A) One row-type set for every capability, typed reads and `Json.decodeSql` alike: `Int`, `Float`, `String`, `Bool`, `Bytes`, `Decimal`, `Instant`, `Duration`, a payload-less enum, a refined or opaque type over a scalar one, or an `Option` of one. `check_row_shape` no longer takes a dialect. (B) `D1` storage: `Instant` and `Duration` are `INTEGER` milliseconds, `Decimal` is canonical `TEXT`, an enum is `TEXT`, the variant's wire name. The generated codec already reads each of these from that form, so `D1` needs no row pass; an `Instant` field over a text that is not an RFC 3339 time with an offset fails the decode naming the field (the codec also reads an offset RFC 3339 text, which the issue's risk note did not expect, so an ISO-text column keeps reading). (C) Typed parameters: `SqlValue` gains `Numeric(value: Decimal)` and `Timestamp(value: Instant)`; `PgNumeric` and `MySqlDecimal` take a `Decimal`; a `Duration` binds as `Integer` milliseconds and an enum as `Text` of its variant's name. The decimal variant is `Numeric`, not the `Decimal` the issue wrote, because `Decimal` is a reserved keyword and cannot name a variant; an enum has no `toString`, so binding it is a `match` over its variants, and no language surface is added (the accessor is its own issue, #4560). (D) `Postgres` and `MySql` read a `Duration` from a `bigint`, which arrives as text, through the `int8` path. `MySql` reads an `Instant` from a `DATETIME` or `TIMESTAMP`'s zone-less text as UTC, as `MySqlTimestamp` binds it, through a `MySql` flag on `__bynkPgRow`; a `DATE` or any other text still fails the decode. (E) `bynk.d1.select_field_missing` is unchanged. A new warning, `bynk.d1.column_affinity`, flags an `Instant` or `Duration` field over a column declared without `INT` (text affinity) and an enum field over a column that is not text. `Decimal` keeps `bynk.d1.decimal_numeric_affinity`.

**Consequences.** A `D1`, `Postgres` or `MySql` row may hold an `Instant`, a `Duration` or an enum with no conversion by hand. The two payload changes are breaking and give a type error at each `PgNumeric(...)` or `MySqlDecimal(...)` call that passes a string; a literal `s` is replaced by the `Decimal` literal. The runtime's `postgres.ts`, `mysql.ts` and the `PGlite` double turn the decimal into its canonical text at the driver edge, and `WorkersD1` does the same for `Numeric`. New code: `bynk.d1.column_affinity` (a warning). Not done here: the row-field hover that names the column convention, which is a follow-up.

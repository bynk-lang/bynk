## ADR: ord-order-lock
title: The order of a `derives Ord` type is recorded in `bynk.schema.lock`
summary: a new `[orders]` section records each project-owned `derives Ord` type's member order; a reorder is `bynk.types.ord_order_changed` until `bynk lock accept-order` rewrites the entry

**Context.** The language made declaration order meaningful by choosing it as the derived `Ord` (fields in order for a record, variants in order for a sum). Moving a field or variant changes how every value sorts, and nothing reports it: the wire contract hash ignores that order. The lock already exists to catch a code edit that looks inert and changes what running programs do, for stored shapes and event versions.

**Decision.** [DECISION A, B] `bynk.schema.lock` gains `[orders]`, keyed `<unit>.<Type>`, one entry per `derives Ord` record, sum or enum of the project itself (a dependency's types and the standard library's are not the project's to accept): the field names in order, or the variant names in order each with its payload field names. Type names are not recorded. [DECISION C] A change is two names both present swapping relative order, or a field or variant inserted anywhere but the end; appending, removing and renaming in place update the entry. A rename in place is a removed and an inserted name that fill the same gap between the names the two orders share. A refined or opaque type orders by its base, so it has no entry. A kind change (record to sum) is a type-checked change and updates the entry. [DECISION D] `bynk lock accept-order <Type>|--all` rewrites the entries; it reads the source without checking it, so it works on a project the lock refuses. [DECISION E] A type that no longer derives `Ord`, or is gone, drops out of the lock with no diagnostic. The error stays on the type's own declaration, with the recorded and new order in notes and a "Restore the recorded order" suggestion that moves each member's text back to its recorded slot (offered as an editor action, never applied by `--fix`).

A lock with no entries is written exactly as before at version 2. One with entries is version 3, which a version-2 toolchain refuses rather than parsing and dropping the table. A version-3 lock with no entries reads as version 2.

**Known limit.** A removal is followed at once, so a reorder can be laundered across two clean builds: cut a member, build, paste it back at the end, build. The lock records what the project compiled, not a history, and `bynk dev` makes the two builds easy. The rule catches the edit that moves a member in one step, which is the one that happens by accident; closing the other would mean keeping removed names in the lock.

**Deviation.** The issue says a `--locked` build refuses an out-of-date `[orders]` section. `--locked` governs `bynk.lock` (packages) only; the schema lock has no refuse-instead-of-write mode today, and a build records additive changes to it as it does for events and agents. So this adds none: a reorder is refused in every build and in `bynk check`, which is the guarantee the issue wants, and an additive change updates the entry on the next build.

**Consequences.** Hover on a `derives Ord` type shows its order. The first build of an existing project records its ordered types silently. The `[orders]` section and the version bump are visible in the diff of the lock, as the issue asks.

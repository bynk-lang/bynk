## ADR: migrate-sweep-reports-existing-unique-duplicates
title: The sweep's wake reports existing @unique duplicates as holder counts
summary: Where the duplicates are read, what the report may carry, and why it never fails a sweep

**Context.** #4390, from #4038: `@unique(by: k)` is enforced when a handler commits, so adding it to a `Map` that already holds data leaves any duplicates already stored in place until a commit touches them. Nothing told the author how many there were before the constraint began to refuse commits. `bynk migrate sweep` already wakes every stored instance of a class through its Worker, so it is the one place that visits all of a class's data.

**Decision.** (A) The wake reads the postings. A woken instance, once it has loaded, reads each `@unique` index of its maps and returns, per index, one number for each value that more than one key holds: the count of its holders. The postings sort by value, so the holders of a value are one run of keys, and the read keeps only the run lengths, never the values or keys, however large the map. The class's `@unique` indexes are passed to the wake by the emitter; a class with none is emitted exactly as before. (B) The report names no value-derived label. A stored value, a hash of it and the keys holding it all stay on the account: the sweep reports the map, the field, the number of shared values and the holders of each (`3 values are held by more than one key: 2, 2 and 4 holders`), gathered over the class's instances with the count of instances. A hash would let a reader confirm a guess at a value, which is the thing the rule is there to prevent. (C) It is information, not a verdict. It does not make the sweep fail (the exit code is unchanged), does not hold a class's floor, and is not recorded anywhere: like the instances' versions, what is stored is Cloudflare's state and a copy would go stale (Decision F of the sweep). (D) The wake reconciles the map's postings before reading them (the existing "first touch rebuilds the postings" step), which for an index just declared is one pass over the map held in the woken instance's own overlay; that is why a map that was populated before `@unique` was added is read correctly. (E) The new `duplicateHolders(index)` is a method of the store handle beside `hasDuplicate`, in both the in-memory and the storage-backed handle.

**Consequences.** After adding `@unique` to a populated map, `bynk migrate sweep` shows how many duplicates exist and how widely they are held before any commit is refused. A deploy plan cannot show it: it reads no stored state, so the report appears in the sweep's own output, which is the wake path the issue names. Not done: a way to list the keys of a duplicated value (it would leak the value's holders and was not asked for), and failing a sweep or blocking a deploy on a duplicate.

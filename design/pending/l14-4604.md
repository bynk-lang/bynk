## ADR: decode-error-message-never-the-value
title: A DecodeError's message names the path, the expectation and the JSON kind, and never the value
summary: Why the decoder redacts instead of the docs hedging, and what each failure now says

**Context.** The docs say a decode error names the path and the expectation and never carries the value being decoded, so a program can log it. The decoder did not keep that: `Malformed` carried `String(__e)` from `JSON.parse`, whose text quotes part of the input on recent V8; the integer and finite checks put `String(actual)` in the message; and an unrecognised sum or `Result` tag was echoed as written. A request body, a stored record or a secret could reach a log through a message the docs called safe (#4604, found while documenting #4101).

**Decision.** Option (A) of the issue: redact in the decoder, so the documented contract holds, and a docs hedge (B) is not taken. A message names the path, the expected type and the actual JSON *kind*, never the value. A number that passed `typeof` and failed a check is reported by a class from a closed set: `non-integer number`, `integer outside the safe range` or `non-finite number`. A tag that names no variant is `unrecognised variant`, and a non-string tag is its `typeof`. `Malformed` is `not valid JSON at offset N`, the offset read from the end of the engine's message (so quoted input cannot choose it), or `not valid JSON` where the engine gives none. The same helper (`__bynkJsonParseMessage`) shapes the `MalformedJson` detail of a service-call response. A refusal's own `violation.message` is the predicate's message and is unchanged. The `kind` and `path` of every error are unchanged.

**Consequences.** Every generated deserialiser and the shared standard-library codecs re-bless, and a decode error is safe to log whatever it decoded. The message text of a failed decode changes, which is `breaking:` for a program that compared it. The `actual` values that already named a fixed reason (`a duplicate`, `invalid decimal`) and the contract hash of a call's skew check are unchanged: neither is the decoded value.

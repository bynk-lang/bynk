## ADR: http-result-streaming-element
title: An HttpResult names the element its Streaming body carries in an optional second type argument
summary: `HttpResult[T, E]` declares what a streaming route streams; a route that names nothing keeps today's behaviour, so the change is additive; a signature never depends on a handler's body

**Context.** `Streaming(s)` carries a stream, but `HttpResult[T]` has one type parameter, `T`, which is irrelevant to a streaming body. The checker accepts a `Stream[String]` or a `Stream[SseEvent]` there (#3918), and binds `s` in a pattern as `Stream[String]` whatever the handler streams, so a unit-tier test that matches `Streaming(s)` on a route streaming `SseEvent`s cannot read the events as `SseEvent`s and a mismatch is not an error (#4394). Existing streaming routes declare `HttpResult[()]`, so the declared type says nothing about the element.

**Decision.** `HttpResult` takes an optional second type argument, `HttpResult[T, E]`, the element a `Streaming` body carries. `E` is `String` or the `SseEvent` record `bynk` exports, because those are what the router can frame as server-sent events; any other type is `bynk.types.streaming_element`. With `E` named, `Streaming(arg)` requires exactly a `Stream[E]` (a mismatch is `bynk.types.argument_mismatch`), and `Streaming(s)` in a pattern binds `s: Stream[E]`. With `E` omitted nothing changes: construction accepts either, and the pattern binds `Stream[String]`, so every existing route and golden is untouched and nothing breaks. An `HttpResult` that names none is compatible with one that does, and two that name different elements are not. A route that never streams may name an element; it is only what `Streaming` would carry. The runtime `HttpResult<T, E = string | SseEvent>` carries `E` on its `Streaming` variant, and its non-streaming constructors are `HttpResult<T, never>`, so they are assignable to any element. The wire contract, `bynk openapi` and the generated client are unchanged: a `Streaming` reply is already `events: AsyncIterable<string>`.

Two options were rejected. Reusing `T` as the element, `HttpResult[Stream[SseEvent]]`, is refused today by `bynk.types.stream_at_boundary`, which holds that a `Stream` never appears in a service handler signature; exempting it would contradict that rule, and `T` stays the success body's type. Inferring the element from the handler's body, as the issue first suggested, would make a signature depend on a body: editing a body would silently change what a test in another unit sees, and that test may be checked before the body that determines it.

**Consequences.** A route opts into the strictness by declaring `E`, and `HttpResult[T, SseEvent]` is the recommended spelling for a route that streams events. A route that does not keeps the old `Stream[String]` binding in tests, which the docs now say plainly. The change threads one optional field through `TypeRef::HttpResult` and `Ty::HttpResult`; the tree-sitter grammar gains a two-argument production for `HttpResult`.

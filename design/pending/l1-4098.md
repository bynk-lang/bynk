## ADR: wait-for-what-a-deploy-created
title: A deploy waits, bounded, for Cloudflare to show what it has just created
summary: after creating a queue, and before the triggers of a first upload it forgave, the deploy polls a read until the new resource is visible (1 s doubling to 8 s, for 30 s at most), failing at once on a failed poll and saying the platform is lagging when the wait runs out

**Context.** #4098. On a fresh account, a first deploy failed two or three times before it succeeded, each time on Cloudflare's lag right after a create. A queue Bynk had just created was missing from the queues listing for a few seconds, so wrangler's own provisioning created it again and was refused (11009). A new Worker's lookup answered `10007` after the upload; #3562 forgives that failure and runs the `triggers deploy` wrangler skipped, but that ran against the same lag and failed. A re-run about 20 seconds later succeeded every time.

**Decision.**

- **Wait for a known create, by reading.** After `create_queue` makes a queue, the queue step polls `queue_find` until the queue is listed. A queue the run found, not made, never waits. On the path #3562 already forgives, before `triggers deploy`, the first-deploy watch polls `GET /workers/workers/{script}`, the lookup that lagged, until it finds the script (a 404 or `10007` reads as not yet). Then the deploy carries on as before.
- **Bounded, with named pacing.** `visible::VISIBILITY_PACING` waits 1 s, doubling to 8 s between polls, and gives up after 30 s of waiting, with the reasoning beside it. The time counted is the time slept, so tests inject the sleep. The live check of a fresh-account first deploy is to set the real figure.
- **A failed poll fails at once.** A denied token, a server error or a transport failure is the deploy's failure, with that error; it is never waited past.
- **The lag is said plainly.** When the wait runs out, the deploy fails with `Cloudflare has not shown <the queue or Worker> 30 s after it was created: the platform is lagging behind the create. Run `bynk deploy` again to finish the deploy; nothing more is created`, instead of wrangler's internal error. The ledger already records what was created (record before push, and #3999), so the re-run only finishes.
- **Not a retry under ADR 0888 Decision H.** No failed request is repeated: only a read is asked again, for a resource this run is known to have created. The client's retry policy stays at one attempt.

**Consequences.** A first deploy no longer needs manual re-runs on the platform's lag, and a redeploy is unchanged (it creates nothing, so it never waits). The every-kind apply makes one more call per queue it creates (`queues info` after `queues create`). A platform stuck for longer than 30 s still needs a re-run, now named as such.

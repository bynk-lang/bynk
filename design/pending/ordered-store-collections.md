## ADR: ordered-store-collection-handles
title: An agent's store collections are insertion-ordered handles
summary: A store collection is held as a handle backed by a JS `Map`, not a plain object, behind an interface every method of which may be asynchronous

**Context.** The spec makes a `Map` insertion-ordered, but an agent's `store Map` was held in memory as a plain JS object, which enumerates integer-like keys (`"2"`, `"10"`) in ascending numeric order before every other key. A map put as `10, 2, a, 5` was read back as `2, 5, 10, a`, in a handler as much as after a reload. Per-entry storage (#3189) already stores each entry's insertion sequence, so the stored form could carry the order; the in-memory form could not.

**Decision.** Each `Map`, `Set`, `Cache` and `Log` field of the state is a handle: `StoreMap`, `StoreSet`, `StoreCache` (a `StoreMap` over `{ v, exp }` with `liveSize(now)`) and `StoreLog`, in the runtime's `store` module. A `Map` handle is backed by a JS `Map`, which keeps insertion order for every key (an overwrite keeps its position, a key removed and inserted again goes to the end), and it holds the posting lists of its `@indexed` fields, in insertion order, instead of a sibling `<map>__idx_<f>` state field. The stored layout is unchanged. The codec's wholesale-shaped record keeps each collection as a record or array, with the insertion order noted beside a record (a record cannot carry the order of its integer-like keys); `loadState` fills each handle from it and `commitState` encodes each handle to it. A held `Map[K, Connection]` stays in the `"state"` record as the object it has always been, so a build that predates this one still reads it (and, finding `<field>__order` undeclared, only warns about that key once, keeping it); the insertion order, which an object cannot carry for integer-like keys, is stored beside it as a `<field>__order` array of keys. A record with no such array reads in object order, and a stale array is tolerated (keys it lacks follow, removed ones are skipped). No `STORAGE_LAYOUT` change is needed: a rollback reads the same record, only in the older order. The interface (`StoreMapHandle`, `StoreSetHandle`, `StoreCacheHandle`, `StoreLogHandle`) returns `Awaitable` from every method, so a handle backed by per-entry storage can replace the eager one without a change to the emitted code. The eager classes the emitted state uses return plain values, so a store query stays a synchronous thunk over an array, and a query over a plain `List` is unchanged.

**Consequences.** A `Map` enumerates in insertion order for every key, on `bundle` and `workers`. The emitted state, its zero value, its rehydration, its encoding and every store operation change shape (the goldens of every agent with a collection), and the `@indexed` posting lists leave the state record. Making a store query asynchronous, which a storage-backed handle needs, is left to that handle's change; this one keeps the queries synchronous.

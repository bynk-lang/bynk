## ADR: partial-content-validators-and-if-range
title: A 206 or 304 carries the handler's own validator, and a stale If-Range is never answered with a 206
summary: The etag and lastModified helpers, the ifRangeHolds commons function, and the router's fail-closed safety net for If-Range

**Context.** #4466, a follow-up to #4389 (ADR partial-content-and-not-modified). `PartialContent` and `NotModified` could not carry a validator, because `ETag` and `Last-Modified` are headers the router owns, so a client could not resume a range download safely with `If-Range` (it had no validator to send back) and a handler answering `304` itself could not say which representation it was for. The issue also asks that the router honour `If-Range`.

**Decision.** (A) Two typed helpers beside `retryAfter`, `at` and `download`, written on the variant itself: `etag(tag: String)` and `lastModified(at: Instant)`, for `PartialContent` and `NotModified` only. They are additive: no variant changes shape, so nothing breaks. The router still owns `ETag` and `Last-Modified` everywhere else (`RawTagged` is how a 200 gets its own). `etag` takes an RFC 9110 entity tag, checked at compile time for a literal (`bynk.http.invalid_response_header`) and at run time for a computed one (a fault). `lastModified` writes an IMF-fixdate to the second, and faults on an instant outside the years 0 to 9999 (an IMF-fixdate has a four-digit year). (B) `If-Range` has two possible designs. Router-side, the router would serve the full body when the validator is stale; but a `PartialContent` already holds a start..end stream, the router does not parse `Range`, and the only way to give it the whole body is a second field on the variant, a fallback thunk, which changes a variant #4389 has only just defined and makes the response depend on a closure the router calls. Handler-side, a pure function answers the question and the handler picks `PartialContent` or a full `RawStreamed`. This ADR takes the handler-side design: `uses bynk.range` brings in `ifRangeHolds(ifRange: Option[String], etag: String) -> Bool`, a new first-party commons (id block 15), written in Bynk like `bynk.html`. It is `true` with no `If-Range`, and when the `If-Range` is exactly `etag` and neither is weak (the strong comparison RFC 9110 §13.1.5 requires); a date `If-Range` never holds, so the handler answers the whole body, which is always correct. The commons is not `bynk.http`, because `http` is a reserved word in a commons name. (C) A handler that skips the check would send bytes of a changed representation, which is the corruption `If-Range` exists to prevent, so the router also fails closed: on a `GET` whose request carries `If-Range`, a `206` is compared with the validator the handler attached, an entity tag against `etag` (strong) and a date against `Last-Modified` (exact). A match sends the `206`. A mismatch, or a `206` with no validator, is not sent: the route answers `500` and logs `PartialContent for a stale If-Range: check ifRangeHolds before answering 206`. The check sits in the router's existing conditional-`GET` step (`notModifiedIfMatch`), so no emitted entry changes, and it runs after the router's own `If-None-Match` handling, which RFC 9110 §13.2.2 evaluates first: a matching `If-None-Match` is a bodyless `304`, which cannot leak stale bytes, so only a `206` that survives it is checked against `If-Range`.

**Consequences.** A handler can serve a resumable download: it attaches its object's `etag`, asks `ifRangeHolds`, and answers 206 or 200. A date `If-Range` is honoured by the router's net but not by `ifRangeHolds`; a handler wanting it compares the date itself. The router never converts a 206 into a 200, so a forgotten check is a visible `500` and a log line, not a silent wrong answer. `bynk.range` takes id block 15. Not done: parsing `Range` for the handler, an automatic `416`, and a `lastModified` finer than a second.

## ADR: bynk-client-typed-typescript-client
title: `bynk client`, a typed TypeScript client for `from http` services
summary: A generated single-file module with an inlined runtime, optional values as `T | null`, refinements checked on encode and decode, and per-route response unions

**Context.** A front end (SvelteKit, Next.js, anything that can `fetch`) calling a Bynk `from http` API either hand-writes types and `fetch` calls or generates them from `bynk openapi` with a tool that cannot know Bynk's codecs. The compiler holds every fact needed to emit the client itself: the wire-contract IR that drives the emitter's codecs, the editor's wire peek and `bynk openapi`. The foreign-caller client (`bynk-client.ts`, #1970) signs every call with a per-edge secret and addresses `/_bynk/call/<service>`, so it is wrong for a browser. #3508 proposed the surface and the maintainer accepted its recommendations, with one change: **optional values appear in the generated TypeScript as `T | null`**, not as Bynk's tagged `Option`, and the client converts at the boundary using the same codecs as the server.

**Decision.** This increment is slice BC1 of #3508, the minimal useful client. Decisions A to K of the proposal stand as recommended, with the change above.

- *Surface (A).* `bynk client [INPUT] [--out FILE] [--service NAME]...`. `INPUT` defaults to `.`, the project must check clean, and the module goes to stdout without `--out`. `--service` is repeatable and takes `Name` or `unit.Name`; a client for several services is one `createClient` with one property per service, so two services answering the same method and path are not an error. The default layout is a single file. `--check`, `--layout dir` and the `[build.client]` manifest key are slice BC2.
- *Output (B).* A generated file committed in the front end's repository, headed `@generated` and marked experimental. The runtime is inlined, not imported: a browser-safe subset (no signing, no Web Crypto, no Workers types) written in `bynk-emit/src/emitter/http_client_runtime.ts`, plus the runtime's own `result`, `bytes`, `decimal`, `time` and `keys` modules for just the names the generated codecs use. A guard test holds the restated `BoundaryError`, `JsonValue` and `ValidationError` types equal to the runtime's. No npm package.
- *Codecs (C).* The codecs are the foreign-caller client's: `emit_helpers_for_owner_qualified` under a qualifier, with call sites named through `serialise_expr_via` and `deserialise_ref_via`. The shared closure and rename step moved to `client::surface_closure`, which both clients call. Because the codecs speak `Option`, every boundary type is declared twice: the *wire* type (`__Wire_Order`, what a codec makes and takes) and the *public* type (`Order`, with `T | null`), with generated functions between them. A type with no `Option` reachable has no conversion. A request writes `Some` and `None` in the tagged form, which the server's lenient decoder reads; a response is decoded by that same lenient decoder, so a route's tagged or plain-JSON mode (ADR 0723) gives the same `null`. An `Option[Option[T]]`, or an `Option` inside a `Map`, `Set` or `Result`, has no `T | null` form, so a route that holds one is left out and named. `Instant` and `Duration` stay `number`; an opaque type is branded and never checked.
- *Refinements on both sides.* On encode the generated function runs the decoder the server runs over the value it just encoded, so a violation is returned as `CallFailure` `Invalid` before any request is made, with the server's path and message. On decode the response is checked by the same codec.
- *Results (D).* Each call returns `Promise<RouteResponse | CallFailure>` and never throws. `RouteResponse` is a union keyed by `status` carrying the `HttpResult` variant name as `kind`, with the members `bynk openapi` documents for the route, from the same wire peek. Open question 2 (two variants sharing a status) is settled against the registry: within the supported variants a status maps to one variant, except `400`, `413` and `415`, where a handler's own message variant and the boundary's own refusal share a status; both are members, told apart by `kind` and by the body's shape (`{ error }` against `{ kind }`). `Invalid` carries a `BoundaryError`, the shape the server's `400` has, rather than the sketch's bare `ValidationError`, so the path survives.
- *Transport (E).* `createClient({ baseUrl, fetch, headers, credentials, origin })`. `fetch` is injected and called with a standard `RequestInit`; a per-call `init` merges over the client's defaults. `headers` is a value or a possibly async function. `origin` is sent as `Origin`, for a framework's server calling a cookie-authenticated route (the CSRF seam of #3386); a browser sets its own and ignores it. Whether a Workers-hosted server runtime may set `Origin` on an outgoing `fetch` is not verified here; the reference says only what the option does. The `Transport` seam and Service Binding transport are BC5.
- *Naming (open question 4).* A function is named from the method and path: `GET /orders/:id` is `getOrderById`, `POST /orders` is `postOrders`, a static segment before a parameter is singular. Two routes of a service that share a name are a command error naming both.
- *Left out in BC1.* A `@form`, `@multipart` or `@raw` body, a typed `cookies` record, a route that can answer a raw or streamed body, a route guarded by a request signature, and a route whose types have no `T | null` form are named on stderr and left out, never emitted wrong. If every selected route is left out the command fails. They arrive in BC3 and BC4. A redirect answer is a member of the union, but `fetch` follows redirects by default, so it appears only under `redirect: "manual"`.
- *Out of this slice.* `--check`, `--layout dir`, `[build.client]` (BC2); `credentials`/cookie recipes and form encoders (BC3); raw bodies and streams (BC4); the `Transport` seam (BC5); the HTTP contract hash and `API_CONTRACTS` (BC6); the example front end, recipes and editor command (BC7). Open questions 3 and 9 stand as recommended: the server does not reject a stale client, and the HTTP JSON encoding is read from the same wire IR as wire version 1, so `WIRE_VERSION` is embedded as documentation.
- *Size, measured.* Bundled with esbuild 0.24 (`--bundle --minify`, tree-shaking the inlined runtime to what `createClient` reaches): a one-route client (`GET /hello/:name`, string in and out) is 2.4 KB minified and 1.1 KB gzipped; three routes with refinements, a sum and path parameters, 8.4 KB and 2.7 KB; five routes with `Option`, a generic page, an opaque id, `Decimal`, `Instant` and a typed query, 14.4 KB and 3.4 KB. The cost grows with the codecs the routes reach, not with the project. The `--no-validate-responses` flag of the proposal is not added: the measured cost does not yet justify it.

**Consequences.** A new command, a new generated file the author asks for, and no change to what a Worker serves or to any other output: a project that never runs `bynk client` builds byte-identically, and `bynk openapi` and the foreign-caller client are untouched apart from the shared closure helper. The generated module's shape is a public surface from this release, shipped as experimental; member names may change in a minor version until it is stabilised. The system tier runs a generated client against a compiled Worker both in process and under `wrangler dev`, and type-checks each generated module under `tsc --strict`. `bynk openapi` stays the language-neutral contract; the two share the wire peek and so cannot disagree on a shape or a status.

## ADR: api-key-mint
title: `Actor.mint(identity, label)` makes an API key in a service handler, stores only its digest, and answers it once
summary: The first `ApiKey` member, its type and where it is legal, the generated agents' slice-1 shape, and how the `system` tier tests the seam

**Context.** The API keys track (`design/tracks/api-keys.md`, spine #3939) settles the key format, the peppered storage and the verification contract up front (the three ADRs of slice 0). It records the members' shapes in the slices that ship them. Slice 1 ships verification and `mint`, because a scheme that verifies keys nobody can mint ships nothing usable (§14).

**Decision A — `mint`.** `Actor.mint(identity, label)` on a local `ApiKey` actor is `Effect[Result[ApiKeySecret, TooManyKeys]]`. It takes the actor's own identity type and an `ApiKeyLabel` (1 to 64 characters, none of them a control character), needs `given Clock` for the key's creation time, and is legal only in a service handler, where the pepper is (`bynk.actor.api_key_mint_outside_handler`). The runtime draws the key number and the 32-byte secret, digests the secret under the pepper, and asks the identity's `<Actor>KeyOwner` to store the digest. That handler files it in `<Actor>Keys(handle)`, taking the handle a fresh one when the identity has none or its store is retired. `TooManyKeys { limit }` is the answer when the identity holds 100 keys. Expiry is not a `mint` argument (Q5): `ttl` is a later slice, so `expires` is `None`.

**Decision B — the key goes out once.** `ApiKeySecret` is `{ id: ApiKeyId, key: ApiKeyValue, label: ApiKeyLabel, created: Instant, expires: Option[Instant] }` in the `bynk` prelude, with `ApiKeyId`, `ApiKeyLabel` and `TooManyKeys`. All five are experimental under `[unstable] allow`. `ApiKeyLabel` is a name the track did not list; it is the refined label type §9 describes. A type that holds an `ApiKeyValue` is `bynk.types.secret_at_boundary` everywhere but one place: an HTTP handler's `Effect[HttpResult[ApiKeySecret]]`, whose codec reveals the key on the wire. No Bynk code can build an `ApiKeyValue`, so every `ApiKeySecret` is one `mint` answered.

**Decision C — the agents' slice-1 shape.** `<Actor>Keys(handle)` keeps one `Map` per field (digest, `kid`, label, created and an empty scope set), keyed by key number, beside the identity and a `retired` flag. Parallel maps rather than a record keep the reserved names to the two agents. `verify(keyNo, presented, first, dummy)` compares exactly once: against the record's digest when there is a record whose `kid` the seam sent, else the presented digest against the dummy. It admits only a real record that matched. The pepper is threaded to `mint` in `deps.__apiKey`, and `callDurableObjectMethod` drops that key from every agent call's body, so no pepper reaches an agent (D2 B).

**Decision D — the `system` tier.** `by Client("acct-7")` mints a real key into the in-process store, once per identity, under the suite's pepper. `by Malformed` (a bad checksum), `by Unknown` (an unknown key number, then an unknown handle) and `by Forged` (the real id with a foreign secret) are the failure principals. Each also counts the store's `Crypto.equal` calls over the platform binding the in-process agents construct, and fails the case unless the seam compared none, once against the dummy, or once against the record, respectively. `by Nobody` reaches the seam as on any secured route. Below `system` the identity is given. `bynk test --against` refuses a case acting as an `ApiKey` actor (`bynk.test.remote_unsupported_api_key`).

**Decision E — what slice 1 refuses.** `previous` and `ttl` are refused (`bynk.actor.api_key_unknown_key`) until slice 3 reads them. An `ApiKey` actor is not admissible on a WebSocket `on open`, or as an actor-sum member until slice 4 (`bynk.actor.scheme_not_admissible`). `key: identity` stays `bynk.http.rate_limit_key_unavailable` until slice 2. `by Expired` and `by Revoked` are refused on an `ApiKey` route. `bynk.actor.api_key_unlimited` warns on a route with no `clientIp` rate limit.

**Consequences.** A service can mint keys and authenticate requests with them, with no hand-written cryptography. Listing and revoking keys (slice 2), expiry, last use and rotation (slice 3), sums (slice 4), and OpenAPI and the client (slice 5) follow. `bynk deploy` mints the pepper as a Worker secret through the `SignedCookie` key path; live check K1 confirms that on a real account before this slice counts as done.

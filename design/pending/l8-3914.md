## ADR: www-authenticate-on-401
title: Every 401 carries a WWW-Authenticate challenge
summary: The challenge follows the route's actor, uses a registered scheme where one exists, and is exposed to browsers by CORS

**Context.** RFC 9110 §15.5.2 says a server generating a `401` MUST send a `WWW-Authenticate` header with at least one challenge. Bynk sent none: the `Bearer`, `Oidc`, `Signature` and `SignedCookie` seams answered a bare `401`, and so did a handler's own `Unauthorized`. Clients that read the challenge (the scheme, or RFC 6750's `error="invalid_token"` to refresh a token) got nothing.

**Decision.** (A) `Bearer` and `Oidc` routes answer `Bearer realm="<context>"` per RFC 6750, adding `error="invalid_token"` only when the request presented a bearer token (a missing token gets the bare challenge, §3.1), and never an `error_description`, whose text could reveal why verification failed. (B) Where no scheme is registered, a `Bynk-` scheme: `Bynk-Signature realm="…", header="<the actor's header>"` and `Bynk-Cookie realm="…"`, so the RFC's MUST is met without implying a protocol a generic client might try to speak. A route with no verifying actor (`Visitor`) answers `Bynk realm="…"`. (C) `realm` is the context's qualified name: stable, and no more than the service's own identity. (D) The router wraps each route's response in `applyChallenge`, so a handler's own `Unauthorized` carries the route's challenge, and so does a `401` rendered through `on rejected` (its other headers are kept, as a `405`'s `Allow` is). A sum of actors lists one challenge per member, in the sum's order. The WebSocket upgrade's `401` is wrapped the same way. (E) A CORS service adds `WWW-Authenticate` to `Access-Control-Expose-Headers` on a response that has one.

**Consequences.** Observable change is a header added to `401`s; no status changes and no program stops compiling. The `error="invalid_token"` parameter is decided from the request's `Authorization` header, not from why the seam failed, so a handler's own `Unauthorized` on a request that did present a token also carries it. Emitted entries gain one `applyChallenge` call per route and re-bless.

## ADR: each-implicit-workspace
title: An opt-in implicit workspace for a manifest-less directory of projects
summary: `--each` on `check` and `test` runs the immediate-subdirectory projects as a synthesised `members = ["*"]` workspace

**Context.** After #3248, `bynk check`, `test` and `compile` refuse a directory that has no `bynk.toml` at or above it but holds projects below it. The only way to run such a directory (bynk-lang/showcase, about 27 independent projects, is the motivating case) was to add a root `[workspace]` manifest the repository may not want. #3258 asked whether the directory could be an implicit workspace instead, and the proposal (#3274) settled the forks; the maintainer accepted it as recommended.

**Decision.** Opt-in, not automatic: `--each` on `check` and `test` only. Without it the refusal stays the default, and now names the flag (for `compile`, which cannot take it, the message is unchanged). Automatic running was rejected because a command typed in the wrong directory would silently run an unbounded number of projects, and for `test` execute their code; an environment variable or config setting was rejected as invisible action at a distance in a directory that has nowhere to keep config. Discovery is the immediate subdirectories that hold a `bynk.toml`, matching `members = ["*"]`, not any depth: the two forms mean the same, and the run set is the directories `ls` shows. `out`, `node_modules` and hidden directories are never members, and a project inside a member belongs to it. The implicit workspace is a `Workspace` value built by `bynk_project::implicit_workspace`, so `run_check`, `bynk test` (the workspace loop, filter validation and flag refusals), `--fix` planning and `--emit` run it down the existing workspace path with no second loop. One deliberate difference from a real `members = ["*"]`: a subdirectory with no manifest is skipped (with a note if it holds `.bynk` files) instead of failing the whole run, since a repository of examples routinely keeps a `docs/` beside them. Other behaviour follows from the shared path: a member that cannot load is reported under its header and the run continues and fails at the end, and the exit code is non-zero if any member failed. `--each` is accepted and inert at a real workspace root, and an error at a project, inside one, on a file, in a directory holding no project (naming any deeper ones), or in a directory with `.bynk` files of its own, so the flag never silently does nothing. `fmt` is unchanged.

**Consequences.** One new flag on two commands, no change to a program's meaning, the checker, emitter or runtime. Each member is prepared (dependencies fetched, lock read) and run as when it is run alone, and one that fails to prepare is named and does not stop the others from running (the run still fails). A refused `--each` prepares nothing. Each member: it keeps its own `bynk.lock`, there is no shared `[registries]`, and a dependency's own path dependencies are still refused outside a real workspace (a project's direct path dependencies on a sibling work as they do alone). The language server needs no change: it already treats each directory holding a `bynk.toml` under a workspace folder as its own project, so a test pins that a manifest-less folder of projects is analysed per project. No change to hover, completion, semantic tokens or signature help. The flag is not offered on `build`, `compile`, `deploy`, `dev`, `tail`, `migrate` or `revert`, which act on one deployable project; a later `compile --each` would need a story for per-member output and failure.

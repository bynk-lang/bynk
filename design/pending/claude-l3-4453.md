## ADR: hover-names-the-plain-wire-shape
title: A field's hover names the plain-JSON shape the routes that write it use
summary: Which fields and routes the hover section covers, how the reach is decided, and what is left unsaid

**Context.** #4453, from #3974 (#4452): a route with `json { options: plain }` writes an `enum` as a bare string, a `String`-keyed `Map` as a JSON object and an `Instant` as RFC 3339 text, but a field's hover showed only the Bynk type, so nothing in the editor said the wire form differs from the tagged one.

**Decision.** (A) The section is appended to the hover of a record field (`SymbolKind::Field`), after what the hover already said, as the wire-contract appendix is for a service. It reads the project's boundary tables (`ContextBoundaryInfo`), the same source the wire-contract peek uses, so no new analysis pass is added. (B) A route is plain by `effective_json_options` (its own `@json(options:)`, else the service's `json { }`), the function the emitter and OpenAPI read, so the hover cannot disagree with what the route writes. (C) A route writes a type when the type is its response type or reached from it through record fields, variant payloads, a generic application's declaration and arguments, and the `Option`, `List`, `Map`, `Set` and `Result` they sit in; only the response is read, because the option is about how the response body is written. The reach is by type name in the route's own table, so two units that each declare a same-named type are read as one: the section can name a route that writes a same-named type, and cannot miss a route that writes this one. (D) Only the three shapes #3974 added are described: an `enum` (a sum whose variants carry no payload), a `Map` whose key is a `String` or a refined or opaque `String`, and an `Instant`, alone or inside an `Option` (`null` for `None`) or a `List`. Any other field keeps its hover. (E) The routes are listed (`GET /plain`, up to three, then a count), and a type only tagged routes answer with gets nothing, which is the "unchanged on a tagged route" the issue asks for. A type reached by both forms lists only the plain routes and says the tagged form is kept elsewhere.

**Consequences.** Hover tests cover an `enum`, a `Map[String, _]` and an `Instant` field on a plain route, the same fields on a tagged route (unchanged), a field with no plain-only shape (unchanged), a type reached only through an `Option`, a generic application, a `Set` and a variant payload, a route's own `@json` overriding its service's in both directions, the `Option` and `List` wording, and the "and N more" count. Not done: the shape of a request body (the option governs responses) and a section for a generic record applied to a type argument.

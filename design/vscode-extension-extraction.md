# Extracting `vscode-bynk` into its own repository

**Status:** draft for discussion — nothing here is decided. Forks marked
`[DECISION]` carry a recommendation.

## 1. Why, and why not

`vscode-bynk/` is a self-contained TypeScript project (~850 KB, 80 of the
repo's 179 commits touch it) living inside a Rust workspace. It already
consumes the compiler as a *released binary*: `bynkServerVersion` in
`package.json` pins a GitHub Release, and `src/server.ts` /
`src/toolchain.ts` download `bynkc-lsp`, `bynk` and `bynkc` from it (#1673).
The playground (`bynk-lang/playground`) is already extracted on the same
model, consuming `bynk-web-<tag>.tar.gz`.

**Gains:** independent release cadence (a client-only fix no longer rides a
workspace release); the main repo's CI sheds Node, xvfb and the VS Code
download; a contributor surface that doesn't need a Rust toolchain.

**Costs:** a server change and its client change stop being one atomic PR; the
pre-merge guarantee "this server change doesn't break the client"
(`extension-tests` builds `bynk-lsp` from source) is lost unless replaced
(§5); three Rust drift guards lose their inputs (§4).

**Recommendation:** proceed, but only with §4 and §5 landed first — the
extraction is safe exactly to the degree those two replace what the monorepo
gave for free.

## 3. History split

Use `git filter-repo --subdirectory-filter vscode-bynk` on a fresh clone, not
the working repo:

1. `git clone --no-local bynk bynk-vscode-split && cd bynk-vscode-split`
2. `git filter-repo --subdirectory-filter vscode-bynk --tag-rename '':'bynk-main-'`
   (monorepo tags are release tags for the *compiler*; keep them namespaced or
   drop them rather than letting `v0.405.4` mean two things).
3. Rewrite `package.json` `repository` to the new URL; keep `publisher:
   bynk-lang` so the Marketplace identity and install base are unchanged.
4. Commit messages carry `(#NNNN)` issue refs that point into the old repo.
   Either leave them (GitHub auto-links bare `#N` to the *new* repo — wrong) or
   `--message-callback` rewrite to `bynk-lang/bynk#NNNN`. **Recommend rewrite**.
5. Push as `bynk-lang/vscode-bynk`; protect `main` with the same ruleset
   (required check, merge queue, stamp-App bypass if the pin job survives).

`[DECISION]` Alternative: `git subtree split` keeps tags out of the picture but
loses nothing else; filter-repo is preferred for the message rewrite.

The old directory is removed in one PR in the main repo *after* the new repo
publishes a release from its own CI (§8), leaving a `vscode-bynk/README.md`
stub is **not** recommended — the docs pages point at the new repo instead.

## 4. Replacing the drift guards

The three guards exist to catch *the compiler changing and the extension
lagging*. After the split the direction of data flow must be: compiler
publishes, extension verifies.

**Mechanism — a released `editor-contract` artifact.** Add to `release.yml`
(next to `web-assets`) a small asset `bynk-editor-contract-<tag>.json`,
generated by an `xtask` subcommand from the same Rust sources the tests use:

```json
{
  "version": "v0.405.4",
  "reservedKeywords": ["…bynk_syntax::keywords::KEYWORDS…"],
  "semanticTokens": { "types": [...], "modifiers": [...] }
}
```

The extension repo's CI downloads the contract for the pinned
`bynkServerVersion` and runs the three checks in TypeScript/Node against it:

- **Keywords** (`textmate_keywords`): every reserved keyword appears as a whole
  word in `syntaxes/bynk.tmLanguage.json`. Direct port of the Rust test.
- **Legend** (`legend_drift`): custom token types/modifiers in `package.json`
  `semanticTokenTypes/Modifiers` mirror the contract's custom entries.
- **Snippets** (`scaffolds_compile`): this one needs the *compiler*, not just
  names. In the extension repo, expand each snippet body (substituting default
  placeholders as the Rust test does) and run the downloaded `bynkc check` on
  the result. The binary is already downloaded for `extension-tests`.

**Timing caveat — the guard now fires one release late.** Today a keyword added
in a PR fails that PR. After the split the extension only learns at the next
pin bump. Close the gap with the compatibility job in §5, which runs the same
checks against the *latest main build*, and — the cheap half — keep a
reverse guard in the main repo: a test that fails when
`KEYWORDS`/legend change without a bump of a checked-in
`editor-contract.snapshot.json`, with the PR template prompting "does the
extension need a change? file an issue in `bynk-lang/vscode-bynk`". A snapshot
diff is a visible, reviewable signal that a contract changed.

`[DECISION]` Contract-as-release-asset (recommended) vs. a git submodule /
vendored copy of the three extension files in the main repo. Vendoring keeps
the Rust tests as-is but creates two sources of truth that themselves drift.

Remove from `bynk-lsp/Cargo.toml` the `exclude` entries and doc comment for
`legend_drift` / `scaffolds_compile`, and delete the three tests once the
snapshot guard lands.

## 5. CI in the new repo

Port from `ci.yml`, keeping SHA-pinned actions and the Node 24 floor:

- **extension** — `npm ci`, `npm run check`, build, `check-bundle.mjs`, web
  bundle, `@vscode/test-web` smoke tests, `vsce package`.
  - Web build: replace `npm run build:wasm` with a download of
    `bynk-web-<pinned tag>.tar.gz` unpacked into `wasm/`; the Rust/wasm toolchain
    drops out of this repo entirely. `scripts/build-wasm.sh` stays in the
    compiler repo, where `package-web-assets.sh` already calls it.
- **extension-tests** — same xvfb/`@vscode/test-electron` suite, but
  `runTest.ts` points at `bynk`, `bynkc`, `bynkc-lsp` **downloaded from the
  pinned release** into `.bynk-test-bin/` instead of `../../../target/release`.
  Drop its read of the workspace `Cargo.toml` version (use the pin).
- **server-pin** — `check-server-pin.sh` moves over unchanged apart from
  `GITHUB_REPOSITORY` defaulting to `bynk-lang/bynk` (already the default; make
  it explicit and use a read token).
- **contract** — the §4 checks.
- **compat (scheduled + manual)** — nightly job that builds
  `bynk-lsp`/`bynkc`/`bynk` from `bynk-lang/bynk@main` and runs the full
  integration suite plus the §4 checks against that build. This is the
  replacement for the lost pre-merge coupling; a red nightly opens an issue in
  the extension repo. Cost: one Rust build per night.
- **Main repo side:** a `repository_dispatch` from `release.yml` after
  `github-release` (event `bynk-release`, payload `{tag}`) so the extension
  repo reacts immediately (§6) rather than polling.

Protocol compatibility: the extension and server communicate over custom
requests that change with the compiler. Define a **compat window** in
`package.json`: `bynkServerVersion` (exact, what is provisioned) and
`bynkServerMinVersion` (oldest server the extension still works against — used
when a user has a user-supplied `bynkc-lsp` on PATH). Today the pin is exact;
the min is new and should be checked in `server.ts`, surfacing a clear
"update your toolchain" message.

## 6. Release and versioning

Today: the extension version equals the workspace version, enforced in
`release.yml` `verify`, bumped by `bump-version.sh`, stamped on merge.

`[DECISION]` Versioning scheme after the split.

- **A. Independent semver (recommended).** The extension has its own version
  line; `bynkServerVersion` is the only link. Drop the `verify` equality check,
  the `vscode-bynk` lines in `bump-version.sh` and `stamp.yml`. Marketplace
  versions must be monotonic — start at a value above `0.405.4` (e.g.
  `0.406.0`) so existing installs update.
- B. Keep lockstep via cross-repo automation. Preserves "one version number" at
  the price of a bot in each repo and a failure mode when one side is red.

Release flow in the new repo (A):

1. `bynk-release` dispatch (or a manual run) → workflow runs
   `scripts/next-server-pin.sh <tag>` (same rules: no pre-release pin, never
   backwards), opens a **PR** (not a direct push — the bypass-App argument in
   today's `server-pin` job relied on the pin *and* tag being one decision; with
   independent versions a pin bump is an ordinary change worth CI) titled
   `chore: point at bynk vX.Y.Z`, runs the full suite incl. §4 contract against
   the new pin, and auto-merges on green.
2. Cutting an extension release = tagging `vX.Y.Z` in the new repo → `vsix`
   job builds with the pin as committed (the current "move the pin to this tag
   first" step goes away: the pin is now already correct on `main`) → publishes
   to the Marketplace with `vsce publish --azure-credential --skip-duplicate`
   (secrets/OIDC federation re-created for the new repo; Open VSX if/when wanted).
3. The old `vsix`, Marketplace publish and `server-pin` jobs are deleted from
   `release.yml`; the `workflow_dispatch` input that publishes the extension
   goes with them.

Also move/rewrite `xtask/tests/server_pin.rs` (tests `next-server-pin.sh`) into
the new repo with the script.

## 8. Sequencing

1. **Prep in-place (main repo, no behaviour change):** emit the
   `editor-contract` asset in releases; port the three guards to Node *inside*
   `vscode-bynk` running against the asset; add the snapshot guard. Both old
   and new guards pass.
2. **Make the extension standalone in-place:** `build:wasm` → web-assets
   download; `runTest.ts` → downloaded binaries; `bynkServerMinVersion`. Prove
   it by running the extension CI from a copy of the directory outside the repo.
3. **Split:** filter-repo (§3), create the repo, port workflows, publish a
   first release from the new repo (version above the last monorepo one).
4. **Cut over:** remove `vscode-bynk/` and the Rust guards, update docs, drop
   the release jobs — one PR, after step 3's release is live on the
   Marketplace.
5. **Watch:** first nightly compat run; first auto pin-bump PR end to end.

Steps 1–2 are valuable on their own and reversible; the decision to actually
split can be taken after step 2 with the real cost in hand.

## 9. Risks

- **Marketplace publish credentials** for the new repo (Azure federated
  credential bound to the old repo's workflow identity) — set up and dry-run
  before cutover, or the first release blocks.
- **Contract drift unnoticed** between nightly runs — mitigated by the snapshot
  guard making contract changes visible in the compiler PR.
- **Contributor friction** for features spanning compiler + client: two PRs,
  ordered by release. Document the protocol-change recipe (server first behind
  a capability flag, client after the pin bump).
- **Issue/PR links** into the old repo; mitigated by the message rewrite and a
  redirect note in the old directory's last commit.
- **`.vscode-test` cache, `package-lock.json`, Dependabot** configs need
  recreating; low risk.

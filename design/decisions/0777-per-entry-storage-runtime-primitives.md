# 0777 — The per-entry storage runtime: key layout, a staged write-set flushed in one transaction, and the wholesale split

- **Status:** Accepted (v0.528)

**Context.** The per-entry storage track (`design/tracks/per-entry-storage.md`, #3195, proposal #3189) moves `Map`/`Set`/`Cache`/`Log` entries and `@indexed` postings from the single `"state"` value to keys of their own. Its first slice is the runtime half: nothing emitted calls it yet, and the emitter is wired to it by the slice that changes the layout. The spike (recorded on the track doc, §5) established what the primitives may rely on: Cloudflare documents up to 128 keys per batched `get`, `put` and `delete`; each call is atomic; puts issued with no `await` between them coalesce atomically, but no size limit is promised for that; `transaction()` is still available on SQLite-backed objects although the documentation calls explicit transactions "no longer necessary"; and keys list in UTF-8 byte order.

**Decision.**

1. **Key layout.** One letter per kind, then the field, then the entry: `m/<field>/<k>` (a `Map` or `Cache` entry), `s/<field>/<k>` (a `Set` element, value `1`), `l/<field>/<t>-<seq>` (a `Log` entry), `i/<field>/<index>/<by>/<pk>` (one posting, value `1`), `x/<field>/<exp>/<k>` (a `Cache` expiry entry), `c/<field>` (per-collection metadata). Every part is escaped so that the separator cannot appear inside one (`%` becomes `%25`, `/` becomes `%2F`); the escape is reversible, so a listed key decodes to its entry key. Times and counters are zero-padded to fixed width (16 and 10 digits) so byte order is numeric order. The `"state"` key and the `__layout` marker in it are unchanged by this slice; `__layout: 2` names the per-entry layout and an absent marker the wholesale one.
2. **No key-length cap.** The proposal's `StorageKeyTooLong` fault was to guard a 2 KiB platform limit. The spike found that limit applies only to the key-value-backed backend, which `bynk deploy` no longer emits (ADR 0438); on SQLite-backed objects a key and its value share one 8 MB limit. No cap is added; a key too large for its value fails as the platform's own error.
3. **One staged write-set, flushed in one transaction.** `EntryOverlay` holds a handler's puts and deletes. Reads see them (read-your-writes, ADR 0109 D2), a ranged read merges them into storage's result and stays bounded (it asks storage for only as many extra entries as the handler's own deletes in range could remove), and nothing reaches storage until `flush`. `flush` writes every staged put and delete, plus the `"state"` record, inside one `storage.transaction`, in batches of at most 128 keys. A throw anywhere rolls the whole flush back and leaves the overlay as it was; a handler that faults calls `discard`. The flush does not rely on write coalescing, because Cloudflare does not promise it has no size ceiling, and a flush can be many thousands of keys. It uses the asynchronous `transaction()`, whose commit-or-abort behaviour is documented and was confirmed on workerd; a `transactionSync` flush over `storage.kv` is the alternative if `transaction()` is withdrawn.
4. **The split from wholesale.** `splitWholesale` turns a wholesale `"state"` record into the trimmed record (collection and posting fields removed, `__layout: 2` set, `__v` and every other field kept) and the per-entry writes, without changing its input. It is the core of the lazy upgrade the emitter will run in `loadState`.
5. **The test storage.** `InMemoryStorage` gains the batched forms, `list` with `start`, `startAfter`, `end`, `limit` and `reverse` in UTF-8 byte order, and `transaction`. It refuses a batch over 128 keys, as the platform documents, because workerd run locally does not, and a test passing locally with a larger batch would prove nothing. It counts operations (`stats`) so a behavioural fixture can assert that a handler's I/O does not grow with the size of the state.

6. **Two limits of the double, stated.** It refuses an `undefined` value, as the platform does. It refuses overlapping or nested transactions on one storage, where workerd would serialise them; a behavioural fixture that runs two handlers on one agent at once must go through the per-instance queue (#3202), and a failure of that kind is a test bug, not a storage one.
7. **Order is left to the layout slice.** Keys list in the UTF-8 byte order of the encoded key, which is not the iteration order of a wholesale `Record` (integer keys first, then insertion order) and, because `/` is escaped to `%2F`, not always the raw key's own order. Which order `Map` iteration and `Query` results promise is settled by the slice that changes the layout; nothing here promises one.

**Consequences.** No emitted code changes and no stored data changes: the runtime module `entries` is emitted only into a project that imports it, and nothing does. The `DurableObjectStorage` interface the runtime speaks gains the batched, ranged and transactional forms, which a real SQLite-backed Durable Object already provides. The layout itself, the lazy upgrade, the index-routed read and the `Cache` and `Log` housekeeping follow in later slices of the track. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

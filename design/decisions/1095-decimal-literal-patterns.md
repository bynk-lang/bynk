# 1095 — A `Decimal` literal pattern matches by value; a `Float` literal pattern is refused with a reason

- **Status:** Accepted (v0.819)

**Context.** #3973. `match d { 1.20d => … }` and `match x { 0.1 => … }` both failed with the generic parse error "expected identifier as a match-arm pattern, found float literal", and the grammar's `literal_pattern` read as admitting them. For a `Float` the refusal is right, since exact equality on floats is a trap and `NaN` never equals itself, but the reason was never stated. For a `Decimal` there is no such problem: `==` compares by value (`1.20d == 1.2d`), so a literal pattern is well defined, and a price tier, a VAT rate or a fixed fee is naturally a literal match.

**Decision.** (A) A `Decimal` literal pattern compares with `Decimal` equality, so `20d`, `20.0d` and `20.00d` match the same values. Like a `String` literal it never completes the type: a `Decimal` match needs a `_` arm or a name. The pattern is kept in a normal form (no trailing zero in the fraction), so equality of patterns is equality of values, while the formatter prints the literal as written. (B) A second arm whose literal is equal by value to an earlier one is `bynk.types.unreachable_arm`, reported by the usefulness check; the `duplicate_literal_arm` report is not given for a `Decimal`, so that `20d` after `20.0d` and `20d` after `20d` read the same. (C) A `Float` literal parses, and the checker reports `bynk.types.float_literal_pattern` at the literal, top-level and nested, with the reason and the alternative. The issue's alternatives (`_ where InRange(0.0, 0.5)`, a `match` guard) do not apply, since a `Float` is not a `match` scrutinee at all, so the note points at an `if` comparison instead. (D) A negative literal (`-1.5d`) is a pattern, as `-5` is.

**Consequences.** The grammar's `literal_pattern` admits a decimal and a float literal, in the tree-sitter grammar and the hand-written parser. A `Decimal` arm lowers to `__bynkDecimalEqual` in the `if` chain, and a match with one never takes the `switch` path; no runtime changes. A `match` on a `Decimal` is now accepted (it was `match_non_sum_discriminant`), and the message that remains for other types names `Decimal` among the primitives. A refined pattern on a `Decimal` stays an error, as before, though it now reads `pattern_type_mismatch`. Hover on a `Decimal` arm says it matches by value at any scale, for an arm (or an or-alternative) whose literal is followed by `=>` or `|`; a literal nested in a payload has no hover. New code: `bynk.types.float_literal_pattern`.

# 0537 — `bynk.schema.lock` records each agent class's stored state shape per version, and refuses a change deployed data cannot be read through

- **Status:** Accepted (v0.372)

**Context.** A deployed agent's `store` fields hold user data, and before this change nothing compared their shape across builds. Renaming `store owner: Cell[String]` to `store ownerName: Cell[String]` checked and compiled with exit 0: `ownerName` read as `""`, and the old value rode along unread (#539, the 2026-10-01 review §3.1). `bynk.schema.lock` recorded events only (ADR 0299). This is slice S0 of the state-migrations track (`design/tracks/state-migrations.md`, spine #2188, settled by #2189), proposal #2204, which also settled the five forks below.

**Decision.**

1. *Lock format.* `bynk.schema.lock` moves to `version = 2` and gains `[agents."<unit>.<Agent>"]` entries: a class `version`, a `floor`, and `shapes`, one snapshot per version from `floor` to `version`. Each snapshot records whether the change into it was additive, and one entry per `store` field: `name`, `kind` (the storage kind's head), `type` and `refinement`. The table is omitted when a project has no agents.
2. *The renderings reuse the contract walk (#2204 Decision A).* `contract.rs`'s canonical walk gains two storage modes beside the contract one. Both expand named records and sums structurally and sort fields and variants by name, as the contract form does. Unlike it, they carry no type names, because stored bytes carry none, so renaming a type is not a change. Two consequences follow from that, both found in review. Recursion closes with a positional back-reference, `@N` for the named type N levels out, instead of `@Name`, so renaming a recursive type is not a change either, while two different cycles still differ. A sum variant's payload renders like a record (`name: type`, sorted), because a stored payload is keyed by field name (`payload_prop`): renaming a payload field is a change, and reordering payload fields is not. `type` strips every predicate. `refinement` keeps them, including an opaque type's, which the contract form elides because a consumer cannot observe it but the stored owner re-validates. The contract form and its hash are unchanged.
3. *Agent fields carry no `default` axis.* Every `store` field already has a zero or an initialiser (`bynk.agents.non_zeroable_state_field`), so an added field is always readable. Initialisers and storage annotations are not part of the shape: neither changes what is on disk.
4. *Reconcile.* A new class baselines at version 1, with `additive = false`. An unchanged shape keeps its entry. Added fields, or a changed `refinement` with an unchanged `type` (#2204 Decision B), bump `version` and append an `additive = true` snapshot. A changed refinement also warns with `bynk.agent.refinement_changed`, because a narrowing faults on load under ADR 0124. A removed field, a changed `type` or a changed `kind` is `bynk.agent.non_additive_state_change`, and the entry is left untouched. A rename is a removal plus an addition. When exactly one removed and one added field share a kind and a structure, the diagnostic names the likely pairing. When several do, it says the pairing cannot be inferred; a pairing is never applied. A recorded class with no declaration is `bynk.agent.class_removed`. `parse` refuses an agent entry that breaks `1 <= floor <= version`, or that lacks exactly one snapshot per version from `floor` to `version`, as `bynk.project.schema_registry_corrupt`. Such an entry comes from a hand edit or a bad merge, and reconciling against it would silently re-baseline it. Renaming a context therefore presents as every one of its classes removed, and gets the same note. Slice S3, which gives class renames a declaration, inherits that case.
5. *The way past a refusal, until the migration slices land (#2204 Decision C).* The deploy ledger records no Durable Object classes (ADR 0194 D1, ADR 0443), so the toolchain cannot know whether a class was ever deployed. The note asks: a never-deployed class's entry can be deleted from the lock, which re-baselines it; a deployed one follows ADR 0124 D3's conventions. `class_removed` is not deferred to the rename/removal slice, because that would leave one of this slice's two loud failures silent.
6. *Upgrade (#2204 Decision E).* `parse` reads a v1 lock as v2 with no agents. A build writes it back as v2; `check` and `test` read it without writing (ADR 0493). An older toolchain fails on a v2 lock with its existing unsupported-version error. That refusal is the reason for the bump: `SchemaRegistry` has no `deny_unknown_fields`, so without it an older toolchain would parse the lock, drop `[agents]`, and write the lock back without it.
7. *Everywhere events reconcile, agents do.* That means the build, `check` and `test` read-only, and the editor's round (ADR 0494). Agent diagnostics are attributed to the agent's own file.

**Consequences.** A non-additive change to stored state is now loud before deploy rather than silent after it. A project's first build after this change rewrites its lock once, to v2 with every agent baselined, and that shows in the diff. A shape that drifted before this change is baselined as it stands, since the lock can't see history it never recorded. The runtime unknown-key report in slice S1 is the backstop for that. Until slices S2 (declared `migrate` steps) and S3 (class rename and removal) land, a deployed class has no in-language way past the refusal.

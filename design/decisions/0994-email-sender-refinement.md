# 0994 — A Sender refinement admits only authenticated mail

- **Status:** Accepted (v0.729)

**Context.** Part of #3888. A handler that acts only on authenticated mail began with `if s.identity.dmarc == DmarcPass { … } else { Reject(…) }`, and forgetting the `if` was silent.

**Decision.** (B) `Sender` is a refinement base, as `Caller` is (#3890). The predicate is `Dmarc(<DmarcVerdict>, …)`, capitalised as a fixed compiler-known check, composed with `&&`, `||`, `!`, and admissible only over `Sender`; any other base or an argument that is not a `DmarcVerdict` variant is `bynk.actor.refinement_predicate_unsupported`. A refinement inherits `Sender`'s scheme and identity. Because the verdict has three values, a predicate is decided at compile time by evaluating it against each, and the route carries the admitted verdict tags. (C) The runtime refuses a message whose verdict is not admitted before the handler runs, with `setReject("sender not authenticated")`, logged by outcome only. It is a refusal, not a fault, so a later `fallback` does not receive it. (E) `Sender` and its refinements share the `Internal` scheme, so at most one appears in a sum. A `Sender` refinement is refused on every protocol but email (`bynk.actor.scheme_not_admissible`), because nothing elsewhere would check its `Dmarc(…)`. A refinement whose predicate admits no verdict at all is `bynk.actor.sender_admits_nothing`, so no address is silently dead.

**Consequences.** Security-relevant: a handler can now refuse unauthenticated mail by declaration. Mail from a domain with no DMARC policy is refused by `Dmarc(DmarcPass)`, which is what the refinement says; `!Dmarc(DmarcFail)` is the lenient rule. No existing program changes meaning. The test harness reading the verdict from a case's headers at `unit` and `integration` (D) follows in the next part of #3888.

# 1030 — `?` in a case fails the case on any `Err` or `None`

- **Status:** Accepted (v0.767)

**Context.** A `case` body has no return type an author sees, so `?` in one is the language's "fail the case here" (#2857): it throws the case's expectation failure, reporting the operand and its location. The checker nonetheless typed a case body as returning `Effect[Result[(), ValidationError]]`, so only an `Err` of `ValidationError` converted; any other error was `bynk.types.question_error_mismatch` naming that synthetic return type (`Effect[Result[_, ValidationError]]`), which the author never wrote, and an `Option` operand was refused as outside a handler. Tests mostly unwrap results of the code under test, whose error types are the author's own, so the rule fell on the common case.

**Decision.** (A) In a test `case` body or a `property` body, outside any lambda, `?` accepts any `Result[T, E]` and any `Option[T]` and yields `T`. The checker does it before the return-type rules, so no error type is compared. The check is a lambda depth the checker now tracks, because a lambda swaps the return type but not the body kind. The emitter already failed the case on any `Err`; it now also guards an `Option` on `None`. A failure reports the same three things as before (the expression, what the operand was, the `?`'s location): an `Err` shows its error value as an `expect` shows a value, and a `None` reports `the operand was None`. The wording is today's, not the example's `` `x?` was Err `` shorthand, so existing reports do not change. (B) A lambda is unchanged: `?` inside one returns from the lambda by the lambda's own return type, and still errors where that is not a `Result`. (C) A helper `fn` is ordinary code: `?` there follows the helper's return type, because only a case or property body has the fail-the-case meaning. (D) A property's `?` fails the property for that input and shrinks like a failed `expect`; the property body shares the case's checking, so there is one rule. (E) Hover on a `?` in a case or property says "fails the case on Err or None", for a `Result` as well as an `Option`; completion, semantic tokens and signature help are unchanged, because there is no new syntax.

**Consequences.** It only accepts programs that were refused, so nothing that compiled changes. A `?` on a non-`Result`, non-`Option` operand in a case is still `bynk.types.question_on_non_result`. The `question_error_mismatch` diagnostic can no longer name the synthetic case return type, so that leak is gone.

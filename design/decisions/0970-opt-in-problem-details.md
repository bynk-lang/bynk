# 0970 — A service or route opts in to RFC 9457 problem details for the errors it answers

- **Status:** Accepted (v0.705)

**Context.** One service answered errors in two shapes: its error variants sent `{ "error": message }` or no body, and the router's rejections sent `{ "kind": …, "details": … }` or no body. A client that is not Bynk's handles both, and `RawError` and `on rejected` exist only to match someone else's contract, with no standard shape to opt into. The bodies are written by the renderer and the router, not by the handler, as with `json { options: plain }`.

**Decision.** (A) The shape is opt-in and the default is unchanged: `errors { format: problem }` on a `from http` service, `@errors(format: …)` on a route, the route winning, then the service, then `format: bynk` (every error body byte for byte as before), the arrangement `json { }` and `@json` already use. The section follows `json { }` in header position. (B) In `problem` format an error variant with a message answers `application/problem+json` with `type: about:blank` (RFC 9457 §4.2.1: a problem that is just its status), `title` (the status's reason phrase), `status` and `detail` (the message); a router rejection answers the same with `type: https://bynk-lang.org/problems/<kind>` in kebab case and the rejection's own members as extension members (`kind`, `path`, `expected` and `actual` of a structural mismatch, a refinement's `violation` with the rejected value already removed), `detail` being the rejection's own detail. (C) What it does not touch: a `RawError` body, an `on rejected` handler's replacement (it is still handed the rejection's `kind` and `detail`), a status with no body (`401`, `403`, `404`, `405`), the `500` a fault answers and every success body. (D) `bynk openapi` and `bynk client` follow in the next increment. (E) A shared mapping function returning `HttpResult[T]` needs no change: its variants render as problems in this mode.

The variant body is chosen where the response is built (an option on `httpResultToResponse`), and the rejection body where the router stamps a rejection, before `on rejected` runs, so one runtime function covers every site that stamps a rejection. The `type` URIs are a published surface, listed once on the reference page; new kinds are additive. Two checks are shared between the section and the annotation: `bynk.http.errors_not_http`, `bynk.http.errors_unknown_field` and `bynk.http.errors_invalid_field`; the rest are `bynk.http.errors_duplicate` and `bynk.parse.duplicate_errors`.

**Consequences.** A client that expects problem details gets them from every error the router and the variants produce, with one opt-in line. Nothing changes for a service that does not opt in. Hover on `@errors` and on a service that declares the section names the two shapes, completion offers `errors` in a service body and `format` and its values inside it, and the section is a contextual keyword like `json`, so semantic tokens are unchanged. Per-kind pages for the type URIs, and the OpenAPI and client reflection of the mode, follow.

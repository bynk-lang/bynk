# 1059 — bynk.schema.lock records an Analytics instance's column mapping

- **Status:** Accepted (v0.792)

**Context.** Part 3 of #4105, which closes it. `writeValue` (part 1) writes a record's fields to `blob1…`, `double1…` and `index1` by position, and `select[T]` (part 2) reads them back by the same mapping. A point already written keeps its positions, so reordering the record silently changes what every reader of the old points sees, and nothing else reports it.

**Decision.** The lock's `[analytics]` section records each instance written with `writeValue`, keyed `<unit>.<Instance>`: the record's name (informational), the `@index` field and the blob and double fields in column order, each as `name:kind` (`text`, `enum`, `bool`, `number`, `decimal`). Because the mapping is the checker's record of each `writeValue` call (`Callee::AnalyticsWrite`, kept in the project's callee accumulator), the entry is reconciled after the units are checked, not with the declaration-only passes that record agent shapes and `derives Ord` orders. A change is refused as `bynk.analytics.mapping_changed`, at the record's declaration, and the recorded entry is left as it was: a recorded column removed, moved, or changed in kind, or the `@index` field changed or removed. Appending a field at the end of a column family, and renaming a field in place (the column keeps its place and kind), update the entry and are not errors. An instance no longer written is dropped; one written with more than one record type has no single mapping, so it is left as it was (a typed read of it is already refused). The document is at lock version 4 once it has an `[analytics]` entry (version 3 is `[orders]`), so a toolchain that does not know the table refuses the lock instead of dropping it. **The accept follows the #3956 `accept-order` pattern and folds into today's flow, not a new `bynk lock` family:** `bynk lock accept-analytics <Instance>` (or `--all`) is a sibling subcommand of the existing `bynk lock`, reads the lock, recomputes the live mappings and rewrites the entries in the same commit as the change. Unlike `accept-order` it type-checks the project (the mapping is read from checked units, so it refuses a project that does not check), through a new `checked_callees` entry point beside `check_project`.

**Consequences.** The three parts of #4105 are complete: a record is a data point's schema (`writeValue`, `select[T]`), the limits are compile-time errors, and the schema lock refuses the change that would make old points read wrong. The editor's own analysis (the language server) does not reconcile the lock, as it does not for agent shapes' non-declaration facts: the diagnostic shows on `bynk check` and `build`. The tooling delta of the issue (hover on a field's column, completion of written fields in a read type, signature help for the type arguments) is not in these three changes and is filed as a follow-up.

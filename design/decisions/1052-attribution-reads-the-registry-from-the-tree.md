# 1052 — The probes that count diagnostics read the registry from the measured tree's source, not the registry compiled into xtask

- **Status:** Accepted (v0.787.1)

**Context.** The per-PR attribution (#4428) measures the base revision and the PR's tree with the same xtask binary. Three probes took their registry from `bynk_syntax::diagnostics::REGISTRY` / `EXPLANATIONS`, which are compiled into that binary: `explained_codes` ignored its `root` altogether, and `diagnostic_coverage` and `emit_diagnostics` took the registry total and the cross-reference from it. Both sides therefore read the same registry, so a PR that added an explained code never appeared to have moved `explained_codes`, and the attribution passed #4468 with that probe undeclared. The table gate caught it on the stamp, the late failure #4428 was meant to remove (#4476).

**Decision.** `registry_codes(root)` and `explained_code_count(root)` in `xtask/src/greenfield_status.rs` read `<root>/bynk-syntax/src/diagnostics.rs`. A registry entry is the `"bynk.…"` literal a `d(` or `dg(` call opens with (`warn(d(…))` counts through its inner `d(`), inside `pub const REGISTRY`; an explanation is the `code: "bynk.…"` field inside `pub const EXPLANATIONS`; `//` comments are removed first. The three probes use them. A synthetic root with no such file (a test's temporary directory) reads the compiled-in registry; a tree that has the file but no `REGISTRY`/`EXPLANATIONS` the scan can read (the const renamed, the file split) is a loud failure naming it, never a silent fallback. `registry_source_matches_the_compiled_in_one` asserts, through source-only readers with no fallback, that the source reading equals the compiled-in registry and explanations on the live tree, so a new constructor shape the scan does not know turns that test red instead of leaving the attribution blind. A temporary-tree test shows a PR that adds an explained code is reported as moving `explained_codes` and `diagnostic_coverage`, is refused without `probes:` naming them and accepted with it.

**Rejected.** Building and running the base worktree's own xtask for the readings. It is accurate for every probe whatever it reads, but the worktree's paths differ from the PR's, so a cold workspace build would run in every PR's CI. It stays an option if a probe appears that source reading cannot express.

**Consequences.** Live readings are unchanged (the table and the stamp path are untouched); only the base-versus-PR comparison gains correct readings for these probes. Adding a registry constructor shape needs the scan taught the new shape, and the pinning test says so.

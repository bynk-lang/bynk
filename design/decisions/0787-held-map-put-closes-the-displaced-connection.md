# 0787 — A put over an existing key in a held Map closes the displaced connection

- **Status:** Accepted (v0.537)

**Context.** The WebSocket guide (§2.9) frames a held `Connection` as a resource you cannot lose, and `remove` honours that by closing the connection before deleting the entry. `put` over a key that already held a connection did not: Workers overwrote the stored connection id and the bundle target overwrote the in-memory `TestConnection`, so the displaced connection was neither closed nor returned. Its client socket stayed open with nothing holding it. This surfaced in review of #3255 (#3224) and is recorded as #3261, with three options: close on replace, refuse, or document the drop. The maintainer's decision is recorded on the issue: https://github.com/bynk-lang/bynk/issues/3261#issuecomment-6770811011.

**Decision.** Close on replace. A `put` over a key that already holds a connection closes the displaced connection first, as `remove` does, and then stores the new one. The maintainer chose this over refusing a `put` on an existing key (the most explicit option, but it makes the common reconnect case an error and needs a separate `replace`) and over documenting the drop (which leaves the trap in place). Both targets behave the same: on Workers the old connection id is resolved and closed, then the entry is overwritten; on the bundle the old `TestConnection` is closed, then the entry is overwritten. Putting back the connection the key already holds must not close it, so the displaced value is compared with the new one before closing: by connection id on Workers, by object identity on the bundle. A key that holds no connection closes nothing, so a first `put` is unchanged.

**Consequences.** Documented behaviour changes, so this is a language increment: a program that replaced a held connection and relied on the old socket staying open now has it closed. `put` is now an awaited operation on both targets (it was a synchronous expression), which its `Effect[()]` type already allowed. The close happens while the handler runs, before the end-of-handler commit, exactly as for `remove`, so a handler that closes a connection and then faults has closed it although the entry is not committed as replaced; the book says so. Emitted TypeScript for a held-map `put` changes on both targets. No grammar or checker change, and no change to hover, completion, semantic tokens or signature help.

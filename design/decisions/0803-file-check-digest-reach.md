# 0803 — What an edit re-checks under the file-check memo, and why consumers' keys stay span-inclusive

- **Status:** Accepted (v0.548.4)

**Context.** ADR file-check-memo (#3299) keys a file's replayed check on a digest of everything the check read. Its "known limit" assumed a body edit re-checks the direct consumers of the edited context because the key includes the consumed declarations' bodies, and proposed two body-fact digests (#2719 needs-context, #1702 compared type parameters) to stop that. Measuring before building them showed the premise was wrong for the bench shapes.

**Decision.** (1) No body-fact digests now. A consumer's key does not include the exporter's bodies: the cross-context information it reads is signatures and types, and the needs-context set is computed after the files are checked, from the typed units, so no file's check reads it. A body edit to ctx0 of the linked shape re-checks exactly ctx0 when nothing after it in the file moves (one group per context). With three groups per context, the bench's size, it re-checks ctx0 and its four direct consumers, because the edit shifts the spans of the types declared after it, and a consumer's key is span-inclusive on purpose: a diagnostic of its own can carry a label that points into the context it consumes at an offset. Erasing foreign spans from consumers' keys would turn those five re-checks into one, but it saves about 1 to 2 ms of a ~150 ms round and needs a proof that no replayed output embeds a foreign span; it is not worth that risk. Where a `uses`d commons function's body changes under its importers, `combined_fns` includes the body, so importers re-check (correct, since compared type parameters #1702 are derived from it); narrowing that to signature plus the compared-parameter set is worth doing only for a project with large shared commons, which no bench shape exercises. (2) The digest hashes each distinct shared declaration once per round. Units share their `uses` and `consumes` targets' declarations as `Arc`s, so the same few types and functions were rendered into hundreds of files' digests. `DeclDigests` memoises the digest of each `Arc<TypeDecl>` and `Arc<FnDecl>` by address for one round: safe by construction: each entry holds a clone of the `Arc` it was computed from (one refcount bump per distinct declaration), so the allocation cannot be freed, and its address cannot be reused for another declaration, while the cache lives, even if some path builds a temporary `Arc` mid-round and drops it. The memo drops it when each round ends (with a debug assertion that it is empty when the next begins, and a test that a round leaves none behind), because the parse cache builds fresh declarations each time and a later allocation could reuse an address and be handed a stale hash.

**Consequences.** A callgrind profile of a warm round (200 linked contexts, one-file edits) before this change put the digest at 28% of instructions; after, the whole run is 13% cheaper and the digest's share is down by 47%. In-process warm round at the bench's size, medians over four runs each: about 171 to 155 ms (-9%); at one group per context, about 67 to 60 ms. The remaining warm-round cost is spread over work proportional to the project's source size: the digest's own hashing of each declaration once, the index rebuild (about 19% of instructions, mostly `IndexBuilder::build`), copies of the replayed records (about 12%), and dropping the previous round's maps (about 10%). `xtask/tests/analysis_oracle.rs` pins which files an edit re-checks, and carries the profiling harness (`profile_warm_rounds`, ignored).

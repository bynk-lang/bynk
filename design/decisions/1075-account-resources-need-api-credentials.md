# 1075 — Account resources need API credentials

- **Status:** Accepted (v0.807)

**Context.** ADR 0888 drew the wrangler/REST boundary: wrangler builds and runs code, and REST manages account resources. It also put every account operation behind `CloudflareApi`, with `Wrangler` as its one adapter, until back-half paydown 1D.4 (#4056) moved the resource kinds to REST one at a time. REST cannot reuse a `wrangler login` session. It needs `CLOUDFLARE_API_TOKEN` and `CLOUDFLARE_ACCOUNT_ID`, and wrangler infers a single account where REST cannot. So the move breaks a deploy that relied on `wrangler login` alone, and the question is how that need is stated before anything changes. 1D.4a moves KV, the first kind.

**Decision.**

- **Scope (#4056 Decision B).** The five resource kinds (KV, R2, D1, Vectorize and queues) move to REST. The Worker-scoped operations stay on wrangler: the secrets (`secret list`, `secret put`, and the sweep's `secret put`/`delete` by name), `triggers deploy` and the deployments listing behind the presence check. So do the push, `rollback`, D1 migrations (remote and `bynk dev`'s local ones), `whoami` and `bynk dev`'s local Secrets Store listing. This amends ADR 0888's list, which put secrets, triggers and deployment listings on REST.
- **Routing (Decision C).** `cloudflare::Account` is the one `CloudflareApi` a run uses. A moved kind's methods send requests built by its module under `cloudflare/rest/` (`rest/kv.rs`). Each request is data: a method, a path, a body and whether it may be sent again, with a decoder for the answer. Every other method delegates to the `Wrangler` adapter. The trait keeps its operation shapes, so no kind's policy changes and the recording fake logs operations, not transports. A moved operation's typed return replaces its stdout parser: `kv_list` returns the ids. The kind decides "already gone" from the REST error's code (KV's 10013) instead of wrangler's prose.
- **Credentials up front (Decision E).** After the plan and before the confirmation, `gates::account_checks` asks for the REST client of each REST-managed kind whose steps will call the account. For KV that means a namespace with no recorded id, or a `--prune` delete of one with an id. A missing variable is refused in the kind's words, naming the token's permission, so nothing has been created. A run that needs nothing asks nothing: a redeploy with every namespace recorded works with `wrangler login` alone. In that case KV's drift read (the check that a recorded namespace is still on the account) is skipped and the ledger trusted, as a failed read always was, and the plan says so in a note. `--dry-run` is unchanged.
- **The doctor row (Decision F).** A project that declares an account resource gets a `cloudflare api` row in the Deploy capability, found by a text scan of its `.bynk` files: a `capability … =` of a resource kind, a `queue(` source, or the bare `Kv`. The row is `ok` when both variables are set and otherwise `warn`, naming the unset ones. It is never `fail`, because `bynk dev` runs the same gate and needs no token, and the deploy's own pre-flight refuses exactly when one is needed. It is offline: `Toolbox::env_set` reports only whether a variable is set, never its value, and the row makes no call to check the token.
- **The probe (Decision I).** The gated growth probe `wrangler_resource_ops` counts the account operations still run as a wrangler process: `OpKind`'s variants, less the operations kept on wrangler. A moved kind deletes its variants. It counts operations rather than trait methods, because the trait's one `vectorize(op)` method covers six operations. Counted that way, it read 15 on `main` before 1D.4 (KV 3, R2 1, D1 2, Vectorize 6, queues 3), reads 12 after 1D.4a (KV), and falls to 9 after 1D.4b (R2, D1), 3 after 1D.4c (Vectorize) and 0 after 1D.4d (queues).

  The kept list has eleven entries, named as `OpKind` names them: `Push`, `TriggersDeploy`, `Rollback`, `D1MigrationsApply`, `D1MigrationsApplyLocal` (`bynk dev`'s, which Q4 keeps), `Whoami`, `SecretsStoreListLocal`, `WorkerDeployments`, `SecretList`, `SecretPut` and `NamedSecret`. #4056 used different names for four of them: its `deploy_triggers` is `TriggersDeploy`, `secret_names` is `SecretList`, `secret_delete` is `NamedSecret` (the sweep's delete by name), and `local_secrets_store_list` is `SecretsStoreListLocal`.

**Consequences.** A KV project that creates or prunes a namespace needs both variables, and each later 1D.4 slice names the kind that now needs them. Queue and Vectorize projects will need them on every deploy. A KV failure reads as a REST failure (`POST /storage/kv/namespaces: Cloudflare answered …`) behind the kind's unchanged `could not create …:` prefix. Each KV operation is one HTTPS request instead of a wrangler process. The matching on wrangler's KV text and its two KV parsers are gone, along with KV's `OpKind` variants.

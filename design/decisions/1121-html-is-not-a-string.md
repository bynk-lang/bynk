# 1121 — Markup is `Html`, a type in `bynk.html` distinct from `String`, and escaping by context is the compiler's job

- **Status:** Accepted (v0.833.1)

**Context.** A Bynk service serves a page by reading a shell with `embed`, filling its markers with `String.replace` and `bynk.html`'s `escapeText`/`escapeAttr` ([ADR 0993](0993-html-escape-commons.md)), and returning `Raw(…, "text/html; charset=utf-8")`. The escapes are right only where the author put them, and even a correct escape is wrong in a URL attribute, an unquoted attribute, `<script>` or `<style>`. Nothing in the types records which strings are markup: the serve-a-page guide inserts `content` unescaped because it "is markup you built". The HTTP security review found this, and the typed-HTML track (`design/tracks/typed-html.md`, spine #3927) answers it. [ADR 0143](0143-raw-http-body.md) and `reference/http.md` say Bynk serves bytes with a content type and "does **not** template HTML (that is the frontend tier)"; [ADR 0954](0954-html-response-security-headers.md) D leaves a policy built from the page to a typed-HTML feature. ADR 0993 kept its escapes bare, rather than `Html.escapeText`, because an `Html.` prefix needed a placeholder type before this track defined the real one.

**Decision A — `Html` is a type, not a `String`.** `Html` is an opaque type over `String`, declared in the first-party `bynk.html` commons (ADR 0993's unit) and reached with `uses bynk.html`. It is not a built-in: a name in `BUILTIN_TYPE_NAMES` may not be a user's `type`, so a built-in `Html` would break every project's own `type Html`, the reason [ADR 0659](0659-url-commons.md) B kept `Url` out. The compiler knows it by its resolved identity, as [ADR 0666](0666-d1-sql-bools-literal-sql.md) B keys the D1 check on `bynk.cloudflare`'s `D1`. Its operations are the checked `html"…"` literal, a template's `fill`, `Html.text(s)` (escaped as element text), `Html.join(xs)`, `Html.empty`, `Html.unsafe(markup, reason)` and `h.toString()`. These are the only ways to make an `Html`, and `toString()` goes only the other way. `escapeText` and `escapeAttr` keep their names, types and behaviour, and stay bare.

**Decision B — the bridges.** Data reaches markup only through the escape its context needs, chosen by the compiler from where a placeholder or hole sits (the context-model ADR in this increment). Raw markup enters only through `Html.unsafe` (the unsafe-rule ADR in this increment). There is no `Html` constructor, no implicit conversion from `String`, and an opaque `Html` cannot become a `String` through interpolation, because `interpolable` admits no opaque type (`bynk.types.interpolation_non_scalar`).

**Decision C — `Html` does not cross a boundary.** A record may hold an `Html` field (a template's fields record needs one), but a type containing `Html` is refused by the codec, as a request parameter, by `Json.decode` and as an agent `store` field (`bynk.html.at_boundary`). Markup from outside therefore enters only through `Html.unsafe`; to send markup as JSON, a program sends its `toString()`. A pass-through `Forwarded` is opaque with no body accessor, and `Html` has no constructor from it, so an upstream body can never become `Html` or a page. That is structural, not a check.

**Decision D — ADR 0143 is revised for HTML responses.** Bynk now builds HTML pages, checked at compile time, and serves them with a page response (recorded with its slice). The "does not template HTML" stance in ADR 0143 and the matching `reference/http.md` passages (*Raw responses*, and the generated-CSP item under *What is deliberately excluded*) are rewritten by the track's book slice. `Raw` itself is unchanged: bytes with a content type, for everything that is not a page Bynk built.

**Consequences.** Every new form is additive: `Html` is a new name in a unit a program opts into, and no program that compiles today changes meaning. It enters as experimental, behind the single gate `bynk.html.typed` in `BUILTIN_EXPERIMENTAL`, with `bynk.html.Html` and its companions mapped to it in `BUILTIN_GATED`, and joins the frozen surface only on promotion. A unit that already `uses bynk.html` and declares its own `Html` would see a clash; the first code slice surveys the corpus for one. `EmailMessage.html` and `EmailReply.html` stay `Option[String]` until promotion, when moving them to `Option[Html]` is a breaking follow-on with its own proposal.

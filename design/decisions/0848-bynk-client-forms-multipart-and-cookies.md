# 0848 — `bynk client`: `@form`, `@multipart` and typed `cookies`

- **Status:** Accepted (v0.609)

**Context.** BC1 and BC2 of #3508 left out the routes whose request is not JSON and path: a `@form` or `@multipart` body and a typed `cookies` record. The proposal's Decision F fixed their shape and Decision E left one fact unverified: whether a framework's server, hosted in a Worker, may set `Origin` on an outgoing `fetch`, which the signed-cookie CSRF seam (#3386) needs. This is slice BC3.

**Decision.**

- *`@form`.* The body is the record's public type. Each field is written into its wire form with the shared serialisers, the record's own decoder checks it (a refinement is refused as `Invalid` before sending, rooted at `body` as the server's error is), and the text is the server's own leaf rules: a `List` repeats its key, an `Option` is its value or absent, an enum is its variant's name, a `@name` field is written under its wire name. It is sent as `application/x-www-form-urlencoded`. The writer is the same one a `query` uses, behind no `?`.
- *`@multipart`.* A file part (the standard library's `File`) is a `Blob` in TypeScript, `Blob | null` for an `Option[File]` and `readonly Blob[]` for a `List[File]`, so a browser's `File` input passes as it is. The client does not read a file's bytes: the record's decoder checks the text fields with an empty file standing in for each file part, then a `FormData` is built from the text fields and the blobs. A part is sent under the `File`'s own name, else `blob`, because a part with an empty file name is read back as text (found against the real server). The caps (`maxFile`, `maxParts`, `maxBody`) are the server's, and its `413` is a typed answer. `fetch` sets the content type, which carries the boundary. `File` has no codec in a service's own type table, so the client carries a minimal one for the stand-in.
- *Typed `cookies`.* The argument is its own interface, a field that is an `Option` or has a default may be left out, and a `@name` is the cookie's name (`__Host-sid`). It is written as the request's `Cookie` header, with a cookie's value unencoded as the server reads it. It is for server-side calls: a browser sets its own `Cookie` header and drops a script's. Where `typeof document` is defined and cookies are given, the call returns `CallFailure` `Invalid` (path `cookies`, naming `credentials: "include"`) rather than send a request that would lose them (the maintainer's call on #3508); the check is `document`, so a DOM emulation counts as a browser, which is documented. The interface and the reference say so.
- *Left out still.* A raw `query: RequestQuery` or `cookies: RequestCookies` view is named and skipped, as the raw bodies and streams of BC4 are.
- *`Origin`, verified.* The system tier runs the generated client inside a real `workerd` (`wrangler dev`), calling a Bynk Worker with `origin` set; the route answers with the `Origin` header it received, and it is the one the client set. So a Worker-hosted server runtime may set `Origin` through the client, and the CSRF recipe in the reference no longer carries an unverified marker. Node's `fetch` sends it as well. A browser forbids a script setting it and ignores the option.
- *CORS and CSRF documentation.* The reference gains a CORS recipe for a browser front end (a credentialed `cors` policy with explicit origins and `credentials: "include"`, or a Bearer token through `headers`) and states the `origin` fact above.
- *Known edge.* A `List` field with no default in a form, a query or a cookie record cannot be sent empty, because an empty list writes no key and the server refuses a missing list. That is the server's rule, which the client reproduces and the reference states.

**Consequences.** A front end can call every `from http` route that is not a raw body or a stream. The client's text for existing routes is unchanged apart from the runtime gaining a few small helpers. The typed-cookie refusal in a browser is a behaviour a page's tests under jsdom will see.

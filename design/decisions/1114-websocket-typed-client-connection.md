# 1114 — `bynk client` generates a typed `connect` for each `from websocket` service

- **Status:** Accepted (v0.829)

**Context.** `bynk client` covered `from http` routes only. A front end connecting to a `from websocket` service wrote by hand the URL with its route parameters, the authentication handshake (the `Sec-WebSocket-Protocol` pair of #3900 and #3904), the JSON encoding and decoding of frames without the server's refinement checks, and reconnection, including after a credential expires (#3903). The service's contract (`in`, `out`, route parameters, actor) is typed, and the generator reads the same model for HTTP (#3906).

**Decision A — one `connect` per service, taking the route's parameters and the credential its actor reads.** `connect` hangs from the existing `createClient(options)` object, as `api.<service>.connect(...)`, so a WebSocket service shares `baseUrl` (`https` becomes `wss`), `origin` and the other options with the HTTP routes, instead of a separate `ChatGateway.connect` of its own. It takes the `on open` route parameters in order, positionally, as an HTTP function takes its path parameters, encoded and checked the same way (a value the server would refuse is `CallFailure` `Invalid` and nothing is opened), and sends them in the query string of the upgrade, which is where the Worker reads them. The credential follows the actor of `on open`: `Bearer` takes `{ bearer }` and `Oidc` `{ oidc }`, each a token or a function that makes one, offered as the subprotocol pair `["bynk.bearer"|"bynk.oidc", token]`; a `SignedCookie` actor takes none, since the browser sends the cookie; a `None` actor takes none; an actor sum with an anonymous member makes the bearer optional. A service whose frame or route types cannot be represented is named and left out, as a route is.

**Decision B — frames are typed and checked both ways.** `send` encodes the value through the server's codec and runs the server's decoder over it, so a refinement the server would refuse is returned as `CallFailure` `Invalid` and nothing is sent; `frames` and `onFrame` deliver the `out` type decoded. A frame that does not decode closes the connection. A page cannot close with `1008` (`WebSocket.close` throws `InvalidAccessError` for any code except `1000` and `3000` to `4999`), so the client closes with `4008` and the reason `invalid frame`, the nearest code a page may use; a close the server makes keeps its own code. A plain `Bytes` frame is a binary message (a `Uint8Array`) and any other frame type is JSON text, the rule of #3905 in both directions. The server writes `out` frames with the same codec (#4549), so what the client decodes is what the server sends, an `Option` included.

**Decision C — reconnection is opt-in, with a credential callback.** `reconnect: { credentials, maxAttempts, backoff }` reconnects after a `1008` with the reason `authentication expired` (#3903) or an abnormal `1006`, with an exponential backoff (250 ms doubling, at most 30 s, five attempts in a row by default), asking `credentials` for a fresh credential each time. A close the client made (`close()`, or a frame it refused) and any other `1008` never reconnect. Without `reconnect` the connection stays closed. Frames are not replayed, so a frame sent while the connection was down, or one the server sent meanwhile, is the application's concern, and the reference says so; a frame still queued when a connection closes is dropped, never resent on the next one, and `credentials` is called once for every attempt, not once per connection. `frames` and the listeners carry across a reconnect, and `onClose` reports `willReconnect`.

**Decision D — environment-neutral.** The connection uses the platform `WebSocket` (browsers, Workers, Node 22 and later) and no dependency, as the HTTP client uses `fetch`. A `webSocket` option on `createClient` supplies another constructor, as `fetch` does, which is how a Node client sends an `Origin` or a `Cookie` header (the standard constructor cannot). A platform that fires `error` and never `close` for a refused upgrade (Node's) is handled: an error before the socket first opened ends that attempt, once.

**Decision E — experimental, as `bynk client` is.** Member names may change until the client is stabilised. The WebSocket half of the runtime is inlined only into a client that has a `from websocket` service, so a client without one is the same text it was, apart from a `webSocket` option on `ClientOptions`. No WebSocket service has a contract hash (`API_CONTRACTS` lists HTTP services), and `sendContract` does not apply to one.

**Consequences.** A front end connects to a `from websocket` service with the server's types and checks, with no hand-written handshake, and survives an expired credential when it asks to. `bynk client` selects `from websocket` services as well as `from http` ones, by name as before. The upgrade driver of the `system` tier and the client agree on the handshake because both follow the one documented subprotocol pair; the client is tested against a real Worker on workerd, for a `Bearer` actor (typed frames both ways, local refusal, a forged token, an expired token with reconnect) and for a `SignedCookie` actor refused without a session, and type-checked under `tsc --strict` for `Bearer`, `SignedCookie` and `None`. A real Chromium (Playwright, against the deployed Worker on workerd) signs in over HTTP, then opens the `SignedCookie` service's socket with no credential of its own, which shows the browser itself sends the cookie and the `Origin`; a page at an origin the service does not list is refused, session or not.

# 0957 — A refined pattern on an Int warns, with a fix to the equivalent range pattern

- **Status:** Accepted (v0.695)

**Context.** Refined patterns (`_ where InRange(200, 299)`) predate range patterns (#2699). On an `Int` they are strictly weaker than the equivalent range: a refined pattern is a guard and never counts towards exhaustiveness, a range does and reports the intervals a match is missing, and a reversed range has a fix where the refined form relies on `bynk.types.inverted_range` with none.

**Decision.** [DECISION A] The warning `bynk.match.refined_pattern_is_range`, in a new `match` diagnostics category, with a quick fix (`MaybeIncorrect`, so `--fix` does not apply it: ranges count for reachability and refined arms do not, so the rewrite can make a later arm unreachable, e.g. `_ where NonNegative` then `_ where Positive`), rather than removing numeric refined patterns. [DECISION B] It applies when the scrutinee is an `Int` or a refined `Int`, and only to `_ where …` (a named binding would be lost by a range). The predicates are the three the issue names; their intersection is computed, and the pattern is reported only when it is a single non-empty interval (`_ where Positive && InRange(1, 10)` is `1..10`). `AtLeast`, `AtMost` and every `String` predicate are untouched: the warning claims only what the issue decided. `Float` and `Decimal` are not matched by `match` today, so a refined pattern there does not arise. [DECISION C, deferred] A refinement bound may be a constant under #3951, and range patterns do not accept constants; a refined pattern whose bounds came from a constant is therefore to be reported without the fix, so the fix never writes a different value than the author named.

**Consequences.** `--deny-warnings` builds fail until the patterns are rewritten, which the quick fix does one pattern at a time; a later arm the range now covers is then `bynk.types.unreachable_arm` and is deleted by hand. Hover, completion, semantic tokens and signature help are unchanged.

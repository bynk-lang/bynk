# 0925 — Prelude types: one registration point for compiler-known sums

- **Status:** Accepted (v0.668)

**Context.** #3955 shipped `Ordering` as the first-party commons `bynk.ordering`, reached by an implicit `uses` that a textual check added to a unit mentioning `.compare`, `.sortWith` or `Ordering`. That worked for naming the type in a commons and a context, but the rule lived in three unrelated places, and a context that built `Ordering.Less` or a bare `Less` was refused as `bynk.context.rebrand_construction`, because a commons type a context reaches through `uses` is rebranded per context and its constructors are not in scope there. #3952 and #3976 add compiler-known sums of their own.

**Decision.** [DECISION A] A registry (`bynk_std::PRELUDE_TYPES`: name, declaring unit, trigger spellings) that the implicit `uses` injection, the bare-variant rule and the rebrand predicate consult. It starts with `Ordering`; a later sum is a row and a unit. Hard-wiring each type into the AST and type representation as `Option` is was not taken: a separate `bynk/ordering.ts` module is emitted only for a unit that references it (nothing for a project that never orders anything), so the per-project snapshot cost the issue worried about does not arise; the cost, one small module per project that uses `Ordering`, is stated and accepted. [DECISION B] A unit's own type or variant of the same name wins locally: its declaration shadows the injected `uses` as any imported name is shadowed, and a bare variant that a prelude sum shares with another sum in scope resolves from context only (#3955, #3987). [DECISION C] `Ordering` now; #3952 and #3976 register theirs; whether #4192 and #4181 use the hook is decided with them.

The rebrand is removed for a prelude type rather than done once for everyone: it is a plain tagged sum with no brand, and every context imports the same module, so `compute_is_uses_commons_type` is false for it and a context constructs it directly. A prelude type is recognised by name and by the file id of its declaring unit, so a lookalike declared in a user's file is not one and is rebranded like any commons type. A unit that declares a type of the prelude's name, or `uses` or `consumes` a unit that does, is not given the implicit `uses` at all, so the two never meet (and an unused `bynk/ordering.ts` is not emitted for it). A row must be a plain sum with no invariant, since every context constructs it directly.

**Consequences.** `Ordering.Less`, a bare `Less` with an expected type, and `.then`/`.reverse`/`sortWith` work inside a context under both targets. Nothing is emitted for a unit that does not mention a prelude type. Hover, completion, semantic tokens and signature help are unchanged: they read the same declarations the implicit `uses` already put in scope.

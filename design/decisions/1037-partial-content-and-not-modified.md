# 1037 — HttpResult answers a range read with PartialContent (206) and a handler-resolved conditional read with NotModified (304)

- **Status:** Accepted (v0.774)

**Context.** #4389, found while shipping R2 range reads and conditional gets (#4049): `HttpResult` had no variant for `206 Partial Content` or `304 Not Modified`. `RawStreamed` always answers 200, and 304 came only from the router's own conditional handling, so a handler could not answer a range read with `Content-Range`, or a conditional get from R2 with 304. #3917 added `PreconditionFailed` and `PreconditionRequired` the same way, as two more rows of the variant table that OpenAPI, the client, the status tables and the editor all read.

**Decision.** (A) `NotModified` is a nullary variant, `304`, with no body, in the same bodyless family as `NoContent`; headers come through the existing response-header wrapper. It is for a conditional read the handler resolved itself (an object store checked `If-None-Match` against its own entity tag); the router's automatic `304` for an eligible `GET` is unchanged. (B) `PartialContent(body, contentType, range)` is `206`: a `Stream[Bytes]` body like `RawStreamed`'s, a `String` content-type, and a `range: ContentRange`. The body is a stream because the case it exists for (an object store's range read) hands the handler one, and a `Bytes` part can be wrapped with `Stream.of`. The content-type is an argument because a 206 answers one representation and must name it, as `Raw` does. (C) `ContentRange { start: Int, end: Int, total: Option[Int] = None }` is a record in the `bynk` adapter, not three loose arguments, so a handler passes the range it computed as one value, a unit test matches it, and `total: None` (an unknown size, written `*`) has a name. It renders `Content-Range: bytes start-end/total`. (D) Both are refused at compile time on a route whose method is not `GET`, with `bynk.http.status_needs_get` (explain entry, compiled bad/good pair, negative fixture): a range or a validator is how a client re-reads a representation it already knows, and `HEAD` is answered by the `GET` route as today. The check is made where the variant is typed, in a handler's own body, so a user sum variant of the same name is not mistaken for it. It does not follow a helper `fn`: a `fn` that returns `HttpResult` is a normal pattern and is legal from a `GET` route, and refusing the call would need a call-graph analysis of which functions construct these variants and which handlers reach them. So the runtime is the backstop: a non-`GET` route's response is built with `notGet`, and a `PartialContent` or `NotModified` that reaches it faults (`500`, logged), never sent. A compile-time check through helpers is a follow-up if wanted. (E) A range that is not one (`start` below 0 or past `end`, `end` at or past a known `total`, a non-integer) is a fault at run time, not a refusal at compile time, because the values are computed: the dispatch's fault path answers `500` and logs the route, so a malformed `Content-Range` is never sent. The body is held to its range too: a stream that yields more or fewer than `end - start + 1` bytes errors, which aborts the response as a fault mid-body does, so a client stitching parts together never gets bytes the header does not describe. `Content-Range` is a header the router owns, so `withHeader` refuses it (a second one would be the malformed header this rule prevents), and `download(filename)` applies to `PartialContent` so a ranged download can name its file. (F) Nothing reads the request's `Range` or `If-None-Match` for the handler: the router does not parse `Range` today and the issue asks only for the answers, so the handler states what it sent. (G) The rest follows the variant table: OpenAPI lists a `PartialContent` response with a required `Content-Range` header and a binary body, the generated client reads it as a raw body, the status and problem tables list both, completion and hover take them from the table, and a `system` case reads a `206` back as `PartialContent` with its range parsed from `Content-Range` (a missing or malformed header is a fault, not an invented range) and a `304` as `NotModified`. (H) Neither variant can carry a validator. `ETag`, `Last-Modified` and `Cache-Control` are headers the router owns, so `withHeader` refuses them, and these variants have no argument for one as `RawTagged` has. RFC 9110 §15.4.5 says a `304` should repeat the validators a `200` would have sent, and an `If-Range` resume needs an `ETag` on the `206`, so this is a known gap: the variants as asked for in #4389 answer the statuses, and giving them a validator (an `etag` argument or helper) is a follow-up.

**Consequences.** A handler can serve R2 range reads and conditional gets with their real statuses. A user sum variant named `PartialContent` or `NotModified` is disambiguated by the existing `ambiguous_constructor` rule. `ContentRange` is a new name in `bynk`, so a project that declares its own `ContentRange` and consumes `bynk` unqualified gets the usual duplicate-name error. Not done: a `Range` request header parser, an automatic `416` for an unsatisfiable range, a validator on either variant (H), and a compile-time check through helper functions (D).

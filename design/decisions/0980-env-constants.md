# 0980 — A constant's value comes from `bynk.toml` per environment

- **Status:** Accepted (v0.717)

**Context.** Bynk has no general way to give a value a different setting per deployment environment. Each feature invented its own table (`[deploy.vectorize]`, `[deploy.hyperdrive]`, `[deploy.containers]`, `Oidc`'s `trustFrom`), and where none was invented a staging deployment uses production's values: under `--env` a foreign Worker's name is used as declared, so a staging `Service @worker("legacy-billing")` calls production's billing Worker. A constant's initialiser was a closed static set (ADR 0678 A) and ADR 0826 resolves a constant to its literal before any reader sees it, so the missing piece is a declared, checked way for that literal to differ per environment.

**Decision.** A constant's initialiser may be `env(NAME)` or `env(NAME, default)`. A: `env(…)` is only ever a constant's whole initialiser, so every per-environment value is a named constant (`bynk.env.not_initialiser`). B: it is resolved at build time from `bynk.toml` only, never from the Worker's run-time environment or the build machine's: the value for the environment being built is `[env.<name>.vars]`, then `[vars]`, then the default. C: an optional default; without one the variable is required (`bynk.env.missing`). D: `NAME` is a bare identifier, `[A-Z][A-Z0-9_]*`, so tooling can treat it as a symbol, and constants (upper-camel) cannot be confused with it (`bynk.env.malformed_call`). E: the supported types are `String`, `Int`, `Bool`, `List[String]` and refinements over the first two (`bynk.env.unsupported_type`); a value of another kind is `bynk.env.bad_value`; a value of the right kind that breaks the refinement is refused by the ordinary literal check on the initialiser. F: a `bynk.toml` variable no constant reads is an error (`bynk.env.unknown_variable`), and two constants naming one variable with different defaults are an error (`bynk.env.conflicting_default`). I: a package consumed as a dependency cannot declare an `env(…)` constant (`bynk.env.in_dependency`), since reading deployment configuration is the application's business and a library takes values as parameters. H: a variable named like a secret warns (`bynk.env.secret_like_name`), since `bynk.toml` is committed. The pass runs right after parsing, in the build and the editor alike, and rewrites each such initialiser to the literal it resolves to, so the checker, emitter and runtime see an ordinary constant. This amends ADR 0678 A: a constant's initialiser set gains `env(…)`.

**Consequences.** Every position that accepts constants (ADR 0826) gets per-environment values for free. This increment resolves the `default` environment's values in every build; selecting another environment (`--env`), the deploy plan's listing of each constant's value and origin, the shared-with-default advisories and the editor surfaces follow in the next increment. A variable's value is not secret: the warning and the reference say so. `env(…)` outside a constant's initialiser (anywhere but nested in a list, record, `Some`, `Ok`, `Err` or parentheses of an initialiser) is not yet refused by this pass and falls to the resolver's unknown-function error.

# 1068 — bynk.crypto derives keys with HKDF and hashes passwords with a self-describing PBKDF2

- **Status:** Accepted (v0.801)

**Context.** `bynk.crypto` had digests, MACs and signatures but no key derivation and no password hashing. Without HKDF an author reuses one secret for HMAC, for encryption and for each tenant's key. Without a slow, salted hash a service that stores passwords has nowhere correct to turn, and the by-hand versions fail in familiar ways: no salt, a low or fixed count, a comparison that stops at the first difference. The unit runs no third-party crypto, and the only password function Web Crypto offers on every platform is PBKDF2.

**Decision.** (A) `deriveKey(secret, salt, info, length)` is HKDF-SHA-256 (RFC 5869), `length` 1 to 8160 bytes, a non-empty `secret`; a bound outside that is a fault, as an empty HMAC key is. (B) `hashPassword(password)` draws a random 16-byte salt and returns `pbkdf2-sha256$<iterations>$<salt>$<hash>` (unpadded base64, a 32-byte hash). `verifyPassword(password, stored)` reads the parameters from `stored`, recomputes and compares in constant time; a `stored` that is not in the format, or that claims a count over ten million or a salt or hash outside 8 to 64 and 16 to 64 bytes, is `false`, not a fault, and cannot be made to spin. (C) The count is Bynk's, not the caller's, differs by platform, and is stored with each hash, so a later release can raise it and old hashes still verify. It is 600,000 (OWASP's guidance for this algorithm) on Node and in the browser, and 100,000 on Cloudflare Workers, which is the most deployed Workers will run: Web Crypto there refuses more with `NotSupportedError: Pbkdf2 failed: iteration counts above 100000 are not supported (requested N).` (confirmed on a deployed Worker, [sandbox check](https://github.com/bynk-lang/bynk/issues/4118#issuecomment-7198549618); a local `wrangler dev` accepts 600,000 and cannot see the limit). **The Workers count is about six times below OWASP's recommendation and does not meet it**; the docs say so. `needsRehash(stored)` is `true` for a count below the running platform's, a smaller salt or hash, or a string not in the format, so on Workers a stronger stored count is never reported stale. (C1) A hash made off Workers at more than 100,000 cannot be verified on Workers: `verifyPassword` there returns `false` and logs one warning naming the stored count and the cap, rather than faulting or failing silently; a hash made on Workers verifies everywhere. (D) The password is normalised to NFC before hashing. (E) There is no cheaper option, and the cost is stated. Measured on deployed Workers ([sandbox check](https://github.com/bynk-lang/bynk/issues/4118#issuecomment-7199935890)), PBKDF2-HMAC-SHA-256 at 100,000 iterations costs 23 to 42 ms of CPU per derivation (median 33 ms, five samples) and 10,000 costs 2 to 5 ms, so at the Workers count hashing needs the Workers Paid plan, whose limit is well above the Free plan's 10 ms. The docs say so and cite the measurement. No lower count and no Free-plan mode is offered here; whether to is a separate decision. An identity provider is recommended where the Paid plan is not an option.

**Consequences.** The four operations are additions to `Crypto`, so no existing program changes. A future algorithm (Argon2, if Web Crypto gains it) is a new scheme name in the same format. `Secret` is not yet accepted as the password or the input secret: a `Secret` form of each, as `importSigningKeyFromSecret` is for keys, is follow-up work.

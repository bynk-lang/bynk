# 0979 — A Query gets filterMap, takeWhile, skipWhile and count(p), with takeWhile and skipWhile needing a declared order

- **Status:** Accepted (v0.716)

**Context.** #3963 gave `List` `filterMap`, `takeWhile`, `skipWhile` and a predicate `count`, and asked for the same on a `Query` (its decision C). A `Query` lowers through the runtime query builder, not through the list kernels, so parity was not a plain mapping and #4246 carries the query side.

**Decision.** `Query` has the four methods with the `List` signatures: `filterMap(f: T -> Option[U]) -> Query[U]`, `takeWhile(p)` and `skipWhile(p)` returning `Query[T]`, and `count(p) -> Effect[Int]`. The three builders lower to deferred thunks like `map`, `take` and `skip` (`__q.flatMap` for `filterMap`, and a `findIndex` of the first rejected element followed by a `slice` for the two prefix forms), so a terminal still reads staged state when it runs. `count(p)` is a terminal over `__q.filter(…).length`. A store scan already reads the source whole before `take`, `skip` and `sortBy`, and the new builders are not on the early-stopping whitelist, so they read whole and then cut: where a backend cannot push the cut down, the cost is the read the rest of the query already pays, and it is documented. `takeWhile` and `skipWhile` stop on order, which a query plan does not express as a filter, so they are accepted only on a query with a declared order: an explicit `sortBy` or `sortByDescending` before them (through steps that keep order: `filter`, `map`, `filterMap`, `skip`, `take`, `takeWhile`, `skipWhile`; `flatMap` is not one, since each inner query is joined in its own order), or a `store Log`, which is read oldest first, or one of its windows (`since`, `before`, `between`, `recent`, `reversed`). A local that shares a `Log` field's name shadows it, as in the store dispatch, so it is not a `Log` here. A `Map` scan, a join, a grouping, a `distinct` and a query held in a `let` are refused with `bynk.query.while_needs_order`, rather than guessing an order. The rule is syntactic, over the receiver's method chain.

**Consequences.** A query held in a `let` and then cut with `takeWhile` needs the `sortBy` at the use. A `Map` scan is insertion-ordered in practice, but that is not an order the author declared, so it is refused; this is the conservative reading of "an error on a query with no order", and loosening it later is not a break. `check_query_kernel_method` gains a `receiver` argument so the order rule can read the chain. Completion offers the new methods, because it is built from the kernel op tables; signature help for the two-arity `count` is the per-arity work tracked in #4262.

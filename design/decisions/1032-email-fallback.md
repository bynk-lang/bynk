# 1032 — An email service's fallback forwards mail the handler faulted on, instead of a permanent bounce

- **Status:** Accepted (v0.769)

**Context.** #3885. Every fault ends in `setReject`, which Cloudflare documents as a permanent SMTP error, and an Email Worker has no documented way to ask for a temporary one. A few seconds' outage of a dependency therefore permanently bounces a customer's mail and tells the sender it was not accepted. The handler cannot recover from this itself, because the fault path runs in the runtime after the handler has failed.

**Decision.** (A) A `fallback { forward: "<address>" }` block on the service, parsed with the other policy blocks after `delivery`; the address is a string literal holding a bare address (the rule `from email` uses, not a catch-all), and the block on another protocol is `bynk.email.fallback_not_email`, a second block `bynk.parse.duplicate_fallback`, and any other field or a bad value `bynk.email.fallback_bad_option`. (B) What falls back: a handler fault or a non-verdict return, and a message that cannot be parsed or exceeds a parser limit. An oversized message, a refused `Reply` and a refused `Forward` are rejected as without a fallback, because nothing would accept the first, the handler chose the second, and the fallback would be refused for the same reason as the third. (C) The forward carries `X-Bynk-Fallback: handler-fault` or `unreadable` and nothing from the message, keeping ADR 0808's logging rule; if the fallback forward is itself refused, the rejection is today's, and the log line says so without the address. (D) Deploy warns of an unverified fallback exactly as for a `Forward` verdict, by listing it with the project's forwards. (E) The guide gains the recipe for no rejection at all: accept every message and put the work on a queue, with its retries and dead-letter queue. A fallback that a `from email` service of the project claims, directly or through its domain's catch-all, is `bynk.email.fallback_claimed`, so two Bynk services cannot forward faults to each other forever.

**Consequences.** A service with no fallback is byte-identical. The fallback mailbox receives messages that may be hostile, so the reference says to treat it as untrusted input; only the outcome header is added and the message is passed on, not interpreted. The system tier records a fallback forward as the `Forward` verdict it is, so a case sees where the message went; the header is asserted by the runtime's own tests.

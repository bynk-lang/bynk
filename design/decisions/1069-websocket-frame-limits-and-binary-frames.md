# 1069 — A WebSocket service bounds its frames with `limits { maxFrame }`, and `Bytes` frames are binary

- **Status:** Accepted (v0.802)

**Context.** The generated `webSocketMessage` decoded every inbound message as UTF-8 text and `JSON.parse`d it, with no limit of Bynk's own: Cloudflare accepts a message of up to 32 MiB, so one client could make a Durable Object parse a 32 MiB document per frame. HTTP routes have `limits { maxBody }` for exactly this. And a binary message was decoded as text and parsed, `in: Bytes` meant a base64 string in a JSON document, and an `out` frame was always JSON text, so audio, images and compact protocols could not be expressed (#3905).

**Decision A — `limits { maxFrame: <bytes> }` on a `from websocket` service, defaulting to 1 MiB.** A frame over it is closed with `1009` ("message too large") before it is decoded or parsed, without running `on message`, and the refusal is logged by size only. The value is a positive `Int` literal of at most 33,554,432, Cloudflare's own limit on an inbound message, or `bynk.http.limits_invalid_field`; any other field is `bynk.http.limits_unknown_field`, and `limits` stays `bynk.http.limits_not_http` on a service that is neither HTTP nor WebSocket. The check lives in the runtime (`webSocketAdmit`), where a text frame's length is judged from its UTF-16 length alone except in the narrow band where the UTF-8 size is not decided by it. Rejected: a constant as the value, since an HTTP service's `limits` takes only literals too and the same resolver would be needed for both.

**Decision B — `Bytes` is a frame type, and a frame's kind is checked.** `in: Bytes` delivers each binary message to `on message` as `Bytes` and `out: Bytes` sends binary messages. Any other frame type stays JSON text. A text message to an `in: Bytes` service, and a binary message to any other, is closed with `1003`; the second used to be read as UTF-8 and parsed. `in` and `out` are independent, and no new diagnostic is needed because `Bytes` already type-checked as a frame type.

**Decision C — `maxFrame` also bounds what the server sends.** A frame over it faults the send, so a server bug cannot push oversized frames at clients. The upgrade records the ceiling in the socket's attachment, so `send` knows it after the Durable Object hibernates and for a connection an agent holds by id. A connection accepted before this has no ceiling recorded and is unbounded until it reconnects. In a test, `svc.open(tc, …)` hands the `TestConnection` the service's `maxFrame` (the service object carries it), so a `unit` case sees the fault; a `TestConnection` an agent is handed directly is not bounded.

**Decision D — a frame rate limit is not provided.** A per-connection counter would not survive hibernation, so any limit would be approximate. It is recorded as a follow-up if abuse is seen.

**Consequences.** A service can no longer be made to parse a frame much larger than it expects, and it can carry audio, images and compact protocols as binary frames. A service whose clients send frames of 1 MiB to 32 MiB sets `maxFrame` explicitly, and a client that sent binary messages to a JSON service, which worked only by accident, is closed with `1003`.

# 0916 — A queue consumer's delivery policy is declared in source

- **Status:** Accepted (v0.661)

**Context.** Bynk generated `[[queues.consumers]]` with only `queue` and a fixed `max_batch_size = 10`. Cloudflare's `max_retries` defaults to 3 and, without a dead-letter queue, a message that reaches the limit is deleted. `wrangler.toml` is generated, so nothing in Bynk could change either, and a dashboard setting is overwritten by the next `bynk deploy`.

**Decision.** (A) A `delivery { }` section on the service, beside `limits { }`, not settings in `bynk.toml`: retries and the dead-letter queue change what `Retry` means. It is a contextual keyword parsed with the other policies' machinery, after `json`. (B) The keys are `retries` (0 to 100), `retryDelay` (a `Duration` of whole seconds, at most 24 hours), `deadLetter` (a queue name, or `None`), `batchSize` (1 to 100), `batchWait` (a `Duration` of whole seconds, 0 to 60) and `concurrency` (1 to 250). A value out of range, an unknown key or a repeated key is `bynk.queue.delivery_bad_option`; a constant is accepted wherever a literal of the key's type is (ADR 0826's rule, resolved by the same pass). A second section is `bynk.parse.duplicate_delivery`, and the section on another protocol is `bynk.queue.delivery_not_queue`. (C) A consumer with no `deadLetter` warns (`bynk.queue.no_dead_letter`); `deadLetter: None` says deleting is intended and silences it. Making a dead-letter queue mandatory was rejected as too strong for a throwaway queue. (D) The dead-letter queue is an ordinary queue: its name passes `is_queue_name`, it cannot be the consumer's own queue, deploy qualifies it with `-<environment>` and creates it before the push (recorded in the ledger only when Bynk created it, as a producer queue is), and a Bynk consumer of it must take the source consumer's message type (`bynk.queue.dead_letter_type_mismatch`, compared as written). (E) Revised: the length of an environment-qualified queue name cannot be checked at build time, because `bynk.toml` names no environments (an environment is only `bynk deploy --env NAME`). The deploy plan checks it instead, for a consumer, producer or dead-letter queue, and refuses before anything is created. The build still checks the name alone, so the build-time half of ADR 0654's follow-up stays open.

**Consequences.** Every existing queue consumer now draws `bynk.queue.no_dead_letter` until it names a dead-letter queue or writes `deadLetter: None`; the warning does not fail a build. Only keys written are emitted, so existing consumers' `wrangler.toml` is unchanged, with `max_batch_size = 10` unless `batchSize` is set. Hover, completion and the semantic token for `delivery` are lexical, like the other service policies. A real deploy was not run for this change: the dead-letter queue's qualification and creation are verified through the deploy plan and the generated `wrangler.toml`.

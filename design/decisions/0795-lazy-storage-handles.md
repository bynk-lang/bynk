# 0795 — Storage-backed collection handles read per entry and stage their writes

- **Status:** Accepted (v0.543)

**Context.** The per-entry layout (ADR 0785) already writes only the entries a handler changes, but `loadState` still lists every key and the handles are in-memory (#3254), so a handler's reads and its commit work still grow with the size of the state. Decision F of #3189 says a keyed read fetches one entry, an indexed read fetches the matched postings and entries, and a `Log` window is a key range. The in-memory handles' methods return `Awaitable` precisely so a storage-backed handle can replace them.

**Decision.** `bynk-emit/runtime/src/lazy.ts` adds `LazyStoreMap`, `LazyStoreCache`, `LazyStoreSet` and `LazyStoreLog`, each implementing the corresponding handle interface from `store.ts` over an `EntryOverlay`, so a handler reads its own writes and nothing reaches storage until one transaction. A keyed `get`/`has`/`put`/`remove` reads one key; `size()` reads the collection's `c/<field>` record; an `@indexed` lookup lists the posting prefix and reads the matched entries in batches, sorted by insertion sequence; a scan lists the collection in pages; `Cache.liveSize` and reaping read only the `x/` expiry range; a `Log` window lists a key range, `recent(n)` a reversed list with a limit. Entries are decoded when they are read, so a stored value that fails to decode faults when a handler first reads it. Each handler stages its collection's metadata with `finish()`.
No stored byte format changes except one additive field: the keys and value shapes are those of ADR 0785. A `Log`'s `c/<field>` record gains `skew`, the most a key's time is above its entry's `t` (key times never go backwards, so an entry appended with an earlier `t` is keyed later than its time). A window read widens its key range by it. **An absent `skew` means unknown, never zero**: a record written before the field existed, or by a build that drops it, may hold clamped entries. **This revises the first version of the field, where an absent `skew` meant 0** (that reading is only right if no clamped entry was ever written, and the eager commit already clamped key times before this field existed). A reader with no known skew reads `before`/`between` to the end of the log and filters on each entry's own `t` (a full-tail read; the next commit by a newer writer establishes and records the skew, so that cost is paid once after a rollback or for a log written before the field, not on every read); a writer (`append`, `prune`) first establishes it by reading the log once and then records it, explicitly, even when it is 0. The eager commit records it too, exact over every entry the log holds. A collection with no metadata record at all is empty, so its skew is known to be 0.

**Rollback.** A build from before this change that reads a `c/<field>` record with `skew` ignores it: it reads only `seq`, and when it next commits it rewrites the record as `{ size, seq }`, dropping the key. It neither faults nor misreads (checked against the earlier `entries.ts`). Because an absent `skew` means unknown, a later build that reads the record after such a rollback does not trust a missing value, and reads windows correctly (slower for that log, until a writer records the skew again). No `STORAGE_LAYOUT` bump is needed.

**Sequence numbers.** The insertion sequence a key is given may differ between the eager commit and a handle (an entry added and removed in one handler consumes a sequence in the handle, not in the commit). What is frozen is the order, and that no sequence is ever reused: each writer reads and writes entries ordered by sequence and keeps the collection's next-sequence counter above every sequence it holds. The differential test compares order (sequences as ranks), not raw numbers.

**Consequences.** Nothing calls these handles yet, so the only behaviour change in this increment is the eager commit recording `skew`. They are tested against the in-memory handles: random handlers through both produce the same reads and the same stored state (up to the numbering above), and a one-entry put, a keyed get and an indexed read touch a bounded number of keys at 10 and 1 000 entries. A later increment makes `loadState` build them for current-version records and the lowering await them. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

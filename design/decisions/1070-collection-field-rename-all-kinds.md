# 1070 — The resumable key move covers Cache expiries, Log entries and index postings, and `bynk.store.replaces_collection` is retired

- **Status:** Accepted (v0.803)

**Context.** #4482. Part A (the resumable, batched key move for a `Map` and a `Set`) left a `Cache`, a `Log` and an indexed `Map` refused with `bynk.store.replaces_collection`, because they keep keys the move did not yet cover.

**Decision.** `moveRenamedEntries` takes the field's kind and moves what a renamed collection keeps under its name with the same batched, transactional, new-key-wins move: a `Map`, `Cache` and `Map` entries under `m/`, a `Set` under `s/`, a `Log` under `l/` (its keys carry a time and a sequence, which the rename leaves alone). Two key families are never copied, because copying them is unsafe when both names hold entries (a rolled-back deploy wrote under the old name): a `Cache`'s expiry entries (`x/`) are derived from each entry that moved, in the same transaction as the entry, from its own `exp`, so an expiry for an entry the merge dropped cannot reap the one that won; and index postings (`i/`, for an `@indexed` or `@unique` `Map`) are deleted and not moved, with the moved metadata dropping its index signature, so the handle rebuilds the postings from the entries on first use, as it does for an index added to an existing map. Both old families are swept whatever the field declares now, since the old field may have been indexed when this one is not. The metadata (`c/`, the count, the next insertion sequence and, for a `Log`, the skew) moves after the last family: when both names hold metadata only the entries moved are counted, and a `Log`'s merged skew is the larger of the two, or unknown when either is, so a window or a prune cannot miss the older entries. `bynk.store.replaces_collection` has nothing left to say and is removed. It was never in a release (`bynk-syntax/shipped-codes.txt` does not list it), so it needs no tombstone. The non-additive refusal's rename hint now offers `replaces` for every storage kind.

**Consequences.** Every storage kind is renamed with `replaces`, with no `migrate from`. The same cost note applies: the first load after the deploy does the whole move, and its cost grows with the collection. The workerd test covers a `Map`, a `Set`, an indexed `Map` (read back through an equality filter on the index, which rebuilds the postings) and a `Log`, each with more entries than a batch; a `Cache`'s expiry keys are covered by the runtime unit test, since a workerd `Cache` test would need a clock to expire against.

# 1111 — Event queues have reserved names, carry #3899 signed queue messages that only the event's owner can sign, and deduplicate every `eventId` per subscriber

- **Status:** Accepted (v0.828.3)

**Context.** Any Worker on the account with a producer binding, a Cloudflare event subscription and the dashboard can write to a queue, and account members can read and delete its messages (track §6). Owner-only emission ([ADR 0289](0289-events-owner-only-emission-check.md)) and a proven `publisherId` ([ADR 0485](0485-per-edge-call-signature.md)) must survive the change of substrate. #3899 already shipped a signed queue message format, one verification path (`queueAdmit`) and per-consumer replay deduplication in the `Idempotency` D1 store (track D2, D11).

**Decision A — reserved names.** A subscribing service's queue is `bynk-ev-<slug>-<hash>` and its dead-letter queue `bynk-dl-<slug>-<hash>`: `<hash>` is the first 8 hex digits of SHA-256 over `<qualified context>/<service>`, and `<slug>` is that pair lower-cased with every character outside `[a-z0-9]` written `-`, truncated so the name plus `env_qualify`'s `-<environment>` fits Cloudflare's 63 characters. The names are collision-checked, not injective: the compiler refuses two subscribing services whose queue names coincide (`bynk.event.queue_name_collision`). The functions live beside `env_qualify` in `bynk-project`, so the plan and the emitted config agree by construction. User code may not name a queue that starts with `bynk-ev-` or `bynk-dl-` in a `Queue @name("…")`, a `from queue("…")` consumer or a `deadLetter: "…"` (`bynk.queue.reserved_name`, an error). Only those two prefixes are reserved, not `bynk-` as a whole.

**Decision B — the #3899 format, unchanged.** An event message is a version-1 signed queue message: `bynk.from` is the publishing context's qualified name, `bynk.id` the emission's `eventId`, `bynk.ts` the signing time at the flush, and `bynk.sig` an HMAC-SHA256 under ADR 0485's publisher→subscriber edge key over `bynk-queue-v1`, `from`, `id`, `ts`, the **subscriber queue's deployed name** and the canonical body. The body is `{ "type", "payload", "envelope" }`. Signing over the source queue's name means a message moved to another subscriber's queue does not verify, and a dead-lettered one still verifies against its source. Edge keys are per environment, so a staging message does not verify in production. A rotated key keeps verifying for the 15-day window ([ADR 1096](1096-edge-keys-rotate-through-two-slots.md), #4526), which is a prerequisite for events using edge keys on queues.

**Decision C — verification before decoding.** The subscriber's `queue` entry calls `queueAdmit` directly, with the subscribing service's qualified name as `consumer` and ports built as `admitQueueBody` builds them, and an `admitsContext` that admits exactly one context: the owner of `E`, known at compile time. Then `body.envelope.publisherId` must equal the verified `from`, and `body.type` the subscribed event. An unsigned, malformed, other-version, non-owner or badly signed message is acknowledged, reported and counted, and never handled, retried or dead-lettered. A verified message whose `publisherId` or `type` disagrees with its signer is a compiler or deploy bug: it is dead-lettered and reported, and its claim is released. So ADR 0289 and ADR 0485 hold at the subscriber by signature, not only by the compiler's check on the emitter.

**Decision D — deduplication is built in and always on (#3545 part 2).** Every Workers delivery claims `queueReplayKey("<subscriber context>.<service>", <queue>, <eventId>)` through `queueAdmit`'s existing protocol: claimed only after the signature verifies, so unsigned traffic cannot fill the store; a 15-minute lease over the handler's run; confirmed when the handler completes or the guard excludes the event; released when the handler faults or the message is dead-lettered as undecodable, so a retry or a redrive is admitted once. A redelivery that meets a running lease is retried after it, not acknowledged. Claims are kept for `QUEUE_DEDUP_WINDOW_SECONDS` (15 days: 14 of retention plus 1 of delay), and a message signed longer ago is refused as `stale`, so a lapsed claim never admits a replay. A claim that fails (including on D1's daily limit) never admits unchecked: the message is retried, and on the daily limit retried with a delay to 00:00 UTC. Every subscriber Worker gets `D1_IDEMPOTENCY`. `Idempotency.claim(env.eventId, …)` in author code stays legal and correct but is redundant for redelivery; `claim` remains the tool for business keys.

**Rejected.** A separate event-message format (two signing inputs and two verifiers for one problem). Trusting the queue boundary without a signature (anyone with account access can write to a queue). A timestamp window as the replay defence, as `/_bynk/event/` uses (messages legitimately wait for days). Opt-in deduplication, as #3545's text proposed (D2's replay defence needs the claim unconditionally). Degrading to unchecked admission when the claim store fails or is over its limit (a replay and a redelivery look identical at the entry). A user-declared `deadLetter` on an events service (it would reopen the reserved-name boundary; refused as `bynk.event.delivery_dead_letter`).

**Consequences.** No new secret kind is introduced; the claims table holds keys and expiry times, never payloads. Confidentiality and availability against account members are out of scope and stated in the guide: events must not carry secrets, and a subscriber's `concurrency` and the per-queue throughput limit bound a flood, which the refusal counts make visible. A change to the shared signing or verification is one change, reviewed once, under `/security-review` on every slice that touches it ([ADR 0076](0076-feature-track-posture.md)). Each delivery costs about 3 D1 rows written, up to 5 with the key's index.

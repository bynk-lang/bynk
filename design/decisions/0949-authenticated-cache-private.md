# 0949 — Authenticated responses are Cache-Control private by default, with noStore opt-in

- **Status:** Accepted (v0.687)

**Context.** A `GET` with no `@cache` sent no `Cache-Control`. Responses on routes guarded by `Bearer`, `Oidc`, `SignedCookie` or `Signature` carry one caller's data, but only a response that set a cookie was forced `private`. A shared cache in front of the service, such as a corporate proxy or a CDN the operator adds, had nothing telling it not to store them, which matters most for cookie-authenticated requests because they carry no `Authorization` header to make a cache cautious (RFC 9111 §3.5). `@cache(scope: public)` was refused only on a handler that read `cookies`, not on one whose actor is a credential.

**Decision.** (A) A credentialed route, meaning its `by` clause names a `Bearer`, `Oidc`, `SignedCookie` or `Signature` actor (a refinement takes its base's scheme) or a sum containing one, sends `Cache-Control: private`, not `no-store`, when it has no `@cache`. `private` still lets the caller's own browser cache and revalidate, so the automatic `ETag` keeps working, and stops only shared caches. `Visitor` routes are unchanged. (B) `@cache(noStore: true)` sends `Cache-Control: no-store` and suppresses the automatic `ETag`, because nothing is stored to revalidate. It excludes `maxAge`, `scope` and `immutable` (`bynk.http.cache_no_store_conflict`), and `maxAge` is then not required. It is allowed on any route, so it is the one form of `@cache` that does not need a `GET`. A `noStore` that is not a `Bool` literal is `bynk.http.cache_bad_no_store`, a third code the issue did not name, for the same reason `immutable` has its own. (C) `@cache(scope: public)` on a credentialed route is `bynk.http.cache_public_authenticated`, by the reasoning of `cache_public_reads_cookies`; where both apply, only the former is reported, and a `SignedCookie` route keeps its own `bynk.actor.signed_cookie_public_cache` rather than getting a second error. (D) The default applies to every response of the route that the handler's response path builds, not only `200`s, since a `404` or a `403` can reveal one caller's state: it is stamped last, so an `@cache`, `noStore` or a cookie-setting response's own `Cache-Control` is kept. A response the router refuses before the handler runs, such as a `413` from the body cap, is not stamped: it carries nothing of the caller's.

**Consequences.** An operator who relied on a CDN caching authenticated responses was unsafe; a response that is really shared moves to a `Visitor` route, and the changelog says so. `bynk.cloudflare.edge_cache_public_authenticated` keeps its own, narrower, rule for `EdgeCache` contexts. Hover on `@cache` documents `noStore` and the credentialed default, and completion offers `noStore` inside `@cache(…)`. No route-level hover shows the effective `Cache-Control` of a route with no `@cache`, because the hover model has no actor resolution; the reference states the rule.

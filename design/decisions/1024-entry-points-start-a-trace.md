# 1024 — Every entry point starts a trace, and the runtime's log lines and Logger.log carry it

- **Status:** Accepted (v0.760)

**Context.** The first half of #3895 (the `traceparent` header, the envelope's `trace`, admission after the signature) moved a trace between contexts, but nothing started one and no log line wrote it. This half does both, and closes the issue.

**Decision.** (B) The Worker's `fetch`, `scheduled`, `queue` and `email` each run their body in `__enterTrace`, which starts a trace and holds it in the request scope for everything the entry awaits: the platform's own trace id when `cloudflare:workers` gives one (`tracing.getActiveSpan()?.spanContext().traceId`, read defensively, and only the id, never `traceFlags`), otherwise a random one. That read has not been verified against a real Cloudflare invocation: the `workerd` case exercises the random fallback, so whether an entry Worker's `trace` equals Cloudflare's own id is unconfirmed, and a follow-up is to check it in a deployed sandbox. An entry inside an entry joins the trace already in scope, so a Worker group's dispatcher and the member it hands a request to share one. A signed call or event delivery starts a trace like any entry and `verifyCall` then replaces it with the one its caller carried, once the signature has held; a public request never reaches it, so a client's `traceparent` is never believed (decision C). The box the scope holds is mutated by that replacement rather than re-entered, because an `AsyncLocalStorage` store set inside a callee is not visible after the caller's `await`. (D) A queue message carries no trace, as decided: each batch starts its own. (E) `Logger.log` adds the trace to the record's `fields` as `trace`, replacing a field of the author's of that name so a correlation cannot be forged; the runtime's own lines (the entry's fault log, a failed call's `ContractMismatch`, `CalleeFaulted` and `CallUnreachable`, a detached effect that failed) carry it as ` trace=<id>` on a line of text and `fields.trace` on a record. `Logger.info`, `warn`, `error` and `debug` write the message as it is and carry no trace: they are documented to, and wrapping them in a record would change every existing log line. The trace is an observability aid: every read of the scope answers "no trace" where there is none, and nothing fails a request.

The scope is `AsyncLocalStorage`, so every generated `wrangler.toml` now carries the `nodejs_als` compatibility flag beside `global_fetch_strictly_public`, in the existing compatibility-flags path and so deduplicated by it. `nodejs_compat` provides `AsyncLocalStorage`, so a project that lists it does not also get `nodejs_als`; a project that lists `nodejs_als` itself is told it repeats a default. This is the one user-visible configuration change, recorded as breaking above. Agents (Durable Objects) are not entries in this sense: a trace that reaches an agent's own logs is a follow-up.

**Consequences.** On Cloudflare, the entry Worker's `trace` equals the platform's trace id where there is one, and every context a request reaches logs the same id, which the three-context `workerd` case proves with an HTTP route, a signed call, an event through the fan-out Durable Object and a client `traceparent` that is not believed. The switch-over to preferring the platform's own propagation, when Cloudflare ships it, is a follow-up: both use the same standard header. Log volume grows by one 32-character field per record.

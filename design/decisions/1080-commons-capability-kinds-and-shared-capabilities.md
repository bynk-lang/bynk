# 1080 — A commons names first-party capabilities in its braced consumes; an instantiable kind is a parameter, any other is shared

- **Status:** Accepted (v0.809.1)

**Context.** #3959, settled in the capability-parameters track (D2). ADR 0990 gave a commons a braced, type-only `consumes` and reserved it (Decision E) for capability contracts. A capability parameter needs a kind to name, and a commons function that logs or reads the clock needs `Logger` or `Clock`, of which a caller has exactly one.

**Decision.** (A) A commons may list a **first-party** unit's capabilities in the braced `consumes` ADR 0990 gives it, beside types: `consumes bynk.cloudflare { Kv, KvEntry }`. From a project adapter a capability is still `bynk.commons.consumes_not_types`, whose note names the first-party rule. The selection imports the contract only: no provider is instantiated and no binding is emitted (a commons is not a deployment unit), a unit that `uses` the commons gets no capability through it (as ADR 0990 D says for types), and a selected capability the commons never uses gets the existing unused-import treatment. Naming a `bynk` capability is an explicit `consumes bynk`, so it turns ADR 0983's implicit reach off for the file, as any explicit `consumes bynk { … }` does. (B) **Instantiable means parameter, non-instantiable means shared.** The registry's `instantiable` list decides, so a kind a unit adds later needs no new list. An instantiable kind (`Kv`, `D1`, `R2`, `Queue`, `Service`, …) is only ever a bound: named bare in a commons' `given` (`given Kv`), a test-only one included, it is `bynk.given.kind_needs_parameter`, with a fix to `given Store: Kv`. A non-instantiable first-party capability (`Clock`, `Random`, `Logger`, `Fetch`, `Secrets`, `Locale`, `Idempotency`, the Cloudflare singletons, `Crypto`) is a **shared** capability named bare: the callee's `given Logger` requires the caller's, exactly as between context functions today, and it is never bound. Used as a bound (`given L: Logger`) it is `bynk.given.shared_as_parameter`, because there is only one and a binding would add a name and no choice. A kind in an experimental unit (`bynk.testing`'s `TypedReads`) needs that unit's `[unstable] allow` as usual. `Events` stays refused, for ADR 0726's reason. (C) A valid argument for a parameter bounded by `K` is a capability in the caller's `given` that is a derived instance whose base is `K`, the bare `K` where the kind allows a bare use (`Instantiable::bare`; only `Kv` today), the caller's own parameter bounded by `K`, or, in a commons suite, the double of `K` (written `K`) or a suite-local instance of `K`. The kind must match exactly. A caller binding its bare `Kv` (`given Store = Kv`) writes that choice; a library never falls back to "the default namespace". (D) A commons still declares no capability and no instance (ADR 0469 D4). The one exception is a commons suite's suite-local instance (`capability Archive = Kv`), a fresh in-memory double with no binding and no deploy effect, which lifts `bynk.capability.derived_outside_context` in a commons suite only. (E) No structural bounds, no generic capability kinds (#3879), no capability contract declared in a commons, and no capability from a project adapter.

**Consequences.** A shared library can use `Kv`, `D1` or `Logger` without taking function values, and the platform lock falls where it does today: a context binds a `Kv` parameter only to a `Kv` it holds, which it holds only by consuming `bynk.cloudflare` itself. Shared capabilities are broader than they look: `given Secrets, Fetch` in a commons can read any secret the caller can and send it anywhere. The grant is visible in every signature on the path, and `Secrets` stays shared in this track (ruled 26 November 2026); a narrower grant is the line to revisit if dependency commons reaching secrets becomes a real concern.

# 1046 — A request's credential is an Authorization made from a Secret

- **Status:** Accepted (v0.784)

**Context.** `Secret` (the previous increment) stops a secret reaching a log, a record or a comparison, but a secret still had to become text to be used: `authorization: Some("Bearer " + token.reveal())` put the credential in an ordinary `String` at the one place it is most likely to be logged or echoed, and `Crypto.importSigningKey` took the key as `Bytes` decoded from a `String` revealed first.

**Decision.** (A) `bynk` exports a second opaque type, `Authorization`: the value of a request's `Authorization` header. It is made only from a `Secret`, by the two built-in methods `bearer()` (`Bearer <secret>`) and `basic(user)` (`Basic <base64(user:secret)>`, RFC 7617; a `user` holding `:` or a control character faults, naming nothing). (B) It carries every restriction `Secret` has: no string form, not `Eq`, a `Key` or `Codable`, and `bynk.types.secret_at_boundary` as a record, event or `store` field or handler parameter or result. It has no reader of its own, not even `reveal`: `Fetch.send` is the one place it is revealed, in the platform binding, and a value with a stray newline there is `InvalidHeader` before anything is sent. (C) `Request.authorization` is `Option[Authorization]`. `Request` is a record `bynk` declares, so the record-field refusal skips `bynk`'s own declarations; a program's own record holding an `Authorization` is still refused. A request, holding one, is no longer `Codable` or comparable. (D) `Request.headers` values stay `String`: a credential put there is written with a visible `reveal()`, which review can see. (E) `Crypto.importSigningKeyFromSecret(algorithm, secret)` takes the base64 PKCS#8 a `Secret` holds and imports it, so the key's text is never a `String` in the program. The bytes form is unchanged. (F) At run time an `Authorization` is the same `BynkSecret` wrapper as a `Secret`, so it renders `<secret>` everywhere. The two types are found by where they are declared (`secret_kind`), and a test pins that `bynk` declares exactly these two opaque types.

**Consequences.** A bearer token or a Basic password can go from `Secrets.get` to a request without ever being a `String`. Breaking: a request that built its credential as text must build it from a `Secret`, and a hand-written `Fetch` binding reads `.value.reveal()`. A credential that arrives as text (a header the caller supplied) has no `Authorization` form and goes in `headers`. A capability operation's signature naming a type its adapter consumes from `bynk` (`Secret` in `bynk.crypto`) is now resolved against the consumer's own table when the adapter's contract view lacks it.

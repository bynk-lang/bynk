# 1082 — An API key is `<prefix>_<id>_<secret><checksum>` in fixed-width base62, and its public id names a random handle, never the identity

- **Status:** Accepted (v0.810.1)

**Context.** Opaque, revocable API keys are how most developer and service-to-service APIs authenticate, and Bynk has no scheme for them: a service reads the header itself and hand-writes the key generation, hashing, comparison and revocation (the API keys track, `design/tracks/api-keys.md` §1–§2, spine #3939). The track adds `ApiKey` to the closed scheme set by widening ([ADR 0080](0080-actor-schemes-closed-nominal.md)), as compiler-generated verification, never a user `Verifier` ([ADR 0175](0175-oidc-jwks-scheme.md) A), following `SignedCookie`'s pattern ([ADR 0821](0821-signed-cookie-actor.md)). Unlike a cookie, a key's secret is not self-verifying: the service must store something per key and find it from the presented key. Two questions are settled here: what a key looks like, and how the seam reaches its record without the key revealing whose it is (track §5, §6, Q1, Q2).

**Decision A — the format.** A key is `<prefix>_<id>_<secret><checksum>`:

- **Prefix.** The actor's `prefix`, `[a-z][a-z0-9]{1,15}`, defaulting to `bk`, distinct per `ApiKey` actor in a context. It makes a leaked key recognisable and attributable, and in a sum it tells the seam which arm a key is for without a lookup.
- **Id.** 24 bytes: a 16-byte random *handle* naming the identity's key store, then an 8-byte random key number within it. The id is public: safe to log, to show in a console and to pass to `revoke`.
- **Secret.** 32 bytes from `crypto.getRandomValues`. Never stored, never logged.
- **Checksum.** The CRC32 (IEEE 802.3, the reflected polynomial `0xEDB88320` that zlib and GitHub's tokens use) of the ASCII bytes of everything before it, `<prefix>_<id>_<secret>` with both separators, appended to the secret. It is not a security control (anyone can compute it). It lets a secret scanner confirm a match offline with few false positives, and lets the seam refuse a mistyped or truncated key before any lookup.

Every field is big-endian base62 over the alphabet `0-9A-Za-z` (so digit value 0 is `0`, 10 is `A` and 61 is `z`), left-padded with `0` to a fixed width: 33 characters for the id, 43 for the secret, 6 for the checksum. The secret and checksum share a part with no separator, so the seam splits them by position. A field of the right width whose value does not fit its byte count is malformed, so each key has exactly one encoding. A key is at most 100 characters; a presented key longer than 128 characters is refused before parsing. Base62 with `_` separators keeps a key one "word" that survives a double-click, a URL and shell quoting, the choices GitHub's token format made for the same reasons. Rejected: a fixed `bk_` prefix for every service, under which every Bynk service's keys look alike and a leak cannot be attributed. Rejected: plain (unpadded) base62, under which over a third of ids alone would be shorter than their own format and fail to parse.

**Decision B — the opaque handle.** The compiler generates two agents per `ApiKey` actor:

- **`<Actor>Keys(handle)`** holds one identity's keys (key number → HMAC, pepper `kid`, label, created, expires, last used, and an empty `scopes` set so scopes are not a later migration), plus the identity itself. It is the only agent on the request path.
- **`<Actor>KeyOwner(identity)`** holds that identity's handle, minted at random the first time a key is minted for it. Only the members use it; verification never does.

Verification is one agent call, because the handle is in the key, and nothing in a key reveals whose it is. Rejected: encoding the identity in the id, which would name the customer in every log line and leak, and let anyone who knows an identity aim traffic at its agent. Rejected: an index agent per id, which costs a second sequential call on every request. Rejected: a record per key id, which loses an atomic `revokeAll`. The handle does not rule out a later owner lookup (`Keys` stores the identity) or key transfer (repoint `KeyOwner`); either can be added without a breaking change.

**Decision C — `revokeAll` replaces the handle.** It runs as a `KeyOwner` handler: it empties the current `Keys(handle)` instance in one atomic commit and marks it retired, then mints a fresh handle, which `KeyOwner` commits when its handler returns. A retired instance holds no records and refuses inserts, so a key presented against it gets the ordinary `401` after the same work. `mint` also runs through `KeyOwner`, which runs one handler at a time, so a mint cannot land on a handle being retired. The order fails safe: if the second commit fails, the keys are already gone and `KeyOwner` still names the retired handle, and any `KeyOwner` handler that finds its handle retired rotates it before doing anything else, so the identity is never left unable to get a key. A single `revoke` does not rotate the handle, because the identity's other keys still live in that instance.

**Decision D — the agents are generated Bynk source with reserved names.** Both agents are generated as Bynk source and appended to the declaring context before it is parsed, as `<Actor>Sessions` is ([ADR 0998](0998-signed-cookie-sessions.md) B), so the checker, `bynk.schema.lock`, the emitter and the deploy migration treat them like any agent, and their shape is the compiler's to evolve. They read no clock: the seam and the members pass `now`, so the context needs no `consumes Clock`. Their digest compare is `bynk.crypto`'s constant-time `Crypto.equal`, a capability method, so the generated agents consume `Crypto`; the compiler supplies that requirement with the agents it generates, so an author never declares a capability for code they did not write. Their names are reserved in the declaring context: an author's declaration that takes one is `bynk.actor.api_key_agent_name_reserved`. A context-wide cap of 100 live keys per identity bounds an agent's state.

**Consequences.** A key reveals at most that two keys share an owner, when both ids are seen, until `revokeAll`. One identity's request path is serialised through one Durable Object, a per-identity throughput ceiling inherent in one agent per identity, and the reference states it. A well-formed fabricated key passes parsing and reaches an instance, which the rate limit asked before authentication bounds (the verification-contract ADR in this increment, and [ADR 1009](1009-rate-limit-annotation-client-ip.md)). `ApiKey`, its types and the reserved names enter as experimental under `[unstable] allow`; the stored record shape is versioned with the generated agents and joins the stored-data promise only on promotion.

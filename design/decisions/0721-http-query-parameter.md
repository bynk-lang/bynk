# 0721 — An HTTP handler reads the query string through a typed `query` parameter

- **Status:** Accepted (v0.498)

**Context.** A handler could not see the query string at all. The router matched on `url.pathname` and dropped the rest, and a handler parameter had to be a `:name` path parameter, `body` or `headers` (`bynk.http.extra_param`). Filtering, pagination and options on a `GET` had to be encoded as path segments, which does not scale and is not how HTTP APIs are written. A query is a boundary fact like a path parameter or a body: the language's strength is typed, refined input checked before the handler runs. #918 named the gap and #2341 set the pattern for headers (`headers: RequestHeaders`).

**Decision.** A handler's `query` parameter (special by name, as `body` and `headers` are; a `:query` path segment keeps its meaning) takes one of two forms, and a handler has at most one.

- **A typed `query: T`**, where `T` is a record whose fields are each a `String`, `Int`, `Bool` or `Decimal`, a refined or opaque type over one of those, an enum (a sum with no payload), or an `Option` or `List` of one. The router decodes the query string into `T` and validates it before the handler runs. A field default applies when its key is absent. A violation answers `400` with the same `RefinementViolation` / `StructuralMismatch` body a bad `body` gets, the path naming the field (`query.limit`).
- **A raw `query: RequestQuery`**, a read-only view mirroring `RequestHeaders`: `get(name) -> Option[String]`, `all(name) -> List[String]` and `params() -> Map[String, List[String]]`. Nothing is validated. A test builds one with `RequestQuery.of(["k=v", …])` or `RequestQuery.empty()`.

*Decoding.* The runtime reads `url.searchParams` (percent-decoded, `+` a space, as `bynk.url.decodeQuery` does) into the JSON object the record's own codec reads, field by field (`queryObject`). The codec then checks refinements, fills defaults and reports a field of the wrong type, exactly as it does for a `body`. This is why the typed form is not decoded with the path-parameter codec: that codec reads one `String`-based value and has no answer for an `Int`, a `Bool`, an enum, an `Option` or a `List`. An `Int` or `Bool` that does not read as one is passed on as text, so the codec reports it as a `StructuralMismatch` at `query.<field>`; an enum is its variant's name.

*Unknown keys are ignored*, consistent with bodies and tolerant of cache-busters and tracking parameters; a strict mode can come later.

*A repeated key on a field that is not a `List` is refused* with `400` (`StructuralMismatch`, "a single value"), not resolved by taking the first. `?limit=1&limit=2` is ambiguous, and the safer boundary says so. An absent `List` field is the field's default, so a `List` field with no default is a `400` when its key is absent: write `= []` to make the key optional.

*Routing stays `(method, path)`.* The query never affects which handler runs; that is #918's territory (envelope facts, refinement-based dispatch), which can later admit the query as a source.

*Diagnostics.* `bynk.http.query_wrong_type` (the parameter is neither a record nor `RequestQuery`), `bynk.http.query_field_not_stringy` (a field of the record is not a query leaf, `Option` or `List` of one), `bynk.http.query_not_http` (a `RequestQuery` on a handler that is not an HTTP route), and `bynk.types.request_query_at_boundary` (a `RequestQuery` in a stored or sent position, beside `headers_at_boundary`). A second `query` parameter is the existing duplicate-parameter error, so it needs no code of its own. `bynk.http.extra_param` now names `query` among the allowed parameters.

*Test drivers.* The test address takes the query as an ordinary positional argument in the parameter's slot, as `headers` and `body` do: a `T` (or a `RequestQuery`) at every tier. At `unit` and `integration` it reaches the handler directly. At `system` the driver turns a `T` into a query string (`queryString` over the record's wire form, `RequestQuery` over its own pairs) and appends it to the path, so the router decodes and validates it. `Wire("?limit=0")` fills the same slot with raw text that reaches the router unvalidated, and yields an `HttpOutcome` as for a body.

*`RequestQuery.params()`.* The proposal sketched `List[QueryParam]`, but `QueryParam` is a record of the `bynk.url` library commons, which a built-in method cannot name. `params()` is a `Map[String, List[String]]` instead (every key with its values, in order), which says the same and needs no import.

*Caching (Decision E).* Verified, not changed. The `ETag` is a weak hash of the response body, so two queries on one path carry different validators, and an `If-None-Match` for one is never answered `304` for the other. The edge cache (`EdgeCache`, Workers Cache) is the platform's, keyed on the full URL with its query; the generated `[cache]` stanza only switches it on, and no emitted or test-side cache keys on `pathname`. `EdgeCache.purge` takes path prefixes and so clears every query variant under a path. A runtime test pins the `ETag` behaviour and a behavioural fixture drives two queries on one `@cache` path.

**Consequences.** Filtering and pagination on a `GET` are expressed in the type and checked before the handler runs; the contract is in the record, where `bynk openapi` can describe it as `in: query` parameters (next increment). `RequestQuery` is a new built-in type name, reserved in type position, with a new `Ty`/`TypeRef` variant mirroring `RequestHeaders`. A `query` parameter name that existed on an HTTP handler as a path parameter is unaffected (`:query` binds first); one that was never legal (`extra_param`) is now a query. A non-HTTP handler's parameter named `query` of any other type is untouched.

# 1119 — A typed Container instance key does not suppress the unbounded-instances warning on an open route

- **Status:** Accepted (v0.832)

**Context.** The container-instance-key ADR (point E), following #4112 decision A, said a keyed instance (`@instances(by: K)`) is not warned about by `bynk.container.unbounded_instances`, on the reasoning that the key's construction is where the author bounds the names. That ADR recorded the weakness: a key type limits the shape of a name and not how many names there are, so `by Visitor` decoding a path parameter straight into `TenantId` lets any client start any number of containers, which costs money, as freely as an untyped `String` does. The warning exists to catch unauthenticated cost growth, and a type does not prevent it.

**Decision.** This amends point E, as ruled by the maintainer in #4584. (A) A typed key suppresses the warning only on a route whose `by` actor is authenticated. On a route whose `by` has an open member (`Visitor`, or a sum that includes one), the warning still fires for an instance name drawn from request input, typed key or not. (B) Nothing else about `@instances(by: K)` changes: the option, what makes a type a valid key, and the typing of `send`, `receiveBytes` and `sendBytes` are as in the container-instance-key ADR. (C) The check is the existing one: a route served only by authenticated actors is never checked, so a keyed instance there does not warn, and an open route is checked whether the instance is keyed or not. A name built from a key through a function (`TenantId.of(...)`) is still not followed, as for any function, which is where an author bounds the set. (D) The reference, the guide and the explain entry say a keyed instance on an open route warns, and that serving the route `by` an authenticated actor clears it. A `RateLimit` reduces the rate but does not bound the number of instances: it is usually keyed per client (`clientIp`), so it slows each caller without limiting how many distinct names arrive across many callers, and the warning is about that count. The docs recommend it beside a key, but the check does not consider `@rateLimit`, so it does not clear the warning.

**Consequences.** A program that was silent may now warn: a keyed instance named from a handler parameter on a `by Visitor` route. It is a warning, so not `breaking`. Clearing it is serving the route `by` an authenticated actor, or building the name from a constant, a closed set or through a function (which is not followed); adding a `RateLimit` slows each caller but does not clear it, because it does not bound the number of instances and the check does not look at `@rateLimit`. No key or option changes. Point E of the container-instance-key ADR no longer describes the behaviour.

# 1088 — The schema lock judges the records an event carries by path, as it judges a stored value

- **Status:** Accepted (v0.813)

**Context.** #4523, found by #3975. `FieldShape` recorded an event field's type as a string, so a field of a named record type was judged by the record's NAME. A nested field removed or retyped, a nested `@name` change (#3975) or a nested `replaces` (#3793) passed the lock, and a consumer still holding an older envelope failed at run time instead of at build time. A stored value did not have the gap: its shape is locked per path since #2676.

**Decision.** `FieldShape` gains an optional `paths` list, the same `PathShape` a `store` field has (`paths` is `skip_serializing_if` empty), filled by the walk a stored value uses (`storage_paths`, with its recursion cut-off), rooted at the field's wire name. It is filled only for a field whose type reaches a record or a sum, so a field of a base type, or a container of one, is locked exactly as before. The types come from the unit and the units it uses, so a record from a commons is followed. `reconcile` takes the build's `unit_uses` for that. A field with recorded paths on both sides is judged by `compare_paths`, the comparison the store fields use: a nested field removed or retyped, added without a default or that lost one is non-additive, a nested field added with a default or a new variant is additive, and a nested `replaces` is applied to the recorded paths first, so a rename on its own is additive. Paths are keyed by wire name (a nested `@name`), so a nested wire-name change is a removal plus an addition and is accepted only when the field says `replaces <the old key>`, which is what keeps an older envelope decoding. A record type's own name is no part of an event's compatibility, because the wire carries its fields and not its name; a record renamed with the same fields is not a retype. **No versioning path exists for events:** an event has only the registry's computed schema number (`@schema(N)`, the envelope's `schemaVersion`), and there is no event upcast, `migrate` or version step in the language, so `replaces` is the one way to keep an old payload readable, and the refusal's own advice is to give a breaking shape a new event type name. **Migration of the lock:** none is needed. The field is optional, an existing lock has none, and an unchanged build keeps the event's version and fills the paths in (as stored values did in #2676, Decision C), after which the next change inside the record is seen. A field whose recorded type no longer matches keeps no paths and is a retype as before. The lock gains the paths on the next build that writes it.

**Consequences.** A non-additive change inside an event payload is a build error. A nested `replaces` and a nested wire-name `replaces` are honoured. The event's lock grows with the records it carries. The registry's contract diff reads the same shapes. A deleted nested `replaces` is not guarded: the compiler cannot see which payloads are still in flight, as for a top-level event field.

# 0785 — Collection entries are stored per entry, in a layout frozen for 1.0

- **Status:** Accepted (v0.535)

**Context.** An agent's whole state was one value under the key `state`, so a handler that touched one entry of a large `Map` read and wrote all of it, and the value hit the platform's 8 MB limit. The per-entry storage track (retired; see [`design/archive/retired-tracks.md`](../archive/retired-tracks.md), #3195, proposal #3189) moves each collection entry to its own key. The slices before this one added the forward-compatibility guard (a build faults on a layout it does not know), the handler serialisation that makes a load-modify-commit cycle safe, the runtime primitives, and the sweep and revert reporting. This slice writes the layout. It has to land before the stored-state freeze at 1.0 (ADR 0538), so the stored bytes it settles are the ones every later build keeps reading.

**Decision.** From this build an agent's stored state is:

- `state`: the `Cell` fields, `__v` when the agent has a schema lock, and `__layout: 2`. No collection is in it.
- `m/<field>/<key>`: a `Map` entry `{ i, v }`; a `Cache` entry `{ v, exp, i }`. `s/<field>/<key>`: a `Set` element `{ i }`. `l/<field>/<time>-<seq>`: a `Log` entry `{ t, v }`.
- `i/<field>/<index>/<by>/<primaryKey>`: one `@indexed` posting, value `1`. `x/<field>/<exp>/<key>`: a `Cache` expiry entry, value `1`, so a later slice can reap by range.
- `c/<field>`: `{ size, seq }`, the field's entry count and the next insertion sequence (a `Log`'s next `<seq>`). Written once a field has an entry.

Key parts are escaped reversibly (`%` to `%25`, `/` to `%2F`), numbers are fixed width, and keys sort as UTF-8 bytes. `i` is the entry's insertion sequence: a new key takes the field's next `seq`, an overwrite keeps its `i`, a key removed and inserted again takes a new one. A read sorts by `i`, so a `Map` reads back in insertion order whatever the keys' byte order, and a posting list reads in its entries' `i` order. The `Map`/`Set`/`Cache` stay `Record`s in memory, and a `Record` enumerates integer-like keys (`"10"`) first, in numeric order, so an in-memory iteration of such keys is not insertion order; the stored order is, and a reload restores it. That residual difference lies in how the collections are lowered, not in storage, and is tracked as the follow-up #3254.

`loadState` reads the record and, for a per-entry one, lists the entries and joins them back into the wholesale-shaped record, so a migration step and the rehydration gate see what they always saw. A record with no `__layout` (the wholesale layout) is handed back as it is and not written on load, so a migration step reads it as the stored version shaped it and a handler that only reads, or faults, leaves it untouched. Its first commit splits the state that handler produced, with the marker, in one transaction, so a crash leaves either the old record or the new layout, never a mix, and the split never uses a field kind the stored record did not have. `commitState` encodes the state, diffs it against the entries the handler read (kept per instance, replaced only once the write has landed), and writes the changed entries, the deleted ones and the `state` record in one transaction. A handler that faults before its commit writes nothing, and its base is untouched. The instance serialises its handlers (#3217), so the base cannot be stale. A write is batched at the platform's 128 keys. `bynk migrate sweep` wakes each instance, which loads it and commits a record that has no marker, and that commit does the split. `bynk_emit::STORAGE_LAYOUT` is 2, so each version's deploy facts record it and `bynk deploy revert` refuses a rollback across it while instances hold data.

**What a later slice may not change.** This slice reads every entry of a collection eagerly. A later slice teaches handlers to read one entry, or one index range, lazily. It needs nothing that is not stored here: the insertion sequence and the count and next-sequence record are already in the frozen layout, and so are the postings and the expiry entries. That slice therefore changes no stored byte, and a build from before it reads and writes the same layout.

**Consequences.** Every agent's state record carries `__layout: 2` after its first load and commit, including an agent with no collection. A rollback to a build that predates the layout faults `NewerLayout` and `bynk deploy revert` refuses it, as the forward-compatibility guard and the revert preflight were built to. A migration step reads the record as the stored version shaped it: `loadState` joins every per-entry key found in storage, by the prefix it is under, not by the current class's field list, so a step can read a collection the new version removed or re-kinded. The commit then writes the state the step produced and deletes the per-entry keys that state no longer has, so a collection the step drops, or a field it re-kinds, has its old entries deleted in the same transaction. With no step, a stored collection the definition no longer declares is kept, as the unknown-key rule keeps any stored field: it is joined into the record and written back inline. Reading all of a collection still lists every key, so the saving is in storage writes and in values held, not yet in reads; the lazy-read slice is what removes the rest. A commit still plans and diffs every entry the handler read, and the base is held in memory, so a handler's CPU and memory, unlike its storage I/O, still grow with the state until then. A `Log` key's time component never goes backwards: an entry appended with an earlier `t` than the last takes the last key's time, so keys sort in append order, and the entry keeps its own `t`. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

# 0521 — The web extension loads each `bynk.toml` folder through `vscode.workspace.fs` and analyses it as one in-memory project

- **Status:** Accepted (v0.361.3)

**Context.** Slice 1 of #2102 analysed each open file on its own, so a context's `uses` of a sibling commons couldn't resolve. The worker hid that cascade (`bynk.uses.unknown_commons`, `bynk.suite.unknown_target` and the `bynk.resolve.*` errors they cause), which also hid real errors in those files. `run_checks` already accepts an in-memory overlay and a caller-supplied file list. The single-source wasm path feeds it one file that way.

**Decision.** `bynk_emit::project::analyse_in_memory_project` takes a map of project-relative paths to text (`bynk.toml` plus every `.bynk` file) and runs `run_checks` in `Analyse` mode, rooted at the empty path, so every path in the result stays relative. `[paths] include`/`exclude` are read from the in-memory `bynk.toml` and normalised like the keys (`./src` is `src`; the root is the empty path). An absolute entry can't name a file in the project, so it is dropped and reported as a project warning (`warnings` in `bynk_analyze_project`'s result), which the worker shows once. An `include` left empty that way falls back to the conventional layout. With no `include`, the conventional layout is decided from the files (`src`, `tests`, else the root) rather than from `ProjectPaths::conventional`'s disk probe. It returns every file's diagnostics, plus expression types and locals keyed by path. `bynk-wasm` exposes it as `bynk_analyze_project(files_json, platform?)`, `bynk_hover_project(files_json, path, offset, platform?)` and `bynk_complete_project(files_json, path, offset, platform?)`, with the files as one `{ path: text }` JSON object. Completion shares one implementation with the single-source path and only swaps the analyser. It also passes the project's sources to `bynk_ide::completion` for its cross-unit candidates, and an offset that isn't a character boundary now yields no candidates instead of a panic.

The client treats each workspace folder with a `bynk.toml` at its root as a project. It walks the folder with `vscode.workspace.fs.readDirectory` rather than `findFiles`, which not every web host backs with search, skipping dot-directories, `node_modules`, `out` and `target`, and stopping at 2000 `.bynk` files. It also reads each adapter's `binding` module, resolved against the adapter's directory, because the analysis reads binding modules from the same map and otherwise reports `bynk.adapter.no_binding`. It sends the snapshot to the worker (`bynk/projects`), and again after a worker restart. File watchers, saves, and files created, deleted or renamed through the editor send single-file updates (`bynk/projectFile`). The editor events matter because not every web host's filesystem reports to watchers. Those updates follow the walk's rules: a skipped directory or a new file past the cap is dropped, and so is an open editor's text for a file the walk would skip. A deleted folder takes every project file under it, and a folder created or renamed in makes the client walk the projects again. An update read against a project snapshot that a reload has since replaced is dropped. After any adapter change, saved or still being typed, the client re-derives the binding modules, reads the newly named ones and forgets the ones no longer named. A named module's own changes are sent like a `.bynk` file's. A `bynk.toml` appearing or going away reloads every project, and of overlapping reloads the last one started wins. The worker overlays open editors' live text on the files it was sent, re-analyses the whole project, debounced, on any change, and publishes diagnostics for every file in it. It clears files that no longer have any, along with any single-file diagnostics left from before the project arrived. A file outside every project keeps slice 1's single-file analysis and filter. The status bar reads **Bynk (web)** in a project and **Bynk (web, single-file)** outside one.

**Consequences.** A Bynk repository opened in vscode.dev checks like it does on the desktop: cross-file names resolve, a cross-file misuse is reported, and errors in unopened files reach the Problems panel. Every edit re-analyses the whole project in wasm and re-sends all its text across the worker boundary for hover and completion. That is fine at the size of the repository's examples, but it is the cost to watch, and an incremental project cache in the wasm module would be the fix. The 2000-file cap keeps a huge tree from stalling the browser on its first load. Navigation, rename and references still need `bynk-lsp` on wasm, the follow-up slice 1 recorded.

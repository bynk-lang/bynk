# 0989 — A generic type that wraps its parameter in an Effect takes no Effect

- **Status:** Accepted (v0.724.1)

**Context.** #4324 refused `Effect[Effect[T]]`, written or built by instantiation, but left one hole, recorded in its ADR and filed as #4364: a user generic type whose declaration holds its parameter directly under an `Effect`, given an effect for that parameter, has a field of type `Effect[Effect[Int]]`, which cannot exist at run time. The issue's own repro, `type Wrap[T] = { v: T }` with `Wrap[Effect[Int]]`, is not that case: the field is then an effect held in a record, which is legal, like a `List[Effect[T]]`. The hole is `type Wrap[T] = { v: Effect[T] }`.

**Decision.** Refuse it, with the same `bynk.types.nested_effect`. A parameter counts as wrapped when the type's declaration puts it directly under an `Effect` in a record field or a variant payload, at any depth of containers, or applies another generic type to it at a position that type wraps (`type Outer[U] = { w: Wrap[U] }`). It is refused in the two places #4324 refuses the direct shape. At type resolution, a written `Wrap[Effect[_]]` is refused at the argument. At instantiation, a generic call or method whose declared return type does not nest but whose substituted return type applies such a type to an effect is refused, by the same signature-versus-instantiation rule: `fn make[T](x: T) -> Wrap[T]` stays legal, and `make(e)` with `e: Effect[Int]` is refused. A parameter held directly (`type Box[T] = { v: T }`) takes an effect and is pinned as accepted. The wrapped positions are a fixpoint over the generic types reachable from the one applied, started from nothing and only growing, so any cycle among declarations ends and a recursive type that permutes its own parameters (`type Swap[A, B] = { x: Effect[A], next: Option[Swap[B, A]] }`, where `B` is wrapped one level down) is answered correctly, in time linear in the declarations reached. The check reads the declaration and not its instantiated field types, so it never has to build one. The inferred error carries the same note as the written one, naming the wrapper and the parameter.

**Consequences.** Breaking only for a program that already built an impossible type. Only a direct `Effect` argument counts, as in #4324: an argument that merely contains an effect (`Wrap[List[Effect[Int]]]`, giving `Effect[List[Effect[Int]]]`) is not a nested effect. A type alias that expands to an effect is not looked through, which the resolver does not do for #4324's direct shape either.

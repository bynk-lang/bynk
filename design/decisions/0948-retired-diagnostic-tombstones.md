# 0948 — Retired diagnostic codes are tombstoned, not forgotten

- **Status:** Accepted (v0.686)

**Context.** Removing a diagnostic code made `bynk explain <code>` report it as unknown, so a user upgrading, or reading an old CI log or issue, got no explanation.

**Decision.** `bynk-syntax/src/diagnostics.rs` holds a `RETIRED` table beside `EXPLANATIONS`: the code, the last release that carried it, one sentence on why, and what replaced it. `bynk explain` prints that instead of "unknown" and exits successfully. Each tombstone is also written to `site/src/generated/diagnostics/retired/<code>.json`, one file per code like the live ones. The site builds a short page for each at `/reference/diagnostics/<code>/`, so an old log's `/d/<code>` link still lands, and the index lists them under "Retired codes", alphabetically. `bynk-syntax/shipped-codes.txt` lists every code any release has carried. A docs-consistency test fails when a listed code is neither in `REGISTRY` nor in `RETIRED`. The check is one-way: a new live code needs no line in the list, so no diagnostic-adding PR touches it; `cargo xtask release-page --apply` appends the registry's codes at each release cut, so it grows without anyone editing it. The list was seeded from the registry at the latest release, `v0.661.1`; codes retired in earlier releases were not recorded and have no tombstone.

**Consequences.** The entry records the last release that carried the code, not the version that retired it: the change that removes a code cannot know its own version, which the merge-time stamp assigns. It is the latest release page when the change is written; a release cut while the change is open is the reviewer's to catch. A code added and removed between two releases never shipped and needs no tombstone. Removing a shipped code means adding a `RETIRED` entry in the same change. The table's first entry is `bynk.http.multipart_body_unbounded`, retired by #4276.

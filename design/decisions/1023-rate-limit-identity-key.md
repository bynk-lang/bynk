# 1023 — A route counted by identity verifies its caller before the body is read

- **Status:** Accepted (v0.759)

**Context.** `@rateLimit(Limiter, key: clientIp)` counts by address and is asked before anything else. A limit per user needs the caller's identity, and the router reads and decodes a non-sum route's body in the entry before its compose wrapper verifies the actor, so an identity-keyed limit asked after the verification would be asked after the body read, which is what the annotation exists to avoid. The route's verification therefore has to move ahead of the body read, for the routes that ask for it.

**Decision.** [DECISION A] `key: identity` is accepted on a route whose `by` is a single `Bearer`, `Oidc` or `SignedCookie` actor, and counts by the verified `sub`. It is `bynk.http.rate_limit_key_unavailable` on a `Visitor`, a `Signature` sender and an actor sum, which have no one identity to count by. [DECISION B] The compose wrapper of such a route is two methods in place of one: `<route>__verify(request)` runs the seam's own statements unchanged, in their order, and gives `{ tag: "Err", error }` (the `HttpResult` the wrapper would have returned: `Unauthorized` or `Forbidden`) or `{ tag: "Ok", value: { key, principal } }`; `<route>(params…, principal)` runs the handler with the principal the verification left. Both are built from the same statement builders as the ordinary wrapper, which is `verify` then `run` fused, so no check can be in one and not the other. A `SignedCookie` route's `verify` holds everything the seam does before an identity is trusted: the cross-site refusal of a state-changing request, the cookie's signature, key, audience and lifetime, and, with `sessions = true`, the session-live check. [DECISION C] The entry runs, for such a route: `verify`; a refusal renders through the route's own response policy (challenge, CORS, security headers, `on rejected`); the limiter, keyed by the verified `sub`, with `429` on refusal; then the media-type and length checks, the body read and decode, and `run`. Verification therefore runs exactly once. [DECISION D] The order of refusals is: a credential that fails verification is `401` or `403` and never reaches the limiter, so one caller's forged or expired requests cannot spend another's budget, and a verified caller over the limit is `429` ahead of any `415`, `413` or body work. [DECISION F] The limiter key of an identity route is scoped, `identity:<Actor>:<sub>`, not the bare `sub`. A limiter is shared by every route that names it, so a bare `sub` would put different actors' subs (an `Oidc` issuer's and the app's own user ids) and the addresses a `clientIp` route counts in one key space, where user `42` of one trust domain would spend user `42`'s budget in another. The actor's name scopes the `sub` to its own trust domain, and `identity:` cannot begin an IP address, so the two key kinds cannot collide. The alternative, refusing a shared limiter across actors or key kinds, would forbid a legitimate shared budget; `clientIp` keys stay byte-identical. [DECISION E] A route without `key: identity` is byte-for-byte unchanged: the emitted goldens of every existing route did not change.

Correction carried from part 1: the request-lifecycle page now describes the real order for an ordinary route (the body is read and validated, then the actor is verified by the wrapper), and notes that a `key: identity` route verifies first.

**Consequences.** A per-user limit is a one-line annotation, counted only for callers who proved who they are, and a flood of forged credentials costs a verification and a `401`, not a limit and not a body read. The `RateLimit` instance of the context is still the only configuration. A caller's verified identity is the key, so two users behind one address count separately and one user from many addresses counts together, and two routes naming one limiter share a budget per actor and caller.

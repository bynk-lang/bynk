# 1112 — An agent's event outbox row carries a format version and is part of the 1.0 stored-data promise

- **Status:** Accepted (v0.828.3)

**Context.** The agent outbox (the at-least-once ADR of this slice) writes rows into the agent's Durable Object storage, where they can outlive the build that wrote them: a crash, a failed flush, or the Queues daily cap can leave rows pending across a redeploy for hours or longer. [ADR 0538](0538-stored-state-version-marker-and-frozen-encoding.md) made the encoding of stored agent state part of the 1.0 data-compatibility promise. Outbox rows are stored data of the same kind and need the same promise, fixed before the first row is written (track §10 slice 0 (e)).

**Decision.**

1. *Place.* A row is stored under the reserved key `o/<seq>`. `<seq>` is the instance's outbox counter, assigned at commit in emission order and written as 16 zero-padded decimal digits, so the storage listing's lexicographic order is commit order (the order a later, opt-in envelope `sequence` would need). The counter is stored under the reserved key `n`, as a JSON number holding the next `<seq>`, and is read and advanced in the commit's own transaction, so two commits never take the same `<seq>`. The erasure marker is the reserved key `e`. All three are outside every key and prefix the runtime already uses (`m/`, `s/`, `l/`, `i/`, `x/`, `c/` and `"state"`).
2. *The counter outlives a logical erase.* The reuse-after-logical-erase path keeps `n` with the `o/` rows and `e`, and only the physical `deleteAll()` clears it, which runs only once the outbox is empty. So a restarted counter can never overwrite a pending row. After a physical erase the counter starts again from 0, as the instance's state does. (The track's text has that path keep only `o/` and `e`; keeping `n` too is the refinement this needs.)
3. *Shape.* A row is `{ "v": 1, "type": <event>, "payload": <encoded payload>, "envelope": <envelope>, "sent": [<queue>, …] }`: the emission as committed, plus the subscriber queues it has already reached. The targets are computed at flush time from the running build's routing table, so a row written before a redeploy goes to the subscribers the running build knows.
4. *Versioned and frozen within 1.x.* `v` is mandatory. A 1.x runtime flushes every row version any earlier 1.x runtime wrote. A change to the row's shape bumps `v` and carries the reader for each earlier version through 1.x; dropping a reader is a 2.0 event. A row whose `v` is above the running runtime's (a rolled-back deploy) is not flushed or rewritten: it stays stored and is logged, as ADR 0538's `NewerSchema` rule refuses to decode a newer state record, and it is flushed once a runtime that knows the version runs. So that rule fits the flush the at-least-once ADR describes:
   - a flush's loop stops when a listing finds no row *this runtime can flush*, so a newer row never keeps it spinning;
   - "the outbox is empty", which deletes the alarm, counts every row, newer ones included. While a newer row remains, the alarm stays set at the backoff's 1-hour ceiling, so a roll-forward drains the row without waiting for the instance's next request, and the cost is one invocation an hour per affected instance for as long as the rollback lasts;
   - the physical erase waits for an outbox empty of every row, so an instance logically erased under a rollback stays logically erased, its old keys stored but unreadable, until a runtime that can flush its rows has done so.
5. *Operations honour it.* `bynk migrate sweep` and agent moves (#3819) preserve or flush pending rows, with `n`, before they touch storage, and honour `e`.

**Rejected.** An unversioned row (the first shape change would leave pending rows unreadable after an upgrade). Draining the outbox as part of each deploy instead (a deploy cannot reach every instance, and the Free-plan cap can hold rows past any deploy).

**Consequences.** The outbox slice builds against a fixed place, shape and compatibility rule, and its runtime tests include a row written by an older runtime version. `design/bynk-1.0-definition.md`'s stored-data carve-out covers outbox rows beside agent state when that slice lands.

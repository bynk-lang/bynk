# 0784 — A revert refuses a rollback to a build that writes an older storage layout when instances hold stored data

- **Status:** Accepted (v0.534)

**Context.** The per-entry storage track (`design/tracks/per-entry-storage.md`, #3195, proposal #3189) will move collection entries to keys of their own and mark the `"state"` record with `__layout: 2`. A build that predates the layout, reading the new layout, would zero-merge the collections it no longer finds inline and write the record back wholesale, orphaning every per-entry key; a build with the forward-compatibility guard (ADR for slice 0) faults `NewerLayout` instead. The runtime fault protects data but turns a rollback into an outage. `bynk deploy revert` already refuses a rollback across a schema-version bump when stored instances exist (ADR 0545, `NewerSchema`), reading each version's recorded deploy facts; it knows nothing about layouts. The review of slice 0 (#3209) asked that the writer slice's loud runtime fault be backed by a refusal at deploy time.

**Decision.** A version's deploy facts gain an optional `layout`, the storage layout the build writes (`bynk_emit::STORAGE_LAYOUT`). It is recorded only beyond the original wholesale layout 1, and an absent one reads as 1, so every existing record, and every record this build writes today, is unchanged and still readable. `bynk deploy revert` then checks, per Worker: when the live version's layout is above the target's, every agent class the two versions share is probed for stored data exactly as for a schema-version difference, and the revert is refused (check `layout`) when any instance holds stored data, when that is not known, or when it was not read. With no stored data it passes. A target on the same or a newer layout (the upgrade direction) needs no check. The check does not distinguish a target that has the guard from one that does not: both are unsafe over stored data, so one rule covers them. The check is separate from `agent`, so a rollback that differs in both schema version and layout reports both.

**Consequences.** No behaviour changes today: `STORAGE_LAYOUT` is 1, so no facts record carries a layout and no revert is refused by this check. The slice that first writes the new layout raises `STORAGE_LAYOUT` together with the emitter's writer, and from then on a revert across it is refused while instances hold data. The way back is to deploy a fix forward, as for a schema-version rollback. The Book's rollback guide lists the new check. The check guards `bynk deploy revert` only: redeploying an older tag with plain `bynk deploy` pushes that build over the live data without it, as it would across a schema-version bump today; a preflight for that path is a follow-up for the writer slice to decide. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, name or signature changes.

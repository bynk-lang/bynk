# 1034 — A Bearer WebSocket upgrade offers `["bynk.bearer", token]` and the 101 selects `bynk.bearer`

- **Status:** Accepted (v0.770.1)

**Context.** The reference and the guide tell a browser to connect with `new WebSocket(url, [token])`. The generated upgrade read the token as the first element of `Sec-WebSocket-Protocol`, but the `101` carried no `Sec-WebSocket-Protocol`. Under the WHATWG WebSockets standard, when the client offered subprotocols and the response selects none, the browser fails the connection. Clients that do not enforce this (Node's `ws`, test harnesses) connected, which is why nothing caught it (#3900).

**Decision.** A: the client offers the pair `["bynk.bearer", token]`. The Worker requires `bynk.bearer` among the offered subprotocols and takes the element after it as the token, and the `101` selects `bynk.bearer`. Echoing the token as the selected protocol was rejected: it works, but it puts the credential in a response header that proxies and logs may record. A query-string token was rejected: it is logged by default almost everywhere. B: the old single-element form is refused with `400` and a fixed message naming the pair (`Offer the subprotocols ["bynk.bearer", <token>]`, never the client's text). It only ever worked for clients that do not enforce the standard, so the break is small, and a `401` would hide the cause. No offer, the marker with no token, and a bad, expired or foreign-secret token stay `401`. C: an upgrade to a `None` actor offers no subprotocol and is answered with none, as before; the same pair will carry an `Oidc` token when `Oidc` is admitted on `on open` (a later increment). D: the selected protocol is added by the Durable Object's `101`, through the runtime helper `webSocketUpgradeResponse(client, protocol)`, so both the single-context and worker-group paths get it; the Worker passes the response through unchanged. The helper `webSocketBearerOffer` parses the offer for the Worker's single-actor and actor-sum paths alike, so the rule is one function, tested at the runtime level and driven through the emitted Worker's `fetch` for the `400` and `401` paths. The browser handshake itself, through the `system` upgrade driver, is proved by the `system`-tier upgrade driver issue (#3901), which closes this issue.

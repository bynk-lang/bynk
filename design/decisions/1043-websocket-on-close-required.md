# 1043 — A WebSocket service must handle a departure: `on close` is required and carries `CloseInfo`, and the Durable Object completes the close handshake

- **Status:** Accepted (v0.781)

**Context.** `on open` always transfers the connection into an agent's state (ADR 0577, `bynk.ws.open_transfer_shape`), so every connection is held somewhere and has to be released when the client goes. The ownership rules (`bynk.held.leak`) cover the code paths an author writes; a client disconnecting is the one path only the compiler can require a handler for. `on close` was optional, so a service without it kept a departed client's `Connection` in the agent's store, and a `parTraverse` broadcast raises the first fault, so one client leaving could break every later broadcast to the room. The generated `webSocketClose` discarded the close details and never replied with `ws.close()`, Cloudflare's own pages disagree on whether that reply is still needed under `web_socket_auto_reply_to_close`, and no `webSocketError` was generated at all (#3902).

**Decision A — `on close` is required.** A `from websocket` service without one is `bynk.ws.missing_close`, with a note that the connection `on open` handed over must be released. Rejected: letting the runtime remove the connection from agent state automatically; it does not know which store entry holds it, and implicit removal from a user's `Map` would surprise authors.

**Decision B — `close: CloseInfo` is an optional trailing parameter of `on close`.** `CloseInfo { code: Int, reason: String, clean: Bool }` is a `bynk` record. It is recognised by its first-party declaration, so a user type called `CloseInfo` is a route value, and it is excluded from the positional route-prefix match against `on open`. In a test, `svc.close(tc)` gives `CloseInfo { code: 1000, reason: "", clean: true }` and `svc.close(tc, CloseInfo { … })` sets it; passing one to a handler that declares no `close: CloseInfo` is a `bynk.test.service_call_arity` error. `TestConnection` also gains `closeCode()` and `closeReason()` (`Option`s) so a case can assert what the server closed with.

**Decision C — `connection.close(code?, reason?)`.** Both are optional and it still consumes the connection. A literal code outside `1000` and `3000`–`4999` is `bynk.ws.bad_close_code` (this also excludes `1004`, `1005`, `1006` and `1015`, which are never sent); a computed one faults. A literal reason over 123 bytes of UTF-8, the protocol's limit, is `bynk.ws.bad_close_reason`; a computed one is truncated on a character boundary. `Connection` joins the kernel-method registry, so `conn.` completion offers `send` and `close`, and signature help reads `close(code?: Int, reason?: String)`.

**Decision D — the generated `webSocketClose` always completes the handshake,** after the user's `on close` has run, even when it faults. It echoes the peer's code and reason only when that code can be sent (1000–4999, except 1004, 1005, 1006 and 1015) and otherwise calls `ws.close()` with no arguments, Cloudflare's recommended form. Replying is harmless under the auto-reply flag, so Bynk does not depend on which page is right. This lives in the runtime's `webSocketClosing`, so the emitted method stays a thin call.

**Decision E — `webSocketError` is generated.** It logs the error's class name (never frame contents), closes the socket with `1011` and runs `on close` with `CloseInfo { code: 1011, reason: "error", clean: false }`, so the agent releases the connection exactly once. `on close` runs at most once per socket: the runtime marks the socket's attachment closed before running it, so a later `webSocketClose` for the same socket replies but does not run it again.

**Consequences.** Every WebSocket service handles a departure, can see why the connection ended, and can close with a code and reason, and the platform's close handshake always completes. A service that compiled without `on close` fails with a note saying what the handler must do; the fix is one handler, and such a service already broke broadcasts when a client left. The behavioural proof of the Durable Object's close path is the emitted class driven under Node (`ws_close_handshake`); driving a real upgrade through the deployed Worker is #3901.

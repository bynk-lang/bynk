# 1116 — A commons suite tests capability parameters through kind doubles and suite-local instances

- **Status:** Accepted (v0.830)

**Context.** #3959, slice 3 of the capability-parameters track (`design/tracks/capability-parameters.md`, §9). Slices 1 and 2 let a commons function take capability parameters and a context bind them. A commons suite had no seams, so a library over a capability could not be tested where it is written. And a function with two parameters of one kind needs two distinct doubles to be tested honestly.

**Decision.** (A) *Kind doubles.* A commons suite's `deps` are the doubles of the first-party capabilities its commons selects, built as a context's flattened capabilities are, fresh per case and wrapped by the recording proxy when a case observes. A commons suite case holds them, so a kind's name on the right of a binding (`given Store = Kv`), or as the subject of `stub` or `expect … called`, is that kind's double. A shared capability's double works the same way (`expect Logger.info called`). Naming one in a suite still follows the per-file import rule of #3536: the suite file `consumes bynk.cloudflare { Kv }`, as a context's suite does for a flattened capability. A commons that selects no capability keeps the empty `deps`, so every existing commons suite emits as before. (B) *Suite-local instances.* A commons suite may declare `capability Archive = Kv`: a fresh double of a kind its commons selects, with no binding and no deploy effect. It is shared by every suite of its commons, as their doubles and `deps` factory are, so a name is declared once per target (a second declaration, in any suite file, is `bynk.resolve.duplicate_capability`, pointing at the first). It joins a copy of the target's table that only the test phase and the test emitter see, as a derived capability of the target would, so its cases hold it and its `deps` build its own double. It is refused in a suite whose target is not a commons (`bynk.capability.derived_outside_context`), and a commons itself still cannot declare one (`bynk.capability.outside_context`). Its base must be selected by the commons (`bynk.capability.unknown_base`) and have instances (`bynk.capability.base_not_instantiable`), and its name may not be a capability of the commons (`bynk.resolve.duplicate_capability`). It is experimental under `bynk.given.parameters`. (C) *A parameter is never a seam.* A `stub` naming a capability parameter is `bynk.stub.not_a_seam`, and an `expect … called` naming one is the existing `bynk.observe.not_a_seam`; each carries a note naming what to stub instead (the kind's double in a commons suite, the bound instance in a context's suite). The note is reached when the name is a parameter of a commons function in the project. (D) *Setup over a parameter.* A `given` suite helper names the doubles a case holds (`fn seed() -> Effect[()] given Kv`); setup over a parameter lives in a test-only commons, which a case calls with a binding.

**Consequences.** A library over a capability is tested in its own suite, with each double fresh per case. The emitted output of every existing fixture is unchanged. Tooling for bindings and the guide are slice 4's.

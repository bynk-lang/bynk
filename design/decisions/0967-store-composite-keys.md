# 0967 — Store collections take any Key type, held under the canonical key encoding

- **Status:** Accepted (v0.703)

**Context.** A `store Map`/`Cache` key and a `store Set` element had to be `String`, `Int` or a refined or opaque type over one (`bynk.store.unkeyable_key`), while a value `Map` or `Set` already takes any `Key` type, held under a canonical encoding (`__bynkKeyEncode`). A model keyed naturally by `(region, sku)` or by a sum had to invent a string key and parse it back.

**Decision.** The store key rule is the `Key` rule. A scalar key (`String`, `Int`, or a refined or opaque type over one) keeps its stored form, `String(k)`, so existing state reads unchanged and needs no migration. Any other `Key` type is stored under its canonical encoding: the entry key is `m/<field>/<escaped encoding>` (`s/` for a `Set`, with the same escaping of `%` and `/`), and two keys are one entry exactly when they are `==`, as for a value collection. An `@indexed(by:)` field may be any `Key` type, its posting keyed by the same encoding. `bynk.store.unkeyable_key` and `bynk.index.unkeyable_key` remain, for a type that is not a `Key` (a `Float` at any depth, a `Map`, a `Set`, a function), and now say which part is not. Changing an existing field's key type from a scalar to a composite one is a non-additive schema change, refused by the schema lock as for any other key-type change. A composite key's encoding counts towards the platform's 2 KiB limit on one storage key: the emitted code builds the entry key through `__bynkStoreKey`, which faults any operation, a read as much as a write, whose key would exceed it with a message naming the field and never the key's value; the limit is checked against the longest key the encoding appears in, a `Cache`'s expiry entry, and an index posting, which holds the indexed value and the entry key together, is checked the same way. Because the encoding is the stored key, the schema lock refuses a record field added beneath a key position (a `Map`/`Cache` key, a `Set` element, an `@indexed` field's record), even with a default, since that would change every stored key's encoding and orphan the entries; a new sum variant stays additive, and so does a new field in the map's value.

**Consequences.** Nothing that compiled before changes meaning: the rule only admits more programs, and a scalar key's emitted code and stored form are byte-for-byte the same. The canonical encoding was already a stored contract for value collections and is now one for store collections too, pinned by fixtures for records, sums, `Option`, `Decimal` and `Bytes` keys. A store collection still exposes no key accessor, so a key is never decoded back from its encoding. Hover, completion, semantic tokens and signature help are unchanged, because no syntax, declaration or type shape changed.

# 0726 — A context function may declare `given`

- **Status:** Accepted (v0.501)

**Context.** A function reached a capability only through function values its caller passed in (ADR on #2719). Handler steps that log, query and decode were therefore repeated in every handler, or factored into a function that took `log: (String) -> Effect[()]` and a lambda per call: correct, but ceremonious enough that authors chose repetition. #2010 noted the same gap (`bynk.parse.expected_token` on a `given` after a `fn`).

**Decision.**

- **A. Context-level free functions only.** `fn f(…) -> Effect[T] given Logger, Orders` is legal in a context, where the `consumes` clause says which capabilities exist. A commons is shared by contexts that may consume different capabilities, so a commons function (and a suite helper) keeps the function-value style; a `given` there is `bynk.given.fn_outside_context`, with a note that points at the function-value spelling. Three further refusals, all `bynk.given.fn_unsupported`: a method (a method call has no place to carry the capabilities), a function that does not return `Effect[T]` (a capability operation is an effect), and `given Events` (`Events.emit` buffers until its *handler* commits, so it cannot be hidden in a callee).
- **B. The caller's `given` must include the callee's**, checked at each call (and each reference to the function as a value) against the body the call is written in. Every function on a path declares what it needs, so the rule is transitive without a graph walk, and recursion and mutual recursion need no fixed point. A body that lacks them gets `bynk.given.missing_for_call`, naming the missing capabilities only, with a machine-applicable fix that adds them to the caller's `given`. A call counts as a use of the callee's capabilities in the caller, so the caller's `bynk.given.unused_capability` does not fire for a capability it only passes on. A capability used in a `given` function but not listed in it is `bynk.given.undeclared_capability`, reported by the resolver (the function's names are resolved there), with a note about `given`.
- **C. Emission follows #2719.** A function that declares `given` takes a hidden `deps` parameter, typed as exactly the capabilities it names, after the comparator witnesses and before `__exec`. Its capability calls lower as in a handler (`deps.Logger.error(…)`), and a lambda in its body closes over `deps`. Every call passes the caller's own `deps` on (`cx.cap_deps_expr()`), which carries them because B makes the caller declare them; a reference to the function as a value closes over the `deps` in scope where it is named. No runtime change.
- **D. Generic `given` functions are allowed.** Capability operations keep their own explicit type arguments.
- **Tests.** A test `case` may call such a function directly. A handler is called by a `case` with the harness's `deps`, which carries the target's capabilities and their stubs; a function is called with the same `deps`, so the choice that matches how cases call handlers is to supply the capabilities, not to refuse. The B rule is waived in a case body, which declares no `given`. `stub` and `expect Cap.op called …` observe calls made inside the function, since they apply to the capability, not the call site. A suite's helper `fn` cannot declare `given` (`bynk.given.fn_outside_context`); suite helpers are pure (`bynk.suite.fn_effectful`) and so cannot call a `given` function either.
- **Surface.** `given` follows the return type, ahead of `where` and the contract clauses, as it follows a handler's return type. The formatter, tree-sitter grammar, hover, signature help and completion detail show it; semantic tokens and completion inside the clause are the existing `given_clause` handling.

**Consequences.** Shared handler steps are written once. The capability set stays visible in every signature on the path, which is the point of `given`. A `given` function's emitted TypeScript signature gains a trailing `deps` parameter; this is codegen, not published ABI (ADR 0310 D1). A function named as a value is now imported where it is named, so a sibling file's function passed as a value no longer needs a call to bring its import. A `given` function cannot make agent or cross-context service calls (neither resolves outside a handler). A later step could add capability parameters to commons functions.
